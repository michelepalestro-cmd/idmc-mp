### L-MCP-001  Enumerate the org's managed MCP registry before declaring an MCP wall
**Kind:** OVERTURNED · **Proven:** 2026-09-23 · **Evidence:** 19 servers enumerated and tested with one read-only login (2026-09-23); registry reads in two orgs (2026-09-28) · **Supersedes:** L-MCP-069, L-MCP-070, L-MCP-071
GET `https://hdm.<domain>.informaticacloud.com/a2e-mcp-asset-mgmt-svc/api/v1/mcp-servers?type=MANAGED` with IDS-SESSION-ID: `<v3_session>` lists every managed MCP server of the org with id, name, serverEndpointUrl and context (for example jobmanagement, connectionmanagement, secureagentmanagement, diassetpromotion, cdgccatalogenrichment, cdgcsearchmetadata, cdgcdataqualityscore, dataqualityagent, dqverifyaddress, dataexplorationagent, datamanagementorchestrator, troubleshooting, logmanagement). One org exposed 19 servers with about 140 tools. A verdict based only on the MCP servers wired into the current session, or on GET /public/core/v3/mcpServers, is wrong: run tools/list against each server's serverEndpointUrl first-hand.

### L-MCP-002  What the managed MCP servers can and cannot do
**Kind:** ROUTE · **Proven:** 2026-09-23 · **Evidence:** Tool lists read first-hand with tools/list per server
Seen in one org's registry: jobmanagement (run mapping, synchronization, replication, linear and published taskflows, masking; monitor, stop, terminate), connectionmanagement (create, update and test connections), secureagentmanagement (update_runtime_environment_selections enables services and connectors), diassetpromotion (export and import of asset definitions), cdgccatalogenrichment (glossary, classification and business-metadata writes), cdgcsearchmetadata and cdgccatalogdiscovery (natural-language search, get_asset_details with lineage), cdgcdataqualityscore (get_asset_score), dataqualityagent (the DQ agent), dqverifyaddress, searchcustomer (MDM fuzzy match), dataprovisioning (checkout_data_order), usermanagement (users, roles, groups), ipumanagement (metering exports), troubleshooting, logmanagement and auditmanagement (read-only diagnostics), datamanagementorchestrator (orchestrate) and dataexplorationagent (data_explore). The writes that the old 'MCP can't write' list denied (connections, connector enablement, glossary, roles, imports) all exist.

### L-MCP-003  No managed MCP verb authors a new CDI field mapping, deploys a DBMI task or publishes a CAI process
**Kind:** WALL · **Observed:** 2026-09-23 · **Evidence:** Full enumeration of the managed registry with one read-only login
Across all 19 managed servers (about 140 tools), including datamanagementorchestrator.orchestrate, no verb authors a brand-new CDI mapping definition, deploys a Database Ingestion task or publishes a CAI process: diassetpromotion import lands asset definitions only, and jobmanagement runs only tasks that are already deployed or published. Use REST: package synthesis and import for mappings, task/deploy and job/start on the `<pod>-ing` DBMI API, and POST /active-bpel/asset/v1/publish on `<pod>-cai`.

### L-MCP-004  The April 2026 managed catalog: five servers and eleven actions (argument reference)
**Kind:** ROUTE · **Documented:** 2026-07-26 · **Evidence:** Vendor guide 'Getting Started with Informatica MCP Servers - Headless Data Management' (April 2026) pp.7-8
Address Verification: verify_address (validate, standardize, geocode; persists nothing). CDGC Metadata Search: search_metadata (knowledgeQuery, a natural-language string) and get_asset_details (id, scheme; includes lineage, profile and descriptions). Customer Identification: search_master_record (fuzzy match to a business id) and get_master_record_details (the golden record). Data Provisioning: list_data_collections (limit, search), list_delivery_targets (id, segments; returns collection detail, not targets) and checkout_data_order (dataCollectionId, justification, targetRef; raises a governed access request). Job Management: run_mapping_task, get_job_status, stop_running_job (CDI jobs only, not CAI instances). In September these appear as the contexts dqverifyaddress, cdgcsearchmetadata, searchcustomer, dataprovisioning and jobmanagement among 19 servers.

### L-MCP-005  Three different things get called 'IDMC MCP servers': ask which class and which release
**Kind:** LAW · **Documented:** 2026-07-26 · **Evidence:** Vendor guide; a reference fleet document (2026-07-16); a September registry count
(1) Informatica-managed servers (5 in the April 2026 guide; 19 in one September 2026 registry); (2) CLAIRE/AI-agent servers reached on the CLAIRE API host (`<claire_api_url>/claire-orchestrator-ai-agent/api/v1/mcp`), which appear as tools in the host app, not in the org registry; (3) custom fleets built over the same REST APIs (one reference fleet: 9 servers, about 110 tools). When someone quotes a number, ask which class, which release and when it was enumerated.

### L-MCP-006  MCP is a calling convention, not a network position
**Kind:** LAW · **Documented:** 2026-07-26 · **Evidence:** Vendor MCP guide (April 2026); consistent with every probe since
An MCP server cannot reach a private database that only a Secure Agent can reach, so MCP never replaces the Secure Agent, and editing an MCP proxy's code cannot bypass a server-side check. MCP sits on the same service APIs, so its read/write boundary matches REST's. Judge a server by its action list, not by the word 'MCP'.

### L-MCP-007  HTTP verbs do not apply to MCP, and REST is usually richer
**Kind:** LAW · **Documented:** 2026-07-25 · **Evidence:** Action-by-action comparison
Every MCP call is an HTTP POST of a JSON-RPC body to one server endpoint naming an action; read/write intent lives in the action name, so REST verb matrices do not apply. About 7 of the April 2026 release's 11 actions were thin REST wrappers, and REST was richer (Elasticsearch DSL versus one natural-language string, 1,000 addresses per call versus 1, full activity history versus one job). In July, MCP added two things REST lacked: lineage via get_asset_details and fuzzy identity match via search_master_record. With the 19-server registry and the file-based DQ agent, 'only two' is probably outdated.

### L-MCP-008  Managed MCP servers speak protocol 2025-06-18 over streamable HTTP and bill as their backing services
**Kind:** LAW · **Documented:** 2026-07-25 · **Evidence:** Vendor guide (April 2026)
Informatica-managed MCP servers use MCP protocol version 2025-06-18 over streamable HTTP (not stdio); your AI app is the host and each agent a client, with one connection per server; Informatica calls tools 'actions'. Calls are billed as the underlying service API's IPUs. OAuth uses client credentials with a 5-minute default token lifetime (5 to 1440 minutes).

### L-MCP-010  The CLAIRE agent MCP server is read-only: it cannot provision agents, connections or assets
**Kind:** GOTCHA · **Observed:** 2026-08-18 · **Evidence:** Read-only responses only
The CLAIRE orchestrator MCP server can read org metadata but could not register agents, create connections or author assets. Do not plan provisioning through it; use REST or the managed operations servers (connectionmanagement, secureagentmanagement, diassetpromotion) instead.

### L-MCP-012  AI Agent Engineering 'Fetch Actions' for an MCP tool can fail with 401 from IDMC itself
**Kind:** WALL · **Rejected:** 2026-09-24 · **Evidence:** 401 with an empty server access log
In AI Agent Engineering, New Tool > MCP Tool > Token Authentication (prefix 'Authorization:Bearer ') > Fetch Actions made POST a2e-flow-mgmt-svc/api/v1/mcp/fetch-actions return 401 from IDMC; the request never reached the MCP server (its access log stayed empty) and Save was a no-op, although the user held Admin plus Designer. That is most likely an entitlement or licence limit of that org. In a new org, test a trivial MCP tool connection before building an agent (a reusable template is the Agent Hub 'Business Insights AI Agent using CDGC Metadata Discovery'; swap its execute tools for MCP tools).

### L-MCP-014  Prototype an agent deterministically over MCP tools when the agent engine is not licensed
**Kind:** WORKAROUND · **Proven:** 2026-07-04 · **Evidence:** Deterministic planner working with no LLM credits
Without the licensed agent engine, build a deterministic agent: a rule-based planner (understand, retrieve via MCP tools, rank and explain, consent-gated handoff) with no LLM calls, composed from live read-only skills over golden records and catalog metadata. It costs no credits and keeps the same tool contract, so moving to the licensed engine later is the only delta.

### L-MCP-015  A self-hosted MCP server over governed data: read-only tools and a hard denylist
**Kind:** SECURITY · **Proven:** 2026-07-08 · **Evidence:** An early build failed on sensitive columns and on a missing CLI; fixed with a server-side denylist and a snapshot fallback
Expose read-only tools over published rows only, enforce a hard field denylist (encrypted fields, API keys, e-mail, phone) inside the server, expose no write tools, read live first with a snapshot fallback, and stamp every answer with its source. Tools that shell out to a CLI break on hosts where that CLI is not installed.

### L-MCP-016  Expose databases to an AI agent through MCP Toolbox for Databases with read-only identities
**Kind:** RECIPE · **Proven:** 2026-09-24 · **Evidence:** Reads work; DELETE and CREATE rejected
Run MCP Toolbox for Databases as your own MCP server with tools such as `<x>_pg_list_tables`, `<x>_pg_execute_sql`, `<x>_bq_list_dataset_ids`, `<x>_bq_list_table_ids`, `<x>_bq_get_table_info` and `<x>_bq_execute_sql`. Give it read-only identities (a Postgres role with default_transaction_read_only and a 30 s statement timeout; a GCP service account with bigquery.dataViewer and bigquery.jobUser) and verify that DELETE and CREATE are rejected. Toolbox runs as uid 65532 (chown its config and key files); its /api endpoints are disabled, so clients use JSON-RPC on /mcp (tools/list, tools/call); put it behind TLS with bearer or Basic auth.

### L-MCP-017  Wrap a REST flow such as Data Marketplace ordering as a small stdio MCP server

A local stdio MCP shim can expose list_data_collections, list_delivery_targets and checkout_data_order over the public Marketplace API with self-refreshing session auth, registered in Claude Code at user scope, so an agent can place governed data orders conversationally.

### L-MCP-018  MCP OAuth clients can be created headless through a2e-mcp-asset-mgmt-svc oauth2clients
**Kind:** OVERTURNED · **Proven:** 2026-09-28 · **Evidence:** 201; a gateway then got a 24 h token and listed 83 Informatica tools; verify_address answered Status Ok · **Supersedes:** L-MCP-072
POST `https://hdm.<domain>.informaticacloud.com/a2e-mcp-asset-mgmt-svc/api/v1/oauth2clients` with IDS-SESSION-ID: `<v3_session>` and body {providerType 'IDMC_MCP', clientName, description, credentials {username, password}, accessTimeout `<minutes>`, enabled true, mcpServers [{id, name, serverEndpointUrl, context, serverPolicy null}, ...]} returns 201 with clientId and clientSecret. Other shapes did not create a client (mcpServersDetails, mcpServerIds, servers, resources). List with GET ...?type=IDMC_MCP&page=1&size=50&sortBy=lastModifiedDate&sortOrder=desc&grantType=client_credentials (content[]); delete with DELETE `.../oauth2clients/<clientId>`. The route was found by recording the UI's own requests while a client was created.

### L-MCP-019  An MCP OAuth client secret is shown once: write it straight to a 0600 file, recreate the client if it leaks
**Kind:** SECURITY · **Proven:** 2026-09-28 · **Evidence:** A secret prefix reached a local log once; the client was deleted and recreated
The create call (like the UI wizard) returns the client secret once. Write it with os.open(path, O_CREAT|O_TRUNC, 0o600) into an env file holding IDMC_CLIENT_ID, IDMC_CLIENT_SECRET, `IDMC_TOKEN_URL=https://<domain>.informaticacloud.com/authz-service/oauth/token` and `MCP_BASE=https://mcp.<domain>.informaticacloud.com/mcp-servers/public/` without printing any of it, and mask the password in echoed errors. If even a prefix of the secret reaches a log, delete the client and recreate it; disabling a client stops token issuance without deleting it.

### L-MCP-020  MCP OAuth token lifetime is set in minutes: raise it for daemons
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** A gateway logged 'token refreshed' with 86,400 s; vendor guide pp.17-18
The access-token timeout defaults to 5 minutes in the UI, with a range of 5 to 1440 minutes; accessTimeout 1440 in the create body gave tokens with expires_in 86,400 s (24 h). Five minutes is too short for a background job or a gateway, so raise it deliberately, and scope each client to the servers its consumer needs. (One note recorded accessTimeout in seconds; the unit is minutes.)

### L-MCP-021  An MCP OAuth client stores its creator's password: recreate it when that password rotates
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** Cutover rotation checklist
The client is created with the user's username and password in its credentials, so a password change breaks it. Recreate the client and copy the new secret to every consumer (gateways, cron jobs, scripts), and keep the consumer list next to the client name.

### L-MCP-022  The MCP OAuth client lifecycle in the UI
**Kind:** PROCESS · **Documented:** 2026-07-26 · **Evidence:** Vendor guide (April 2026) pp.17-18
Configuration > MCP Server Authorization > Add OAuth Client: Authentication (IDMC username and password), Details (name, description, token timeout), Resources (which MCP servers), then Generate Credentials, which shows the client ID, the secret and the auth header value (base64 of id:secret) once. Regenerate Secret re-authenticates first; Disable stops token issuance without deleting (the right response to a compromise); Edit changes the name, description, timeout or server scope; Download CSV lists every client with status, servers and last update, ignoring on-screen filters.

### L-MCP-023  Three ways to authenticate to managed MCP servers, and the privileges they need
**Kind:** ROUTE · **Documented:** 2026-07-26 · **Evidence:** Vendor guide pp.12-20; the token URL was used by a working gateway on 2026-09-28
Session ID: IDS-SESSION-ID: `<sessionId>`. JWT: Authorization: Bearer `<jwt>`, minted like the data360 token (30 minutes). OAuth 2.0 client credentials: Authorization: Bearer `<token>` from `https://<domain>.informaticacloud.com/authz-service/oauth/token`, recommended for production because the agent never holds a user's IDMC credentials; a federated variant uses an IdP-issued JWT and needs the org on SAML with SAML users and the IdP's authorization server registered through the Administrator REST 'Identity providers' resource. The feature privileges Execute Managed MCP Servers and View Managed MCP Servers, and the asset privileges MCP Server and Deployed MCP Server (for composite servers), are held by Admin and Designer by default; Operator can run but not create composite servers.

### L-MCP-024  Mint the identity JWT from a login session and cache both tiers
**Kind:** RECIPE · **Proven:** 2026-09-21 · **Evidence:** JWT minted and MCP calls returned 200 (2026-09-21); two-tier refresh in working shims
Get a session from POST `https://<domain>.informaticacloud.com/saas/public/core/v3/login` (userInfo.sessionId) or POST .../identity-service/api/v1/Login (read userInfo.sessionId, sessionId or session_id), then GET `https://<domain>.informaticacloud.com/identity-service/api/v1/jwt/Token?client_id=idmc_api&nonce=<fresh_uuid>` with IDS-SESSION-ID: `<sessionId>` to get jwt_token (about 2,100 characters); the documented form is a POST that also sends Cookie: `USER_SESSION=<sessionId>`. client_id=idmc_api worked for the managed MCP servers, cdlg_app for the CDGC API. The JWT lasts 30 minutes from grant and the identity session about 8 hours: cache both and re-mint the JWT from the session before expiry.

### L-MCP-025  Each MCP server holds its own session; IDS_085 with 400 means a valid credential on the wrong pod
**Kind:** GOTCHA · **Proven:** 2026-07-26 · **Evidence:** Independent 401s per server; IDS_085 resolved by using the correct login host
A 401 on one MCP server says nothing about the others, because each server (and each server in a custom fleet) logs in independently. IDS_085 'User name or password is not valid' with HTTP 400 usually means the right credential sent to the wrong domain or pod, not a bad password: check the host before resetting anything.

### L-MCP-026  MCP looks free during preview, but the backing services bill IPUs
**Kind:** GOTCHA · **Documented:** 2026-07-26 · **Evidence:** Vendor guide p.7
MCP usage is not separately metered during the AI Agent Engineering preview, but every backing CDGC, CDI, Marketplace or MDM call bills IPUs at the normal service rate card. An agent looping on an orchestration prompt can generate real consumption while the MCP line reads zero: budget the underlying service, not the MCP layer.

### L-MCP-027  Using MCP may require switching the org's REST authentication to JWT (vendor statement, unverified)
**Kind:** GOTCHA · **Status:** disputed · **Observed:** 2026-09-02 · **Evidence:** Vendor statement and an enablement plan; untested
Informatica staff stated that MCP needs the org's REST authentication type switched from Session ID to JWT (Administrator > Settings > General settings > Authentication type), which breaks every client that authenticates with INFA-SESSION-ID or icSessionId until it moves to Bearer JWT. The vendor guide says session ID or JWT works depending on the org's configuration, and later calls succeeded with Bearer JWT plus IDS-SESSION-ID and with OAuth tokens; whether that org's toggle had been flipped is not recorded. Check the setting before changing it, and never flip it under a live workload.

### L-MCP-028  Call an MCP server over streamable HTTP: initialize, initialized, then tools
**Kind:** RECIPE · **Proven:** 2026-09-28 · **Evidence:** tools/list returned 89 tools through a gateway
POST the endpoint with JSON-RPC {`"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"<client>","version":"1"`}}} and Accept: application/json, text/event-stream; keep the Mcp-Session-Id response header and send it on every later call; post {"jsonrpc":"2.0","method":"notifications/initialized"}, then tools/list and tools/call. Answers may be SSE: parse the 'data:' lines.

### L-MCP-029  Read each server's endpoint from the registry instead of building it
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** Registry reads (2026-09-28); vendor and July examples
Two managed-server host patterns were recorded: `https://a2e-prod-<pod>-mcp.<domain>.informaticacloud.com/mcp-servers/public/`... in July-era examples, and `https://mcp.<domain>.informaticacloud.com/mcp-servers/public/<context>` as serverEndpointUrl in the September registry. Take serverEndpointUrl from the registry (or from the server's Configuration tab code block) rather than constructing it.

### L-MCP-030  Informatica agent tools return a JSON-RPC envelope inside the text content
**Kind:** GOTCHA · **Proven:** 2026-09-27 · **Evidence:** Unwrap and fallback logic in a working client
An agent tool's result.content[].text can itself be a JSON-RPC message whose result.content[].text is another one: unwrap up to three levels (or read result.structuredContent) before parsing. If a tool rejects a JSON-RPC-shaped (nested) argument with a validation error, retry with the plain argument object.

### L-MCP-031  A local MCP gateway holds the OAuth client and proxies the managed servers
**Kind:** PROCESS · **Proven:** 2026-09-28 · **Evidence:** An org switch through the gateway: 83 Informatica tools; verify_address answered Status Ok
Run one small gateway container that holds the org's OAuth client credentials (a 0600 env file), refreshes the token and exposes the managed servers' tools through one local streamable-HTTP endpoint with server-prefixed names (for example address_verify_address). Scripts and cron jobs then need no IDMC credentials. Moving to another org means recreating the client there, swapping the env file and the MCP base URL, rebuilding with a new image tag, and keeping the previous tag for rollback.

### L-MCP-032  A local MCP shim failing with KeyError 'userInfo' is a failed login, not an MCP fault
**Kind:** GOTCHA · **Proven:** 2026-09-21 · **Evidence:** The error disappeared after the shim was re-pointed by environment override
A shim that logs in and reads response['userInfo'] without checking the status throws KeyError 'userInfo' whenever the login fails (wrong host, wrong org, stale password). Override the login URL, JWT URL, MCP URL and credentials through environment variables instead of hard-coding them, surface the login error code (IDS_085 for the wrong domain or pod, IDS_086 for a locked account), and stop after one rejected attempt.

### L-MCP-033  A CLAIRE orchestrator MCP that lists zero tools may be a mis-pointed local config
**Kind:** OVERTURNED · **Proven:** 2026-09-28 · **Evidence:** 0 tools listed; config inspection; orchestrate listed live in the managed registry · **Supersedes:** L-MCP-073
The CLAIRE agent MCP endpoint (claire-orchestrator-ai-agent) listed 0 tools, or only new_conversation and working, for an org, and the local MCP config turned out to point at a different org than the one under test. ### L-MCP-034  CLAIRE agent MCP: the four-step call sequence
**Kind:** PROCESS · **Proven:** 2026-07-26 · **Evidence:** Live tool schemas read from a connected CLAIRE MCP server
(1) new_conversation (no arguments) as the very first action of every chat session, before any skill call, and not again mid-conversation unless deliberately resetting. (2) OrchestratorSkill, or MdmOrchestratorSkill for mastered entities, golden records, hierarchies and match/merge, with one natural-language prompt (the only required argument); it returns immediately because it is a submission. (3) working with no arguments, polled at about 1-second intervals; it is cursor-based and returns only what queued since the last call, so never skip calls. (4) Stop on a sentinel.

### L-MCP-035  CLAIRE poll sentinels and what to do with each
**Kind:** PROCESS · **Proven:** 2026-07-26 · **Evidence:** Live tool schemas
ANSWER: is the final JSON with responseType=FINAL_BUNDLE carrying artifact, plan and human_probe: render it and stop. PROBE: means CLAIRE needs clarification (usually a vague prompt): ask the human and stop. done means finished: stop. Error: `<msg>` means report it and stop; do not retry blindly. 'Still working...' means poll again silently. Any other text is live progress: show it verbatim and keep polling.

### L-MCP-036  CLAIRE argument rules that silently lose context
**Kind:** GOTCHA · **Proven:** 2026-07-26 · **Evidence:** Live tool schemas; testing confirmed the context loss
Omit conversation_id on the first call and never invent one: the server mints it at response.context.conversation_id. Pass that exact value on every follow-up, because omitting it silently starts a new session and drops all prior context. Use conversation_id or history (a list of {role, content}), never both. artifacts may contain only names CLAIRE already returned. Vague prompts come back as a HUMAN_PROBE; reasoning=true exposes why (REASONING_TRACE items) and events=true exposes what ran (EXECUTION_INSIGHT items).

### L-MCP-037  The CLAIRE working action takes no arguments
**Kind:** OVERTURNED · **Proven:** 2026-07-26 · **Evidence:** Inspection of the working schema (properties={}) · **Supersedes:** L-MCP-074
The live schema of working is properties={}: it is cursor-based server-side polling and must be called without conversation_id. This corrects a published skill signature and an earlier catalog row that passed it.

### L-MCP-038  working is a temporary polling shim: isolate polling, and expect loop bugs
**Kind:** GOTCHA · **Proven:** 2026-07-26 · **Evidence:** Server self-description in the live tool schema
The server documents working as a local polling shim that will be removed once native progress streaming ships, so put polling behind one function and the swap becomes a single edit. Most integration bugs are loop bugs, not auth bugs: a self-generated conversation id, dropping it on the second call, passing arguments to working, surfacing 'Still working...', or stopping before a sentinel.

### L-MCP-039  Claude Desktop keeps MCP servers alive across chats
**Kind:** GOTCHA · **Proven:** 2026-07-26 · **Evidence:** Live behaviour
New Chat in Claude Desktop does not reset CLAIRE's server-side context, because the MCP server keeps running across chats; that is why new_conversation must be the first action of every chat. Skipping it leaks context between conversations.

### L-MCP-040  Render the CLAIRE ANSWER bundle by viewType
**Kind:** RECIPE · **Proven:** 2026-07-26 · **Evidence:** Contracts verified against live responses
GridView: headers from schema_definitions[].label in order, rows mapped by fieldName position, key_insights as a callout below. DataExploreResult (or null): the same grid with null cells as an em dash, execution_context.generated_sql in a sql code fence, then 'Rows: `<row_count_total>` | Execution time: `<execution_time_ms>ms`'. ### L-MCP-041  Wire a local CLAIRE agent MCP server into Claude
**Kind:** RECIPE · **Proven:** 2026-07-26 · **Evidence:** Shim working in sessions; live schemas
The endpoint is a path on the CLAIRE API host: `<claire_api_url>/claire-orchestrator-ai-agent/api/v1/mcp`. The config keys claire_api_url, identity_url, username, password and client_id come from config or environment, never inline or in chat. ### L-MCP-042  Keep Informatica's claire-idmc-agent skill as the transport
**Kind:** PROCESS · **Documented:** 2026-07-26 · **Evidence:** Shipped skill reviewed
Informatica publishes a claire-idmc-agent skill (SKILL.md, a Python MCP shim and a setup script) that operates the CLAIRE agent server: skill selection, the poll loop and the seven viewType rendering contracts. ### L-MCP-043  CLAIRE only sees what is cataloged
**Kind:** GOTCHA · **Observed:** 2026-08-19 · **Evidence:** Empty CLAIRE answers for uncataloged connections
The CLAIRE agent (through MCP or CLAIRE GPT) answers from the CDGC catalog and the MDM repository; runtime connections and tables that were never scanned into CDGC return nothing. Catalog the source first.

### L-MCP-044  Managed agent servers use submit-then-poll with get_skill_execution_updates
**Kind:** PROCESS · **Proven:** 2026-09-27 · **Evidence:** A full frame transcript of a rule-recommendation run with its probe answered (2026-09-27); a shim polling loop (2026-09-21)

### L-MCP-083  FastMCP 2.14 mounted proxies list every upstream on every tools/call: cache each proxy's tool inventory
**Kind:** PERF · **Proven:** 2026-09-30 · **Evidence:** measured on a side-by-side test container: ~26 s per call before, 0.3 s (local tool) and ~3 s (vendor tool) after; tools/list 0.6 s after one fill (2026-09-30)
