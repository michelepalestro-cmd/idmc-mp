## Current

### L-DQ-001  Data Quality authors and measures; a CDI mapping on a Secure Agent executes
**Kind:** LAW · **Documented:** 2026-08-13 · **Evidence:** Page-cited vendor docs (CDQ Introduction April 2026 pp.6-7; IICS Getting Started pp.6-7); used as a locked planning decision on 2026-09-17
IDMC Data Quality is licensed and metered separately but has no production run engine or mapping designer of its own. To cleanse, parse, match/deduplicate or verify addresses on real data, add the DQ assets to the matching transformations in a Data Integration mapping that runs on a Secure Agent (CDQ April 2026 Introduction pp.6-7: design and run the mappings in Data Integration). DQ alone can author assets, test them on sample rows at design time, profile and score, and schedule a single profiling task; it lacks taskflow orchestration and writes no cleansed data to a target (only exception/reject rows). Advanced DQ (match, address, parse) is not pushdown-eligible and runs on the agent; MDM SaaS has its own cleanse/match/merge. Plan and size DQ with a CDI mapping around it.

### L-DQ-002  Say precisely what Data Quality can do without CDI
**Kind:** GOTCHA · **Documented:** 2026-08-14 · **Evidence:** Find-and-verify pass over 15 claims
DQ asset editors test rules on sample rows at design time, so say that DQ alone cannot run on production data, not that it has no engine. DQ alone can schedule one profiling or DQ task but has no taskflow orchestration; profiling is standalone, while viewing the scorecard dashboard needs CDGC and a governance role; DQ alone extracts exception/reject rows (Exception Management) but writes no cleansed data to a target; CDGC lineage is CLAIRE-generated with confidence thresholds or added manually, not purely automatic.

### L-DQ-003  The DQ runtime lives inside the Data Integration Server on the agent
**Kind:** GOTCHA · **Proven:** 2026-06-27 · **Evidence:** DQ libraries found under the DIS ICS/main/DQ directory after enabling DQ
Enabling Data Quality on a Secure Agent adds no separate DQ service directory: the DQ runtime is part of the Data Integration Server (the DIS version bumps when DQ is enabled), with the DQ libraries under `<DIS>/.../ICS/main/DQ`. Troubleshoot DQ transformation runs through the DIS logs.

### L-DQ-004  A CDI task that runs SQL imitating DQ is not IDMC Data Quality
**Kind:** LAW · **Proven:** 2026-08-19 · **Evidence:** Mapping SQL inspection: comments described the SQL as an analog of CDQ cleanse and match/merge
If a mapping task only pushes down SQL written to mimic cleansing or match/merge, IDMC ran a job but the DQ logic is still SQL. Genuine IDMC DQ means the logic lives in DQ assets and transformations (Cleanse, Standardizer, Parser, Match/Merge or Deduplicate, Rule Specification, Profiling) executed by the engine. Read the mapping or its customQuery before claiming that DQ runs in IDMC, and label every status by evidence layer (IDMC-native versus SQL equivalent).

### L-DQ-005  The six Data Quality capabilities a complete demonstration covers
**Kind:** PROCESS · **Reported:** 2026-08-19 · **Evidence:** A demonstration mandate and its build plan
(1) Profiling (completeness, conformity, consistency, accuracy, duplication); (2) standardization and cleansing (address, phone, formats); (3) deduplication (identify and merge); (4) parsing and enrichment (parse free text; enrich, for example ZIP to geography from reference data); (5) rule-based DQ applied continuously in transit; (6) AI-pipeline readiness (remediate before vectorization, embed only valid records). With only entitled features, use a reference-data lookup for geo enrichment instead of a licensed address verification service.

### L-DQ-006  CDQ dictionaries have a write-only REST API on the dedicated `<pod>-dqcloud-api` host
**Kind:** ROUTE · **Proven:** 2026-07-25 · **Evidence:** 201 on create, live on a dm-us pod; the rest per the CDQ API Reference (April 2026) · **Supersedes:** L-DQ-084
POST `https://<pod>-dqcloud-api.<domain>.informaticacloud.com/quality/public/v2/dictionaries/` with Content-Type: application/json and Authorization: Bearer `<jwt>` (or IDS-SESSION-ID) and body {name (max 125 chars), description, columns[] (max 42, unique, max 64 chars each), path (project folder)} returns 201 with the dictionary id. Documented: DELETE `.../dictionaries/<id>` (204); `.../dictionaries/<id>/rows` with POST to add, PUT to replace and DELETE to clear, body {cols[], rows[[...]]}, at most 10,000 rows per call (413 above); POST `.../dictionaries/<id>/finishUpload` is mandatory to commit pending row operations (424 if skipped); 409 on state conflicts. There is no GET or PATCH anywhere, so keep the id from the create response or take it from the UI URL. The API host is the DQ app host with -api appended (`<pod>-dqcloud` becomes `<pod>-dqcloud-api`).

### L-DQ-007  A dictionary accepts UI edits or API edits, never both: Convert to API first
**Kind:** GOTCHA · **Documented:** 2026-07-25 · **Evidence:** Vendor CDQ Dictionaries guide and API Reference (April 2026); UI receipt not captured
A dictionary has one editing environment at a time. For a dictionary authored in the UI, someone must click Convert to API (Definition or Configuration tab) before REST can write it; Convert to UI switches it back, and the create response's customAttributes carry a MODE attribute naming the environment that may update or delete it. A dictionary created through the API presumably starts in API mode, since the documented flow creates it and adds rows over REST. Dictionaries sourced from Reference 360 are editable only in Reference 360. No receipt of the Convert click has been captured.

### L-DQ-010  Rule specifications can be authored headless by cloning a template through v3 export/import
**Kind:** OVERTURNED · **Proven:** 2026-07-09 · **Evidence:** Export 200, edit and re-hash, import/package 200 checksumValid=true, import SUCCESSFUL; RULE_SPECIFICATION count went 4 to 11 to 12 · **Supersedes:** L-DQ-083
Direct create fails (POST /public/core/v3/objects returns 405 Method not supported; every /data360/dq/* rule path returns 404), but a same-type template can be cloned: POST /saas/public/core/v3/export {`"objects":[{"id":"<frsGuid>"`}]} and download the package; give the object a new GUID and name; recompute the SHA-256 of every edited file; POST /saas/public/core/v3/import/package as multipart/form-data (200 checksumValid=true); POST `/saas/public/core/v3/import/<id>` to start and poll it to SUCCESSFUL; then confirm with the v3 objects census on RULE_SPECIFICATION. The clone inherits the template's expression logic, so making each rule implement its own check still needs the rulebuilder canvas.

### L-DQ-011  Moving rule specifications between orgs: package them and check their dependencies
**Kind:** PROCESS · **Proven:** 2026-09-23 · **Evidence:** Rule-spec and bundle-rule exports SUCCESSFUL (2026-09-23); rules invisible in the target until migrated (2026-09-12); re-bound after import (2026-09-28)
Rule specs travel as RULE_SPECIFICATION objects in a v3 export/import package, imported with REUSE on name conflicts. Rule specs from Informatica bundles must exist in the target (or be imported with REUSE) before profiles that bind them can be re-bound. Exporting a bundle rule spec succeeded in an org where exporting an Add-On Bundle mapping template had been refused with 403 MigrationSvc_038 in another org, so test bundle-object export per org.

### L-DQ-015  Address verification: batch REST at 1,000 addresses per call versus one per MCP call
**Kind:** ROUTE · **Documented:** 2026-07-25 · **Evidence:** Vendor Cloud Address Verification guide (July 2025)

### L-DQ-016  Verify addresses from a pipeline through the managed MCP server dqverifyaddress: pre-merge input, real test addresses, a hash cache and a first-check timestamp
**Kind:** RECIPE · **Proven:** 2026-10-01 · **Evidence:** 583 calls and 0 errors on the first run; invented addresses 344 STREET_NOT_FOUND and 203 HOUSE_NUMBER_NOT_FOUND, a real-address seed 25/25 VERIFIED and 9/10 variants VERIFIED_CORRECTED, 51 re-checks with 0 calls, 735 first-check times restored by time travel, and after the switch to the pre-merge layer 43 new records verified with 37 calls and 0 errors (2026-10-01)
The Cloud Address Verification service is exposed as the managed MCP server with context dqverifyaddress and tool verify_address (Interactive mode). Call it from a small pipeline for new records only, cap the calls per run and per day, and store the result code per record in a warehouse table (codes seen: VERIFIED, VERIFIED_CORRECTED, LOW_CONFIDENCE_MATCH, STREET_NOT_FOUND, HOUSE_NUMBER_NOT_FOUND, NO_ADDRESS). E-mail and phone verification and geocoding need their own servers and licences; without them, use CDQ format flags. (1) Feed it from the per-record pre-merge layer, not the de-duplicated golden view: an enrichment job that read the golden view never verified the addresses of records that match-and-merge had folded into a survivor (44 skipped); MERGE (upsert) the results. (2) Test data needs real addresses: invented streets are correctly answered STREET_NOT_FOUND or HOUSE_NUMBER_NOT_FOUND (547 of about 600 synthetic records), so the verified rate stays low however often you re-check; draw from a small pool of real public addresses (civic buildings, libraries, arenas; never private homes) and derive messy variants (lower case, missing suffix or direction, spelled-out suffix, wrong ZIP): 25 of 25 returned VERIFIED and 9 of 10 variants VERIFIED_CORRECTED. A mix of about 72% clean, 24% messy and 5% invented keeps both the correction and the exception story; check shared pool addresses for collisions on the person match key before assigning them (L-MDM-072). Enrichment that deliberately skips test identities must still be proven on a real record. (3) Cost: cache results by a normalized-address hash (results were reusable for 30 days, so re-checks cost 0 calls) and key the work queue on that hash (L-DQ-018). (4) Timestamps: if re-checks MERGE into the results table, keep a first-verified timestamp that is set once (`first_checked_at = COALESCE(target.first_checked_at, target.checked_at)` on update) and count a latency sample only when the first check lands within a few minutes of the record's creation; overwriting the only timestamp turned a 33 s 'record to verified' metric into 26-54 hours. Lost first-check times can be recovered with time travel within about 7 days (L-CDI-161). (5) Swap the job's code under the same `flock` the job takes, after checking the live files' checksums, with a backup and an undo script. Measured with a 20 s polling job: source insert to first check about 33-34 s average (24-44 s, fastest 27 s), a few minutes more until visible in BI. Newer evidence: L-DQ-160.

### L-DQ-017  MCP address-verification calls are not IDMC jobs
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** Absent from the activity log while running every minute
Calls to the dqverifyaddress MCP tool do not appear in the IDMC activity log and do not count against the org's monthly job limit. Describe such enrichment accordingly, and budget IPUs for the backing service.

### L-DQ-018  A verification queue that picks only 'not yet enriched' rows never re-verifies a changed address
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** Gap found in an end-to-end proof
A downstream verification job that selects only records missing from its results table will not re-check a record whose address was added or changed later (for example a record first captured with NO_ADDRESS). Key the work queue on a hash of the address fields, or on the last-modified time.

### L-DQ-019  Data Profiling profiles can be created, updated, executed and polled over REST
**Kind:** OVERTURNED · **Proven:** 2026-10-03 · **Evidence:** 8 profiles executed to COMPLETED 'No errors encountered' in one org (2026-09-24) and 8/8 in another (2026-09-28); reads returned 200 on two pods (2026-07-25); runDetail/<id>/1 read back COMPLETED (33,277 rows, 39 columns), the /filter form 400 PROFILE_SVC_00093, a killed 181-column run left lastRunKey null (2026-10-03) · **Supersedes:** L-DQ-085, L-DQ-087
Base `https://<pod>-dqprofile.<domain>.informaticacloud.com/profiling-service/api/v1`, header IDS-SESSION-ID (a v3 session on some pods). List with GET /profile?limit=200; read with GET `/profile/<id>`; create with POST /profile using a body cloned from a known-good profile on the same connection type; update with PUT `/profile/<id>`; run with POST `/profile/<id>/execute` {} which returns 200 {profileJobId}; poll GET `/job/<profileJobId>` until the status leaves RUNNING, QUEUED, SUBMITTED or STARTING (COMPLETED means done; errorMessage on failure). Reads on the same host: run history one run at a time with `GET /runDetail/<profileId>/<runKey>` (runKey 1 to the profile's `lastRunKey`; each record carries `startTime` in epoch ms, `status`, `rowsProcessed`, `numberOfColumns` and `numberOfRules`), because the `/runDetail/<id>/filter` form answered 400 `PROFILE_SVC_00093` 'Invalid request - Provided argument does not match the expected type' to both POST and GET on one pod; `/ruleOccurrence/...ForProfile_V2_Token/<uuid>` (bindings), /ruleOccurrence/ruleType (the six dimensions) and `/metric-store/api/v1/odata/Profiles('<uuid>')/Columns`, /Insights, /Patterns, /ValueFrequencies. Profiling query CRUD is vendor-documented in a separate guide whose paths are not held. A run that dies with the agent (engines killed mid-run) can leave `lastRunKey: null`, so 'never run' does not prove that no profiling DTM ran; the agent names its profiling DTM sessions `s_profiling_<profileKey>_<run>_<n>`, which maps a running or crashed `pmdtm` process back to its profile.

### L-DQ-020  The `<pod>-dqprofile` service may need the v3 login session
**Kind:** OVERTURNED · **Proven:** 2026-09-28 · **Evidence:** 401 with the v2 session; 8/8 profile jobs COMPLETED after switching to the v3 session · **Supersedes:** L-DQ-086
On one dm-us pod the profiling service answered 401 'Exception encountered while processing JWT' to the v2 icSessionId sent in IDS-SESSION-ID, while the v3 login sessionId (POST `https://<domain>.informaticacloud.com/saas/public/core/v3/login`, field userInfo.sessionId) in the same header worked; another org accepted the v2 id. ### L-DQ-021  POST /profile with client-side ids fails with 500 'Row was updated or deleted'
**Kind:** GOTCHA · **Proven:** 2026-09-24 · **Evidence:** 500 with ids; success without them
When creating or updating a profile through the Data Profiling REST API, omit every id field (profile, source, runtimeOptions, rule blocks, profileable fields). Supplying client-side ids returns HTTP 500 'Row was updated or deleted'.

### L-DQ-022  PROFILE_MDL_00006: int4 and char(n) columns are rejected as profileable fields
**Kind:** ERROR · **Proven:** 2026-09-27 · **Evidence:** PROFILE_MDL_00006 on int4 and char(n) columns (2026-09-24); the builder's type map (2026-09-27)
Binding a profileable field or a rule occurrence to a Postgres int4 or character(n) column returns PROFILE_MDL_00006: skip those columns or profile a view that casts them. When building fields from information_schema, map text, varchar and uuid to NSTRING, numeric to DECIMAL (with precision and scale) and timestamps to TOOLKIT_DATETIME (timestamp or timestamp_with_time_zone); the builder skipped jsonb and array columns (whether the service accepts them is untested).

### L-DQ-023  Rule occurrences are bound inside the profile body: one rule block per rule spec, one MAPPLETFIELD per column
**Kind:** GOTCHA · **Proven:** 2026-09-24 · **Evidence:** Profiles updated with 3-4 rule occurrences each and executed to COMPLETED · **Supersedes:** L-DQ-088
To bind a rule specification to columns, add it once to source.rules[] ({name, description, frsId, inFields[], outFields[], ruleType 'RULE_SPECIFICATION'}) and add one profileableFields[] entry per bound column with fieldType 'MAPPLETFIELD', the rule's frsId, scoreCardId null, a fresh assignmentIdentifier, inputFieldMappings [{dataSourceFieldName `<column>`, inFieldName `<rule_input>`}] and outputFieldMappings [{columnKey 40000+n, outFieldName `<rule_output>`, datatype 'string'}]; data columns are DATASOURCEFIELD entries with columnKey 10001+i. To change the rules, GET the profile, reset source.rules and keep only the DATASOURCEFIELD entries, append the new blocks, PUT it back, and run the profile again.

### L-DQ-036  Profiling exits 127 on Debian 12 because pmdtm needs libidn.so.11: symlink it to libidn.so.12
**Kind:** ERROR · **Proven:** 2026-06-28 · **Evidence:** 1,965 libidn misses equalled 1,965 exit-127s before the fix and 0 after; profiled columns went from 0 to 671 within an hour
pmdtm (under ICS/main/bin/rdtm/) links libpmcurl.so, which needs libidn.so.11; Debian 12 (and RHEL/Rocky 8/9) ship only libidn.so.12, so every profile dies at launch with 'error while loading shared libraries: libidn.so.11' (exit 127) while metadata extraction still works. libidn 1.x is ABI-compatible: fix it durably with a system symlink in /usr/lib/x86_64-linux-gnu, a copy in a compat directory registered in /etc/ld.so.conf.d plus ldconfig, and the compat directory on LD_LIBRARY_PATH in agent_start.sh, then restart the agent; verify with env -u LD_LIBRARY_PATH ldd pmdtm. The same fix cleared a DTM exit 134.

### L-DQ-037  Zero profiled columns: read the pmdtm exit code before chasing jobs, readyToRun or auth
**Kind:** OVERTURNED · **Proven:** 2026-06-28 · **Evidence:** The exit-127 count matched the libidn misses; the fix restored profiling · **Supersedes:** L-DQ-091
When scans complete and metadata is present but no column is profiled, check how pmdtm died on the agent host: 127 means a native library failed to load, 134 SIGABRT, 137 an OOM kill. Every source failing identically is the tell. Stuck-job 406 locks, readyToRun=false and ccgf-auth-pep 500s did not explain it; the missing library did.

### L-DQ-038  Only Data Profiling uses the native pmdtm engine
**Kind:** LAW · **Proven:** 2026-06-28 · **Evidence:** The other capabilities COMPLETED while profiling failed
In a CDGC catalog scan, Metadata Extraction, Lineage, Data Quality and Classification run in the Java scanner, the DQ engine and cloud services, while Data Profiling launches pmdtm on the agent; Data Observability depends on profiling and is skipped when profiling fails. A scan where only profiling fails points at the agent's DTM, not at the source database.

Check query_log for code 241 before you tune buffers or proxies. Refines L-CDI-267.

### L-DQ-149  A profile job can fail in its STAGING_TO_STORE step with 'Health check could not ascertain the status. If possible, may resume automatically.' after the profiling mapping itself COMPLETED; resubmitting worked
**Kind:** GOTCHA · **Proven:** 2026-11-04 · **Evidence:** 1.48M-row, 39-column profile: PROFILING_MAPPING 22:57:33-22:59:34Z COMPLETED, STAGING_TO_STORE 22:57:33-23:20:25Z FAILED; the unchanged re-run COMPLETED in about 2.5 min (2026-11-04)
Execute returns a profileJobId. `GET <profiling-service>/job/<profileJobId>` lists jobSteps of three types: GENERATE_PROFILING_WORKFLOW, PROFILING_MAPPING (the DTM read) and STAGING_TO_STORE (the load into the cloud metric store). One run had a COMPLETED PROFILING_MAPPING (2 min, 'No errors encountered') but a STAGING_TO_STORE that ran 23 minutes and then FAILED with 'Health check could not ascertain the status. If possible, may resume automatically.' The job-level status was FAILED and it did not resume by itself. Read the step list to see which stage failed: a failure in the store step is not a source or SQL problem. Resubmit the same profile unchanged. The second run COMPLETED. Refines L-DQ-106.

### L-DQ-150  A failed profile run does not advance lastRunKey, so the 'latest run' read through runDetail still shows the previous COMPLETED run: track the job id that execute returns
**Kind:** GOTCHA · **Proven:** 2026-11-04 · **Evidence:** Job FAILED 2026-11-04 23:20Z; the same profile's lastRunKey stayed 1, and runDetail/1 showed COMPLETED, startTime 2026-11-03 23:29Z, 1,482,161 rows
After a run failed, `GET /profile/<id>` still had lastRunKey 1, and `GET /runDetail/<id>/1` answered COMPLETED with the previous day's start time and row count. A poller that reads 'the last run' reports a stale green. The reverse also holds: an unchanged run number means no run has completed since then. It does not prove that nobody tried to run it. Keep the profileJobId from `POST /profile/<id>/execute` and decide the outcome from `GET /job/<jobId>` (status plus jobSteps). Before you quote a result, check that the run's startTime is after the change you are measuring. Refines L-DQ-106.

### L-DQ-151  Metric-store column value lists include earlier runs' values: keep only the entries whose totalRows equals the column's current totalRows
**Kind:** GOTCHA · **Proven:** 2026-11-04 · **Evidence:** Pairs of near-identical frequencies for every value on re-run profiles; after the filter, 10 of 10 rule pass rates matched an independent SQL recomputation on the same sample to 0.01 % (2026-11-04)
Reading `Profiles('<id>')/Columns` with their value frequencies after a re-run returned every value twice, once with the previous run's counts and once with this run's (for example 'provisional=803161; provisional=801543'). Summing them double-counts, and a pass rate computed from VALID/INVALID mixes the two runs. Filter each value entry to `totalRows == column.totalRows` (the current run) before computing percentages. If nothing matches, fall back and flag it. Refines L-DQ-123.

### L-DQ-152  Bind independent IDMC rules to the pipeline's own proof columns: a 'passed' DQ stamp with no score, a hash of the empty string and placeholder lineage ids were all fake proofs
**Kind:** PATTERN · **Proven:** 2026-11-04 · **Evidence:** 100 % / 100 % / 100 % of gold rows on the three proof columns; lineage 76.9 % gold, 48.5 % staging, 72.1 % dictionary rows not backed by IDMC objects; 218 checks over 1,290 columns (2026-11-04)
A golden table carried the pipeline's own evidence columns, and rules run in IDMC showed that none of them measured anything. dq_status was 'passed' on 100 % of rows while dq_score was empty on 100 %. The payload SHA-256 on every row was the hash of an empty string (e3b0c442...b855). The lineage columns named non-IDMC SQL steps ('native:...') on 77 % of rows, and a placeholder mapping id on 72 % of dictionary rows. Add these rules to any table that carries self-reported quality or lineage: a status needs a score; a hash must not equal the empty-input hash and must vary; a lineage id must match a real IDMC object id pattern and resolve to an object. Fix the writer, not the rows. Refines L-DQ-122.

### L-DQ-153  Take closed-list rules from the data dictionary's own enum entries, not from observed values: the dictionary and the pipeline disagreed on half the identity-status values
**Kind:** PATTERN · **Proven:** 2026-11-04 · **Evidence:** 60 rule specifications / 218 checks; resolution status fails 50.5 % gold and 37.4 % staging; dictionary severity outside list 8.4 % (2026-11-04)
Rules for status and kind columns (record kind, stage, resolution status, model status...) used the dictionary table's enum_value entries as the reference list, the way a reference-data table would be used. That surfaced drift in both directions. The pipeline wrote resolution statuses that the dictionary did not list (failing 50.5 % of gold rows and 37.4 % of staging rows), and dictionary rows themselves used a severity value outside their own list (8.4 %). A list generated from the loaded data would have hidden both (L-DQ-122). Fix by adding the values to the dictionary or mapping them to listed ones, and keep the rule. Refines L-DQ-122.

### L-DQ-154  Rule-spec design that scores raw vs gold fairly: validity rules pass blanks, one 'value present' rule judges emptiness, and the same specs are bound to staging and gold
**Kind:** PATTERN · **Proven:** 2026-11-04 · **Evidence:** 60 rule specifications (40 new) -> 218 checks across 17 profiles and 1,290 columns; 171 checks >= 99 %, 9 at 95-99 %, 38 need a fix; 10/10 SQL spot checks equal to 0.01 % (2026-11-04)
Each rule is an IDMC rule specification with one input and output VALID/INVALID, plus a plain-English description and test data. Format, range and list rules return VALID for an empty value. Emptiness is judged once, by a separate 'required value present' rule on required columns only, so a blank is not counted as both missing and malformed. The same specifications are bound to the raw/staging table and to the golden table, so 'better in gold' is the same check on both. Scores are read from IDMC's metric store (L-DQ-123). SQL is used only to spot-check a sample of pass rates. Refines L-DQ-122.

### L-DQ-155  The profiling-service list GET /profile ignores offset: page with a large limit and check the count, or a find-by-name after create misses profiles
**Kind:** GOTCHA · **Proven:** 2026-11-05 · **Evidence:** limit=10 vs limit=10&offset=10: identical first 10; limit=1000 -> 80 profiles (all); the same session later created 300+ profiles (2026-11-05)
`GET <profiling-service>/api/v1/profile?limit=10&offset=10` returned the same 10 profiles as `?limit=10`, and `?limit=1000` returned all of them. Nothing errors, so a pager that walks offset loops on page one, and a look-up 'by name in GET /profile?limit=200' (the fallback L-DQ-128 gives when the create response has no id) silently misses profiles once the org has more than 200. Use one call with a limit well above the expected count and assert that the returned count is below the limit. Or keep your own name-to-id ledger written at create time. Refines L-DQ-128.

### L-DQ-156  Define each postal-code column's format before you write its rule: an address-verification output column held ZIP+4 text and failed a 5-digit ZIP rule on half the rows
**Kind:** GOTCHA · **Proven:** 2026-11-05 · **Evidence:** Profile patterns on the column: 9(5)-9(4) 51.49 %, 9(5) 6.4 %; every other verifier output (geocodes, FIPS, census ids, USPS flags) passed 100 % (2026-11-05)
A verifier output column meant to hold the 5-digit ZIP held 'NNNNN-NNNN' on 51.5 % of rows, even though the +4 part was already written to its own column. A 5-digit rule bound to it scored about 48 %, which looked like a verification failure when it was a format choice. Check the profile's pattern list first (9(5) vs 9(5)-9(4)). ### L-DQ-157  Data Profiling stores value frequencies and patterns in the cloud metric store: leave PII columns and raw JSON blobs out of a profile before you create it
**Kind:** SECURITY · **Proven:** 2026-11-05 · **Evidence:** One server: 10,499 columns planned, 402 excluded (PII register + name filter + payload blobs); a wider plan excluded 1,085 of 32,274 (2026-11-05)
A profile's results (top values, patterns, min/max) live in Informatica's cloud metric store, not on your agent, so profiling a column copies its values out of your network. When profiling a whole server, build the column list from a PII register plus a name filter (owner, mailing, care-of, grantor/grantee, buyer/seller, taxpayer, first/last/full name, contact, email, phone, SSN, birth, agent/broker, tenant...). Also exclude raw JSON or payload blobs that may embed those fields. Put the count of excluded columns in each profile's description so a reviewer can see the gap. Refines L-DQ-081.

### L-DQ-158  Profile a live production ClickHouse without hurting it: a separate agent host, a read-only user, one profile at a time, an off-peak window, a load guard and per-query caps
**Kind:** RECIPE · **Proven:** 2026-11-05 · **Evidence:** 22 of 315 profiles COMPLETED, 0 failures, about 1.3 min per profile (about 6.5 h for the rest inside the window) before the runner was stopped for an unrelated reason (2026-11-05)
The source served a website at about 30,000 queries an hour, and an earlier full profile run on its own host had overloaded it. What ran clean: the Secure Agent on a different VM, reading over the network with a read-only user. One profile at a time, only inside a fixed window (02:00-13:00Z), pausing whenever the server's load average is above 8. The SQL override ends in `SETTINGS max_threads = 1, max_memory_usage = 2000000000, max_execution_time = 1200, priority = 10`. Each profile reads at most 100,000 rows: all rows for small tables, every Nth granule for large MergeTree tables. The runner keeps a done-ledger so a restart skips finished profiles. Refines L-DQ-098.

### L-DQ-159  Before 'profile everything', inventory the server from its system tables and price the run in profiles and jobs against the org's job cap
**Kind:** RECIPE · **Proven:** 2026-11-05 · **Evidence:** Legacy server: 2,003 objects, 56,672 columns, about 6.1B rows in 29 databases; 1,708 objects not profilable or skipped; 'light' plan 315 profiles for 295 tables; new server 62 objects -> 19 profiles (2026-11-04/05)
One read of system.tables/system.columns/system.parts gives databases, engines, row counts and column types. Skip objects a profile cannot or should not read: views, materialized views (and their .inner storage), dictionaries, Join tables, empty tables, external or streaming engines (Kafka, S3, URL, MySQL...) and aggregate-state columns. Plan one profile per table, split by the 4,000-character override limit (L-DQ-133) and about 100 columns. Then multiply out to profiles and jobs and compare with the org's monthly job cap and any other demos that share it before running. Here the full scope was about 1,300 profiles, so the owner chose a 'light' scope: the new server plus one legacy database. Refines L-DQ-133.

### L-DQ-160  Address verification of a single free-text address box returns low-confidence matches because users type only the street: use required street, city, state and ZIP fields and full street forms
**Kind:** GOTCHA · **Proven:** 2026-11-10 · **Evidence:** Messy 4-field input -> standardized upper-case street, city, state and ZIP+4; 29 people over four 2-minute runs, none stuck; 1 abbreviated address low confidence in 46 s
A sign-up form with one address field expected 'street, city, ST 12345' but users typed only the house number and street, so the verification service could only return a low-confidence match and the UI showed nothing. With four required fields (street, city, state, ZIP), even messy input (extra spaces, lower case, 2-letter state) came back VERIFIED with ZIP+4 about 28 s after the record landed. Abbreviated forms such as '20 W 34th St, New York 10001' were still rated LOW_CONFIDENCE_MATCH while full forms ('West 34th Street') verified, and an invented address finished as low confidence in 27-33 s. Collect structured fields and treat low confidence as a reviewable result, not a pending state. Refines L-DQ-016.

### L-DQ-161  An IDMC name-cleansing capitalization step lowercased the letter after an apostrophe: 'siobhán O'NEILL' became 'Siobhán O'neill'
**Kind:** GOTCHA · **Proven:** 2026-11-10 · **Evidence:** 1 of 10 scripted user stories; the other stories, including accented names, passed
In a sign-up -> CDC -> cleanse/match golden-record pipeline, the name standardization handled accents correctly but treated the apostrophe as part of the word, so O'NEILL came out O'neill. The same class of defect is documented for CAI and plain INITCAP (L-CAI-086, L-CDI-104): treat straight and curly apostrophes and hyphens as word delimiters in the capitalization logic, and include O'/Mc/Mac and hyphenated names in the test set before loading real customers. Refines L-CDI-104.

### L-DQ-162  Pause address verification while entity ids are still being merged and re-keyed; after the migration run it once on the final master for 'no result or changed address' only
**Kind:** DECISION · **Proven:** 2026-11-12 · **Evidence:** Master address methods: certified 87.8M, verifier 2.1M, suggestion 1.7M, not verified 55k of 91.7M; ~98M paid results kept; 3 IDMC schedules + 2 external starters identified
Verifying during an identity migration wastes paid calls: results land on ids that are about to be merged or re-keyed, and the sweep mostly re-pays for addresses that already failed. With 99.9% of the new master's addresses already verified, pausing cost nothing except that new or changed entities are held from serving until the reset (safe). Pause properly: stop every external starter (cron, timer, a session-launched driver), disable the IDMC schedules that drive the verification tasks, let in-flight runs finish, and read the schedules back at the next boundary (L-METHOD-135). Reset = keep all paid results, verify once in big batches only entities with no result or a changed address fingerprint, count 'premise found, unit unconfirmed' as verified, route no-house-number or placeholder addresses to review, then verify only new or changed addresses in each incremental cycle. Refines L-METHOD-135.

### L-DQ-163  Close the profile -> recommend -> clean -> score -> gate loop on the table you actually serve: 17 profiles and 60 rules had scored only the old table and samples, and gated nothing
**Kind:** PATTERN · **Proven:** 2026-11-12 · **Evidence:** 17 profiles / 1,290 columns / 60 rule specs / 218 checks; gold 90.3% vs staging 97.3%; 73 CLAIRE insights on one table; score column NULL on 100% of rows a week later
IDMC profiling had run 17 profiles over 1,290 columns (one at 101M rows on ClickHouse), 60 rule specifications and 218 checks, and CLAIRE insights found real defects (a status with no score, an empty-input hash, ZIP+4 in a 5-digit column, half the rows provisional). Yet the score column stayed empty on 100% of rows, no rule could stop a publish, and the new golden table was never profiled. Run the loop on the served table per scope with rules bound: profile, keep only recommended rules that test something (L-DQ-122), clean in a mapping on changed records only, write the score back per row and per scope, and let a failing hard rule block that scope's publish. Count profile runs where they run, not in the activity log (L-IPU-055). Refines L-DQ-136.

### L-DQ-164  CDQ Deduplicate can consolidate duplicates into one preferred record (row or field rules), but it is not MDM: no source trust, cross-reference, history, unmerge or steward inbox
**Kind:** FACT · **Proven:** 2026-11-17 · **Evidence:** CDQ April 2026 Data Quality Assets guide ch. 6 (Deduplicate / Consolidation); corrected by an MDM SME review
The Deduplicate asset does fuzzy identity matching (scores plus a ClusterId) and has an optional Consolidation tab. Row-based consolidation picks one survivor (Most Data, Most Filled, Modal Exact); field-based picks each field separately (Highest row ID, Average, Longest, Max, Min, Most frequent, Most frequent non-blank, Shortest). So basic rule-based survivorship exists in CDQ. What it does not give you: source-trust ranking, a persistent golden record with a cross-reference to source ids, merge history, unmerge, or a steward merge/unmerge screen; Exception Management only routes borderline scores to a target. Describe it as 'dedupe + consolidate (batch)' and 'preferred record', not 'match and merge' or 'golden record', and position MDM when trust, xref, unmerge or stewardship is needed.
