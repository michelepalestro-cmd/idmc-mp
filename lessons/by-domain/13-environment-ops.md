## Current

### L-ENV-001  Reach a firewalled agent VM through a cloud IAP jump host
**Kind:** RECIPE · **Proven:** 2026-09-28 · **Evidence:** Used by several lanes when direct SSH and the cloud run-command channel were blocked or jammed
When direct SSH to the agent VM is blocked (source-IP allowlists, rotating egress), hop through a jump VM: `gcloud compute ssh <jump-vm> --zone <zone> --tunnel-through-iap --account=<user> --command "ssh -i <key-file> <user>@<vm-ip> 'sudo bash -s'"`, with the script base64-encoded inline. Move large files with `gcloud compute scp` to the jump host first, then `scp` them on. Pin `--account` (or `CLOUDSDK_CORE_ACCOUNT`) on every call: a peer session can switch the global gcloud account, and the hop then lands as a user without the key (`Permission denied (publickey)`).

### L-ENV-002  Never pipe stdin through gcloud compute ssh on Windows
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** Repeated observations on a Windows workstation
On Windows, `gcloud compute ssh` shells out to plink.exe rather than OpenSSH, and piping a script on stdin through it injects a stray "y" (the host-key prompt answer) into the stream. Copy the script with `gcloud compute scp` or inline it base64-encoded in `--command`, then run it. IAP tunnels from Windows are also slow, so run long ones in the background.

### L-ENV-003  Azure run-command invoke: root, a per-VM singleton and a 4 KB output tail
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** Conflicts and truncated output seen repeatedly across a week of shared use
`python -m azure.cli vm run-command invoke -g <rg> -n <vm> --command-id RunShellScript --scripts @file.sh --query "value[0].message" -o tsv` runs as root through the Azure control plane, needs no SSH key and is the break-glass path when SSH times out. It is a per-VM singleton: concurrent sessions get `Conflict: Run command extension execution is in progress`, sometimes for more than 5 minutes (retry with 25-60 s backoff). Output keeps only the last ~4 KB, so print small filtered results and write big dumps to a file on the VM to read back in chunks. `HOME` is `/root`, so `~` paths resolve wrong (use `sudo -u <user>` or set `HOME=/home/<user>`). Pass scripts as `--scripts @file` (inline multi-line scripts get mangled and a Windows command line caps at 32 KB); output arrives as `[stdout]...[stderr]...` inside `value[0].message`.

### L-ENV-004  Managed run-commands run beside a jammed singleton, but are capped and may be undeletable
**Kind:** WORKAROUND · **Proven:** 2026-09-24 · **Evidence:** Managed run-commands ran while invoke stayed locked; all 25 slots were full on a locked VM · **Supersedes:** L-ENV-055
`vm run-command create -g <rg> --vm-name <vm> --name <n> --script "..."` creates a named child resource that does not share the invoke singleton; read its output with `vm run-command show -g <rg> --vm-name <vm> --run-command-name <n> --instance-view --query instanceView.output -o tsv` (create returns no output, so fold create and show into one call). Output is tail-capped at ~4 KB and front-truncates, so a big base64 blob loses its head (chunk with `split -b 3000`, or use `--output-blob-uri`). Managed run-commands are capped at 25 per VM, and a `CanNotDelete` resource lock stops them from being deleted (`ScopeLocked`), so the slots eventually fill; then fall back to invoke. `docker exec -i <container> python manage.py shell < /tmp/x.py` works through a managed run-command.

### L-ENV-005  A process started through run-command dies on reboot: use systemd
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** An agent ran in the extension scope for hours until moved under its systemd unit (cgroup inspection)
A process launched with Azure run-command lives in the run-command extension's transient cgroup (a `...RunCommandLinux.slice` scope), not under systemd: nothing supervises it, it is exposed to the extension's lifecycle, and it does not survive a reboot. Start the Secure Agent and any daemon through its systemd unit and check the cgroup (`/system.slice/<unit>.service`) after starting.

### L-ENV-006  Launch long remote jobs detached and poll a log
**Kind:** RECIPE · **Proven:** 2026-08-17 · **Evidence:** Clean-slate redeploys completed despite SSH drops; 0 gap-filled lanes after the orchestrator fix
Write the whole sequence to a script, ship it on its own, start it with `setsid` (or `nohup ... </dev/null > log 2>&1 &`) so it survives SSH and IAP drops, then poll the log for a done marker with short, independent calls. Do not ship and background in the same remote command (the pipe wrote 0 bytes). An orchestrator finalizes only on an explicit DONE sentinel, confirmed process death or a wall-clock limit, never on the end of an SSH output stream, and marks unrun lanes as not evaluated rather than failed. Newer evidence: L-METHOD-148.

### L-ENV-007  Move code to a VM as base64, never through heredocs, scp or remote editors
**Kind:** GOTCHA · **Proven:** 2026-07-08 · **Evidence:** Scripts ran unmodified after base64 transfer; SyntaxErrors before
Heredocs, scp, terminal editors and inline run-command scripts mangle backslashes and strip quotes in regexes and nested f-strings. Write the file locally, base64-encode it, send the text, decode it on the VM (`base64 -d > file` or python3) and verify with a checksum or `od -c` before running it. Avoid inline f-strings with nested quotes in commands shipped over SSH.

### L-ENV-008  Human cloud logins lapse; keep service-account paths for headless work
**Kind:** GOTCHA · **Proven:** 2026-10-01 · **Evidence:** Queries across 29 datasets ran through the service-account path while the human login was lapsed; dozens of remote runs through a service-account IAP hop while the human login was lapsed (2026-09-29 to 2026-10-01)
A human gcloud token can hit a reauthentication window ("Reauthentication failed, cannot prompt") that no background session can refresh, and a warehouse-only service account cannot SSH; a service account that holds IAP-tunnel and SSH rights on the jump VM can (`gcloud compute scp|ssh <jump-vm> --account=<service-account> --tunnel-through-iap`, the account pinned on every call, L-ENV-009), and it ran dozens of remote runs while the human login was lapsed (the exact roles were not recorded). Check the human login with a timeout (`timeout 15 gcloud auth print-access-token`) instead of hanging; for warehouse work use a service-account key stored on a VM inside a throwaway container that mounts it read-only; plain SSH with an already-registered OS Login key kept working while the gcloud user token was lapsed. Management-plane actions (snapshots, instance resets) still need the human login. Hop pattern that held: tar the script and its files locally, `gcloud compute scp` the tarball plus a small hop script to the jump VM (up to 4 tries 10 s apart), run `gcloud compute ssh <jump-vm> ... --command 'bash /tmp/<hop>.sh' </dev/null`, and let the hop script copy on to the target VM with plain `scp`/`ssh` (`-o BatchMode=yes -o ConnectTimeout=20`), run and clean up; filter gcloud's banner lines out of the output.

### L-ENV-009  gcloud's active account is global state: pin the account on every call
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** SSH failed after a service-account activation until the account was reset; a peer's switch broke an IAP hop
`gcloud auth activate-service-account` makes the service account the active account for every later command on the machine, so SSH and IAP commands that need the human account fail until `gcloud config set account <human>` is run again, and scheduled jobs that self-heal by activating a service account silently flip it for everyone. Pin `--account=<user>` or `CLOUDSDK_CORE_ACCOUNT` per call instead of relying on the global setting.

### L-ENV-010  Run warehouse and database reads where the key and the client already live
**Kind:** RECIPE · **Proven:** 2026-09-25 · **Evidence:** Reads confirmed through a controller container and a database container
If the host lacks the warehouse client or the key, run the script inside a container that has both: `sudo docker exec -i <container> python -` with the script on stdin. For a private PostgreSQL reachable only from one VM, use the database or app container so the password never leaves it: `sudo docker exec -i <pg-container> sh -c 'PGPASSWORD=$POSTGRES_PASSWORD psql -U <user> -d <db> -f -'`, feeding SQL through a quoted heredoc (`<<'EOSQL'`) so `$` and backslashes survive. Strip a SQLAlchemy driver suffix (`postgresql+psycopg://`) before handing a `DATABASE_URL` to psql, and cast JSON columns to `::text` before `count(distinct ...)`.

### L-ENV-011  Corporate egress rotates, so IP-pinned firewall rules go stale
**Kind:** GOTCHA · **Proven:** 2026-07-26 · **Evidence:** Egress rotated mid-session during an agent install and throughout a week of VM work · **Supersedes:** L-ENV-054
Outbound traffic can leave through a proxy pool whose address changes mid-session (different /24s). Symptoms: SSH and admin ports that worked minutes ago time out while the public app still returns 200, and a rule you just added seems to do nothing. Sample egress per destination (an echo service may be on a bypass list), confirm ownership with RDAP (`https://rdap.arin.net/registry/ip/<ip>`), and prefer a jump host, a tailnet or a control-plane channel over allowlisting a shared proxy range (a /24 is a compromise worth flagging). If you do widen a rule, add whole ranges additively, and relaunch subagents after the fix rather than resuming them, because their cached results are the failed ones. ICMP is often blocked, so ping loss does not mean down.

### L-ENV-012  Reachability is not authentication: know which one failed
**Kind:** GOTCHA · **Proven:** 2026-07-26 · **Evidence:** Environment-trap rules recorded during an agent install
An `SSH-2.0-OpenSSH_...` banner means the port is open; `Permission denied (publickey)` means the port was never the problem; a timeout means network or firewall. `ssh -v` lists "Authentications that can continue": if it says only `publickey`, no pasted password helps. A provider's web console connects from the provider's infrastructure, so narrowing port 22 to user IPs silently breaks it (`Timed out while waiting for handshake`); keep it reachable before narrowing. Account-level SSH keys at a provider apply only to newly created instances. A long key pasted into a terminal can wrap and write a broken `authorized_keys` line that sshd silently ignores: split it into two shell variables, rejoin with `printf`, keep the directory 700 and the file 600, and verify with `ssh-keygen -lf`.

### L-ENV-013  Verify the fix and your own access; trust the provider API over its CLI
**Kind:** PROCESS · **Proven:** 2026-07-26 · **Evidence:** Environment-trap and bootstrap rules
After changing a firewall, a unit file or a permission, re-test the thing that was broken and the access you rely on; confirm a firewall actually filters by probing a port you did not allow; close anything opened temporarily in the same session. A CLI can hold its own stale stored credential and return `401 Unable to authenticate you` while the token you were given is valid: test the token against the provider's REST API before believing the CLI. Some clouds have no remote-exec API at all (console, exec and run routes 404; user data immutable, 405), so plan SSH or the provider's web console for an agent install.

### L-ENV-014  False 'site down' readings from DNS, SNI and TLS
**Kind:** GOTCHA · **Proven:** 2026-09-09 · **Evidence:** False 'down' readings corrected with --resolve and Host-header probes; a back-channel token exchange failed through the public address and passed on the internal URL, and proxy logs showed the bridge gateway as the source of local calls (2026-09-09)
A sandbox or corporate VPN that blocks outbound DNS (port 53) makes healthy hosts look down: pin the address with `curl --resolve <host>:443:<ip> https://<host>/`, use DNS-over-HTTPS, or check from the host itself. A reverse proxy with SNI virtual hosts and no catch-all answers an IP-only probe with an immediate TLS internal_error, and `curl -k https://localhost/...` can return 000 for the same reason (test with the right Host header from inside the proxy container). A zone wildcard record pointing at another server swallows a new subdomain until it gets its own explicit record. Allow about 10 s for slow root pages. Address translation adds two more false readings. No hairpin: a VM, or a container on it, that calls its own public IP or hostname can fail because the cloud does not route that traffic back to the same VM; a server-side OIDC token exchange through the public identity-provider URL failed while browsers worked, so use the internal service URL for back-channel calls, keep the public issuer for browsers and accept both issuers, and give a Secure Agent connection to a database on the same host localhost or the Docker network alias, never the public name. Docker SNAT: with `userland-proxy`, requests to the public IP from the host itself arrive with the bridge gateway as their source, so a reverse-proxy source-IP allowlist answers 403 in local tests while real clients keep their own IP: test allowlists from a genuinely external client.

### L-ENV-015  Bursts of cloud management calls from a proxied laptop get reset
**Kind:** GOTCHA · **Proven:** 2026-09-20 · **Evidence:** Intermittent resets during a tagging pass
Management-plane PATCH calls sent in tight bursts from behind an enterprise proxy were intermittently reset, while isolated calls with retries succeeded. Space bulk management calls out and retry each one.

### L-ENV-016  git-bash swallows az: call python -m azure.cli
**Kind:** GOTCHA · **Proven:** 2026-09-08 · **Evidence:** A VM create 'succeeded' while only an empty resource group existed; the module form showed the real error
Under git-bash the `az.cmd` wrapper can lose its stdout handle: `-o json` output and file redirects come back empty (0 bytes) with exit code 0, so a failed create looks successful. Call the CLI as a module (`python -m azure.cli <args>`), set `AZURE_CORE_USE_PAGER=false` and `PYTHONUTF8=1`, never treat an empty result as "no data", and read the resource back after creating it. Do not write az JSON to a POSIX temp path and read it with Windows Python; parse stdin instead. Newer evidence: L-ENV-127.

### L-ENV-017  MSYS path conversion rewrites leading-slash arguments
**Kind:** GOTCHA · **Proven:** 2026-09-08 · **Evidence:** Mangled REST paths fixed after the export; the az launcher broke with the variable set globally · **Supersedes:** L-ENV-053
git-bash converts arguments that look like POSIX paths into Windows paths: `/api/v2/connection` passed to a helper script, or `/subscriptions/...` passed to `--ids`, arrives mangled. Export `MSYS_NO_PATHCONV=1` only for the IDMC REST helpers that take path arguments; never set it globally, because it breaks the az launcher and the gcloud/bq wrapper scripts. For az, use the `-g` / `-n` forms instead of `--ids`.

### L-ENV-018  Scripts that shell out to bash wrappers can false-RED under git-bash
**Kind:** GOTCHA · **Proven:** 2026-07-08 · **Evidence:** The same gate went green from PowerShell
A Python gate that calls `bash <wrapper>.sh` from git-bash can have its `/c/...` drive paths rewritten into bogus Windows paths, so the wrapper fails and the gate reports RED while the data is fine. Run such gates from cmd or PowerShell, or call the tool directly without a shell wrapper.

### L-ENV-019  git-bash mangles brace JMESPath queries and cmd builtins
**Kind:** GOTCHA · **Proven:** 2026-07-26 · **Evidence:** The .bat approach succeeded where direct calls failed
git-bash brace-expands `az ... --query '{a:b}'`, which gives "invalid jmespath_type" errors: use `-o tsv` with a brace-free query (`--query 'value[0].message'`), `-o table`, or omit `--query` (`-o none`). Calling cmd builtins such as `cmd //c "mklink /J ..."` from git-bash can fail with "The filename, directory name, or volume label syntax is incorrect" even with `MSYS_NO_PATHCONV=1`: write the command into a `.bat` file and run that (directory junctions need no elevation).

### L-ENV-020  %VAR% does not expand in bash
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** A stray literal folder holding a key was found during a cleanup and quarantined for rotation
Writing to `%LOCALAPPDATA%/...` from bash created a folder literally named `%LOCALAPPDATA%` inside the working tree, and a plaintext cloud key landed in it. Use `$LOCALAPPDATA` (or `cygpath`) or an absolute path, and after such a mistake search for stray literal folders and key files.

### L-ENV-021  Windows MAX_PATH makes deep paths look missing
**Kind:** GOTCHA · **Proven:** 2026-07-17 · **Evidence:** False negatives on deeply nested folders
Paths longer than the Windows MAX_PATH limit (260 characters) make `os.path.exists()` return false negatives. Use the `\\?\` extended-length prefix, or `cd` into the directory and work with short relative names.

### L-ENV-022  Windows Cloud SDK traps: spaces in the SDK path, pscp, console encoding
**Kind:** GOTCHA · **Proven:** 2026-07-08 · **Evidence:** The wrappers worked; per-file copy succeeded; writer failures reproduced and fixed
Stock `gcloud` and `bq` launchers break when the Cloud SDK path contains a space: wrap them to call the SDK's bundled Python directly (`<sdk>/platform/bundledpython/python.exe <sdk>/bin/bootstrapping/bq.py`, `<sdk>/lib/gcloud.py`) with `CLOUDSDK_ROOT_DIR` exported. `gcloud compute scp --recurse` (pscp) can fail on local paths with spaces: copy files one by one. The Windows console's cp1252 encoding breaks Python writers on emoji and other non-ASCII text: set `PYTHONIOENCODING=utf-8` (and `PYTHONUTF8=1`), and pass payloads through files rather than heredocs, where apostrophes also break. Minimal VM images can lack `python3-venv`.

### L-ENV-023  The agent shell mangles backslashes in heredocs, sed and inline Python
**Kind:** GOTCHA · **Proven:** 2026-10-03 · **Evidence:** A 0x08 byte found in an expression about to be deployed; an od -c dump showed the no-op replace; a deployed shell script failed on CRLF and was fixed with newline='\n' and bash -n, and a rewritten config file lost its hidden attribute (2026-10-01 to 2026-10-03)
Code passed through shell heredocs, sed or `python -` strings lost its backslash escapes: `\b` in a regex became a literal backspace byte (0x08), `\p` and `\s` disappeared, and a `replace()` meant to escape newlines became a byte-for-byte no-op. Write regex-bearing files with the file-editing tools, use forward slashes in paths, quote heredocs (`<<'EOF'`) so `$` and backslashes reach the remote shell unchanged, and scan for control characters (`grep -P '\x08'`) before deploying. Windows-authored scripts break on Linux hosts in three more ways: Python `open(p, 'w')` on Windows writes CRLF, so a shell script written that way fails on the agent host with `$'\r': command not found` (write with `newline='\n'`, or `newline=''` to keep the source's endings, keep the live file's newline style when patching, and check with `bash -n` before deploying); Git Bash `grep -c $'\r'` miscounts carriage returns (count them on the bytes in Python); and a write to a file with the Windows Hidden attribute fails or drops the attribute (`attrib -h` first, `+h` after). Inside quoted heredocs the shell still turned `\\` into `\`: write scripts with the file tools and use `chr(92)` where a script must emit a backslash.

### L-ENV-024  Workflow scripts must be ASCII, and ${VAR} inside an agent prompt is interpolated
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** Failures on a non-ASCII script and on an unescaped template variable
Files passed as a workflow `scriptPath` are read with a legacy encoding, so non-ASCII characters break them: keep them ASCII. Workflow scripts are JavaScript, so a literal `${VAR}` or a stray backtick inside an agent prompt template is evaluated as interpolation (`ReferenceError: VAR is not defined`): escape it as `\${VAR}` or reword.

### L-ENV-025  Run automation from a private scratch directory
**Kind:** GOTCHA · **Proven:** 2026-07-06 · **Evidence:** The import broke until the stray file was avoided
Other sessions writing scripts into a shared folder such as `%TEMP%` can leave files like `inspect.py` that shadow standard-library modules and break imports (Playwright stopped importing). Run automation from a private scratch directory.

### L-ENV-026  Always sudo docker when the login user is not in the docker group
**Kind:** GOTCHA · **Proven:** 2026-09-11 · **Evidence:** A false '0 containers' reading mid-incident; sudo showed 26 of 29 containers up
Non-sudo `docker ps` or `docker info` from a user outside the docker group silently returns 0 containers and an empty DockerRootDir, which looks exactly like "the stack is down". Check container state with `sudo docker ...` only.

### L-ENV-027  Bind mounts are resolved at container start: recreate after fixing a mounted file
**Kind:** GOTCHA · **Proven:** 2026-09-08 · **Evidence:** A pipeline was dead for 38 hours behind healthy containers; two sibling containers kept failing until also recreated
If a container mounts a credential or config file that was missing or wrong at start, fixing the file on the host does not reach the running container: run `docker compose up -d --force-recreate <service>` (a plain `docker restart` does not reload `env_file` either) and check the logs. When the mount source does not exist, Docker creates an empty directory in its place, the container still shows Up (healthy), and the app fails with `[Errno 21] Is a directory`; recreate every container that mounts it, not only the first one.

### L-ENV-028  Write bind-mounted files in place so the container sees the change
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** A reverse-proxy config change that never took effect; every later flip used in-place writes
Replacing a file (write a temp file and rename it, or delete and recreate) gives it a new inode, and a container that bind-mounts that single file keeps the old inode and never sees the change. For bind-mounted configs and env files open the file `r+`, `seek(0)`, write, `truncate()` (or pipe through `sudo tee` when permissions require). If a mounted directory is replaced on the host, the container keeps serving the old one until it is restarted.

### L-ENV-029  Baked versus mounted: what goes live when
**Kind:** GOTCHA · **Proven:** 2026-09-11 · **Evidence:** Stale images and unchanged pages until rebuilt; fixes lost after rebuilds
Files copied into an image (`COPY` in the Dockerfile) go live only after that service is rebuilt; bind-mounted files change immediately; services behind compose profiles are built only with `--profile`, otherwise `run` uses a stale image; build contexts cache aggressively, so use `build --no-cache <svc>` when source changed. Fixes made in a running container's writable layer survive a restart but not a rebuild or force-recreate: put them in the repository or image and record the commit. Mapping and taskflow definition files baked into an image are read from the image layer, so a volume mount over them does not take effect.

### L-ENV-030  Cloud default usernames in mount and key paths break portability
**Kind:** GOTCHA · **Proven:** 2026-09-08 · **Evidence:** A stack moved between clouds failed silently on a cloud-specific key path
Absolute host paths such as `/home/<cloud-default-user>/<key>.json` in compose volume mounts work on one cloud (the default admin user differs: Azure images use one name, EC2 uses `ec2-user` or `ubuntu`, GCP derives it from the account) and break on another: the path does not exist, Docker creates an empty directory, the container starts and jobs fail. Use compose-project-relative paths (`./config/key.json`), Docker secrets or a secret manager, and audit every volume source (`docker compose config`) before moving a stack across clouds.

### L-ENV-031  A containerized Secure Agent registers under the container hostname
**Kind:** GOTCHA · **Proven:** 2026-09-08 · **Evidence:** A 27 GB agent volume existed only in an OS-disk snapshot; an undocumented agent was found by process inventory
When the Secure Agent runs in a container, it registers in the org under the container's hostname; without `hostname: <agent-name>` in the compose file, the container id becomes the agent name. Agents running as native OS processes do not appear in `docker ps`: inventory hosts by the agent directory and by Java processes such as `Data_Integration_Server` or `Metadata_Platform_Service`. Agent state kept in Docker named volumes exists only in OS-disk snapshots, not in file-level backups, so snapshot or extract it before deleting a VM or the agent is silently de-registered.

### L-ENV-032  Make Docker wait for its data disk, which also makes a hard reset safe
**Kind:** RECIPE · **Proven:** 2026-09-07 · **Evidence:** A reboot outage fixed on four VMs; a banner-dead VM recovered by reset
If Docker's data-root is on a separate mount, add a systemd drop-in with `RequiresMountsFor=<mount>` to `docker.service`; enabling docker alone raced the mount and the stack did not start after a reboot. With the drop-in, `gcloud compute instances reset <vm>` is a safe recovery when a VM is IO-saturated and sshd no longer returns its banner (the reset needs an operator cloud login, not the VM's service account). Newer evidence: L-ENV-101.

### L-ENV-033  Services keep their old environment until restarted through their launcher
**Kind:** GOTCHA · **Proven:** 2026-07-13 · **Evidence:** Runs completed after a launcher restart
A daemon that launches a configurable program via an env var keeps its old environment when the file or the variable changes, which can make every request fail instantly ("unrecognized arguments"): restart it through its launcher and verify with one real run. Never restart a service that tails and finalizes runs while a run is active.

### L-ENV-034  The dbt image's entrypoint always runs dbt build
**Kind:** GOTCHA · **Proven:** 2026-08-18 · **Evidence:** Live tables rebuilt by an intended compile-only run
The official dbt Docker image's ENTRYPOINT runs `dbt build`, so a "compile" through the default entrypoint silently rebuilds live models. Override it (`docker run --entrypoint dbt <image> compile ...`) when harvesting compiled SQL, for example as a mapping spec.

### L-ENV-035  In server scripts use absolute paths after cd, and back files up before writing
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** The compose file was restored from its backup
A shell script on a server that changed directory and then wrote to a relative path truncated a live compose file. Use absolute paths for every write, back the file up first, and check it afterwards.

### L-ENV-036  Exit codes and redirects that hide failures
**Kind:** GOTCHA · **Proven:** 2026-07-09 · **Evidence:** A gate reported rc=0 over 53 collection errors; a watchdog cron failed silently until the redirect moved inside sudo
Piping a test runner through `tail` makes the pipeline's exit status tail's (0): capture the runner's own exit code. `sudo cmd > /root-owned/log` runs the redirect as the caller, so every cron fire fails with Permission denied (use `sudo sh -c 'cmd > log 2>&1'` and prove the fix with one autonomous fire). `exec > >(tee /var/log/x)` without write permission fails quietly and can mask later failures. A hard-coded shared `/tmp` path created root-owned by one cron breaks later non-root runs: use per-UID temp dirs (`/tmp/<name>.$(id -u)`) with a writability check. Backgrounded Python writes nothing to its log until exit unless run with `python -u`. Use `grep -F` for literal dotted keys. Newer evidence: L-ENV-115.

### L-ENV-037  Bound long jobs and HTTP calls with hard deadlines
**Kind:** GOTCHA · **Proven:** 2026-07-13 · **Evidence:** A 12-hour silent stall; a sweep finished in 119 s instead of hanging
A sync or ingest script run by cron can hang (a stuck connection or lock) and silently block every downstream refresh for hours: wrap it in `timeout <n>` plus a lock that expires, emit a heartbeat and alert on a stale one. Python `urlopen(timeout=...)` bounds the connect and each socket read, not the whole transfer: wrap request plus read in a watchdog with a hard deadline and retry only no-response results. An endpoint sweep that reads every body hangs on server-sent-event streams: skip stream paths as well as stream content types.

### L-ENV-038  After a rename, a backup can keep 'succeeding' with a tiny dump
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** A 20-byte nightly dump reported OK
A backup script that targets a container or directory by its old name kept exiting OK after a rename while dumping nothing (a 20-byte dump, a 192-byte tar of a symlink). Monitor backup size against a floor, update backup targets as part of every rename, and take a manual dump before risky work. Newer evidence: L-ENV-113.

### L-ENV-039  Read big cloud-storage objects with bounded byte ranges only
**Kind:** GOTCHA · **Proven:** 2026-09-07 · **Evidence:** A VM reset was required to clear the IO saturation
Spot-check large archive objects with a bounded range read (`gsutil cat -r 0-5242879 gs://<bucket>/<object>`). Never stream with `gcloud storage cp <object> - | head -c N`: gcloud retry-loops on the broken pipe and re-downloads the whole object; on a 143 GB object this IO-saturated the VM until sshd stopped returning its banner and the host needed a reset.

### L-ENV-040  A read-only host watcher when two Secure Agents share one VM

### L-ENV-056  Grafana provisioning and datasource traps
**Kind:** GOTCHA · **Proven:** 2026-09-10 · **Evidence:** 420 panels audited; provisioning fixes held across provider cycles; a panel query returned 48 rows through /api/ds/query while the health check showed 403, and the provisioning reload from the host path worked (2026-09-10)
File-provisioned dashboards win over UI saves (edit the file; a same-uid DB copy is shadowed; `editable:false` titles change only after a full provider cycle); file-provisioned alert rules reject API updates (PUT 500; edit the rules file and call `POST /api/admin/provisioning/alerting/reload`); the Infinity datasource returns empty results for hosts outside `allowedHosts` or without `parser: "backend"`, and panels missing `url_options` crash in the browser while the API query succeeds; the BigQuery plugin rejects `format: "time_series"` (use `"timeseries"`); behind a sub-path all API calls need the sub-path, and BusyBox `wget` in the container cannot send PUT or DELETE; audit panels in parallel through `POST /api/ds/query`. More traps: the BigQuery datasource health check shows 403 when the Cloud Resource Manager API is disabled in the project, yet real queries work (judge the datasource with `POST /api/ds/query`, not the health button); the provisioning directory is often bind-mounted read-only into the container, so write dashboard JSON to the host-side directory and call `POST /api/admin/provisioning/dashboards/reload`; an e-mail admin login breaks URL-embedded credentials (use `curl -u '<user>@example.com:<pw>'`), and wrong admin credentials fall back silently to the anonymous Viewer (GETs succeed, POST and DELETE answer 'Permissions needed'). Apps that read IDMC-built marts directly: a summary endpoint that ran about 14 sequential COUNT(*) queries took about 10 s on every cold cache; collapse the counts into one query, prime the cache at startup, do not wire page controls inside that call's success handler, and validate LIMIT parameters (a negative value surfaced as HTTP 500).

### L-ENV-058  Postgres and API code traps met while testing apps
**Kind:** GOTCHA · **Proven:** 2026-07-13 · **Evidence:** Each fix verified by the failing test or race going green
