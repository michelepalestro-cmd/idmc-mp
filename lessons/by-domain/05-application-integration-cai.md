## Current

### L-CAI-001  Publish CAI assets headless with POST /active-bpel/asset/v1/publish on the -cai host
**Kind:** ROUTE · **Proven:** 2026-09-28 · **Evidence:** 202 plus job id and item state SUCCESS, then live invokes: 4 processes on 2026-07-09, a 9/9 migration wave on 2026-09-28
`POST https://<pod>-cai.<domain>.informaticacloud.com/active-bpel/asset/v1/publish` with headers `INFA-SESSION-ID: <v3 session>`, `Accept: application/vnd.api+json` and `Content-Type: application/vnd.api+json` and body `{"data":{"type":"publish","attributes":{"assetPaths":["Explore/<project>/<folder>/<name>.PROCESS.xml"]}}}` returns 202 with the publish job id in `data.id`. The same call publishes service connectors (`.AI_SERVICE_CONNECTOR.xml`), app connections (`.AI_CONNECTION.xml`) and guides (`.GUIDE.xml`), including assets that an import package created. It is a documented vendor resource (Invoke guide ch.3), not a bypass. Supersedes L-CAI-097 and L-CAI-098.

### L-CAI-002  Poll a publish or unpublish job and read every item: items fail inside a 200
**Kind:** ROUTE · **Proven:** 2026-09-28 · **Evidence:** Status read-backs on every publish in two orgs (2026-07-09 to 2026-09-28); job and item semantics per Invoke guide pp.31-33
`GET https://<pod>-cai.<domain>.informaticacloud.com/active-bpel/asset/v1/publish/<id>/Status` (same headers; `/unpublish/<id>/Status` for unpublish jobs; `/publish/<id>` returns job information) gives `data.attributes.jobState` (NOT_STARTED, RUNNING, IN_PROGRESS or QUEUED while it works, then SUCCESS, WARNING or ERROR) and `itemDetail[]` with `itemState`, `itemStatusDetail` and `assetPath`. The 202 and the 200 envelopes only mean the job was accepted: an item with state NOT_FOUND turns the job into WARNING and any item ERROR makes it ERROR. Poll every 4-5 s for up to about 3 minutes and stop a sequence at the first job that is not SUCCESS or WARNING. `GET` on the `/publish` starter itself returns 405 by design.

### L-CAI-003  The asset path must be Explore/<project>/<folder>/<name>.<TYPE>.xml; resolve it from the v3 catalog
**Kind:** OVERTURNED · **Proven:** 2026-09-28 · **Evidence:** BAD_REQUEST before and SUCCESS after the path fix (2026-09-24); 9/9 assets resolved by name and type and published (2026-09-28)
An asset path such as `<project>/<folder>/<name>` ends the job ERROR with item BAD_REQUEST "Invalid asset path." although the asset exists. Send `Explore/` + the v3 object `path` + `.<TYPE>.xml`, where TYPE is PROCESS, GUIDE, AI_CONNECTION or AI_SERVICE_CONNECTOR. Resolve it with `GET /public/core/v3/objects?q=type=='<TYPE>'&limit=200`, match the last `path` segment to the asset name, and refuse to publish when zero or several objects match. A project name containing a space published fine. This, not a missing designer registration, was the cause of the September "Invalid asset path" wall. Supersedes L-CAI-100.

### L-CAI-004  The publish body's data must be a JSON object: an array returns 500 ClassCastException
**Kind:** ERROR · **Proven:** 2026-09-24 · **Evidence:** 500 ClassCastException with an array, 202 with an object (2026-09-24)
Sending `{"data":[{...}]}` to `asset/v1/publish` returns HTTP 500 with a ClassCastException. Send `data` as a single object whose `attributes.assetPaths` is the array of paths.

### L-CAI-005  Accept: application/json on the asset/v1 routes returns 500 NotAcceptable
**Kind:** ERROR · **Proven:** 2026-09-22 · **Evidence:** 500 NotAcceptable versus 202 on the same body (first seen 2026-09-09, re-confirmed 2026-09-22)
The asset/v1 publish family needs both `Accept` and `Content-Type` set to `application/vnd.api+json`. With `Accept: application/json` the call returns 500 NotAcceptable, which looks like a server fault but is content negotiation.

### L-CAI-006  Publish in dependency order and stop at the first failure
**Kind:** LAW · **Proven:** 2026-09-28 · **Evidence:** 9/9 SUCCESS in dependency order (2026-09-28); 199 limit and payload order per Invoke guide p.30
Publish the AI_SERVICE_CONNECTOR first, then the AI_CONNECTION that references it, then processes without connection references, then processes that call the connection. One call accepts at most 199 asset paths and processes them in payload order. The field scripts published one asset per call and stopped at the first job that was not SUCCESS or WARNING, which keeps the cause of a failure obvious.

### L-CAI-007  Unpublish with asset/v1/unpublish, dependents first: process, then app connection, then service connector
**Kind:** OVERTURNED · **Proven:** 2026-09-29 · **Evidence:** Status read-backs in two orgs, including 59 legacy assets in one cleanup (2026-09-28/29); dependent-entry error per Invoke guide p.33
`POST https://<pod>-cai.<domain>.informaticacloud.com/active-bpel/asset/v1/unpublish` with the publish headers and `{"data":{"type":"unpublish","attributes":{"assetPaths":["Explore/<project>/<folder>/<name>.<TYPE>.xml"]}}}` returns a job id; poll `/active-bpel/asset/v1/unpublish/<id>/Status`. Unpublish processes first, then app connections, then service connectors: unpublishing an asset that something still depends on gives item ERROR "... must be unpublished first. Dependent entry(ies): <names>" and jobState ERROR inside a 200. Maximum 199 per call. Unpublish before renaming a process or its API name, changing Run On or Applies To, or deleting it. Supersedes L-CAI-102.

### L-CAI-008  Delete CAI assets through FRS, and only after unpublishing them
**Kind:** ROUTE · **Proven:** 2026-09-29 · **Evidence:** 81 of 83 legacy CAI objects removed with FRS_070 read-backs (2026-09-28); one integration's processes removed from two orgs (2026-09-29)
FRS refuses to delete an asset that is still published or out of date (`FRS_082`). After unpublishing, delete in bulk with `POST https://<pod>.<domain>.informaticacloud.com/frs/v1/DeleteEntities` and `{"artifactIds":["<frsGuid>", ...]}` (header `IDS-SESSION-ID`; per item `FRS_200` deleted, `FRS_082` still published, `FRS_087` project not empty) or one at a time with `DELETE .../frs/api/v1/BaseEntities('<frsGuid>')` (204). `DELETE .../frs/api/v1/Documents('<id>')` returns 403. Read each id back: `FRS_070` means not found.

### L-CAI-009  List CAI assets with their publication status
**Kind:** ROUTE · **Proven:** 2026-07-25 · **Evidence:** 200 live with the MimeType filter (2026-07-25); PublicationStatus filter documented, not exercised
`GET https://<pod>-cai.<domain>.informaticacloud.com/active-bpel/asset/v1/status?MimeType=<process|screenflow|connection>` lists assets of a MIME type with their publication status (published, unpublished, out-of-date); the Invoke guide also documents a `PublicationStatus=` filter. Use it to find assets edited after their last publish and to make a publish driver idempotent.

### L-CAI-010  Publishing is not API activation: activate and deactivate in the console
**Kind:** GOTCHA · **Proven:** documented, unproven (read 2026-07-25) · **Evidence:** Invoke guide p.8; no activation verb found in probes (2026-07-25) [doc]
The first publish of a process activates its API. If the API is later deactivated on the Application Integration Console APIs page, republishing does not reactivate it, and no verb activates or deactivates an API at any path found. When a published process does not answer, check the API status in Properties Detail and treat activation as a console step.

### L-CAI-011  The runtime can serve the previous version for about 20 s after a publish
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** redeploy verifications (2026-09-28)
Right after a publish ends SUCCESS, calls can still reach the old version for a few seconds (about 20 s observed). A verifier should retry (for example up to 12 times, 10 s apart) before it declares a redeploy failed, or it will roll back a good change.

### L-CAI-012  Renames, moves and Run On changes: unpublish, change, republish; recreate rather than rename by import
**Kind:** GOTCHA · **Proven:** 2026-09-26 · **Evidence:** 9-asset rename (2026-09-26); folder moves re-verified live (2026-09-24); Design guide p.203, Invoke guide p.9
A published process must be unpublished before its name, API name, Run On or Applies To can change, and then republished. A process moved to another folder is republished from its new Explore path. Import-based renames of published processes hung; recreating the connector, connection and processes under the new names, publishing them, switching callers, then unpublishing and deleting the old assets worked. Callers that still use an old name get 404 from the runtime until they are switched.

### L-CAI-013  A designer first-publish regression (cpfPublish 500) was bypassed with the bulk publish REST

After a platform client build change, the Process Designer Publish button failed for never-published assets: `POST https://<pod>-cai.<domain>.informaticacloud.com/activevos-central/<orgIdV3>/app/florence-design/services/JSON/cpfPublish` returned 500 (`publishErrorResponse`) for first publishes and 200 for republishes, the UI said "unexpected error when publishing", and assets stayed "Validation in progress..". `asset/v1/publish` still worked, so publish over REST and give Informatica support the asymmetry evidence and the client build stamp. Supersedes L-CAI-099.

### L-CAI-014  Prove a platform regression with a same-session asymmetry test
**Kind:** PROCESS · **Proven:** 2026-07-08 · **Evidence:** decisive 200/500 split reproduced with raw backend calls (2026-07-08)
To show that a failure is server-side, make the identical call with the same session and endpoint on a case that should work and on the failing case (for example republish versus first publish). A deterministic split, plus the vendor UI failing the same way, is the evidence a support ticket needs.

### L-CAI-015  asset/v1/update changes access, Run On, tracing and connection secrets (documented, untested)
**Kind:** ROUTE · **Proven:** documented, unproven (read 2026-07-25) · **Evidence:** documented only: Design guide pp.210-212 and 415-418 [doc]
`PUT <baseApiUrl>/active-bpel/asset/v1/update?assetType=Process` with `Content-Type` and `Accept` `application/json` and `INFA-SESSION-ID`, body `{"processes":[{"guid":{"$t":"<guid>"},"deployment":[{"key":{"$t":"Run On"},"value":{"$t":"cloud server"}}]}]}`, updates Allowed Users/Groups or Allow anonymous access (one or the other), API Gateway authorization, Run On and Tracing Level (None, Terse, Normal, Verbose); success is `{"status":{"$t":"SUCCESS"}}`. With `assetType=AppConnection` it sets sensitive attribute values, after which the connection must be republished. Needs the Admin, Deployer, Designer or Operator role. Never exercised here, so the host (base URL or `-cai`) is unconfirmed.

### L-CAI-016  Clone a process with its connection and connector through v3 export and import
**Kind:** OVERTURNED · **Proven:** 2026-09-22 · **Evidence:** clone imports SUCCESSFUL with checksumValid true (2026-07-04 and 2026-09-22); clones published and served (2026-09-24)
`POST /public/core/v3/export` with `{"name":"<n>","objects":[{"id":"<objectId>","includeDependencies":true}]}`, poll `GET /public/core/v3/export/<id>`, then download `GET /public/core/v3/export/<id>/package`. The zip holds `<name>.PROCESS.xml`, `.AI_CONNECTION.xml` and `.AI_SERVICE_CONNECTOR.xml` under `Explore/<project>/<folder>/`. Edit, recompute the changed files' SHA-256 lines in `exportPackage.chksum`, upload with `POST /public/core/v3/import/package` (multipart field `package`), start with `POST /public/core/v3/import/<jobId>`, poll to SUCCESSFUL, then publish: the import publishes nothing. To reach a different REST provider, clone the app connection with a new base URL. Needs the migration (export/import) role. Supersedes L-CAI-101.

### L-CAI-017  Rename a cloned process: the elements and attributes to change
**Kind:** RECIPE · **Proven:** 2026-09-22 · **Evidence:** import SUCCESSFUL, checksumValid true, PROCESS count up by one (2026-09-22)
In the cloned PROCESS file change `<types1:EntryId>`, `<types1:Name>`, `<types1:GUID>` and `<types1:DisplayName>` in the repository item, the `displayName=` and `name=` attributes of `<process>`, `PublishedContributionId` (`project:/spi.<NAME>/<NAME>.pd.xml`), and any renamed output fields together with the `to=` bindings that write them. Recompute the hashes and import; the org mints its own object id for the new asset.

### L-CAI-018  Change a live process safely: export, swap only the target XML, re-hash, import OVERWRITE, publish, verify, roll back
**Kind:** RECIPE · **Proven:** 2026-09-28 · **Evidence:** two live processes changed and verified 10/10 and 15/15 cases, one attempt auto-rolled back by the verifier (2026-09-28)
(1) Find the IDMC object id with `GET /public/core/v3/objects?q=type=='PROCESS'` and export that one object (`includeDependencies:false`); keep the zip as the undo. (2) Replace only what changes (the whole `<process ...>...</process>` element, or single `<operation to="...">` expressions) with whitespace-tolerant regexes, because the export is pretty-printed, and assert exactly one replacement each. (3) Recompute only the changed files' SHA-256 lines in `exportPackage.chksum` (upper-case hex; spaces in paths appear as `\ `). (4) Import with `defaultConflictResolution: OVERWRITE`, publish, run side-effect-free verification cases, and re-import the saved zip in the same run if any case fails. Add new inputs as optional parameters so existing callers keep working.

### L-CAI-019  Exporting a process by the GUID inside its XML gives MigrationSvc_034
**Kind:** ERROR · **Proven:** 2026-09-28 · **Evidence:** MigrationSvc_034 with the XML GUID, SUCCESSFUL with the object id (2026-09-28)
v3 export takes the IDMC object id from `/public/core/v3/objects`. The GUID written in the process XML can differ from it (an import can mint a new object id), and exporting by that GUID fails with `MigrationSvc_034` (object resolution failed).

### L-CAI-020  Author CAI assets from scratch as repository-item XML inside a hand-built import package
**Kind:** OVERTURNED · **Proven:** 2026-09-25 · **Evidence:** connector, connection and seven processes imported SUCCESSFUL and published (2026-09-25); the same assets migrated and published in a second org (2026-09-28)
Each asset is an `<aetgt:getResponse>` wrapping one `<types1:Item>` with Name, MimeType, Description, VersionLabel `1.0`, State `CURRENT`, Entry (the asset XML itself), GUID (22 random alphanumerics) and DisplayName. Package the files as `Explore/<project>/<folder>/<name>.<TYPE>.xml`, add the real `<folder>.Folder.json` and `<project>.Project.json` copied from any genuine export of an object in that folder, an `exportMetadata.v2.json` that lists the folder, the project and each asset (`objectGuid`, `objectName`, `objectType`, `path`, `metadata.objectRefs` = dependency GUIDs, `additionalInfo.documentState: VALID`), `exportPackage.chksum` and a contents CSV. Import with OVERWRITE and `includeObjects:[<guids>]`, then publish in dependency order. Persist the GUIDs so a rebuild overwrites the same assets. Supersedes L-CAI-100 and L-CAI-101.

### L-CAI-021  Copy MIME types from a genuine export: the service connector's is spelled businesssconnector
**Kind:** GOTCHA · **Proven:** 2026-09-25 · **Evidence:** imports SUCCESSFUL with these values (2026-09-25)
Repository-item MIME types: `application/xml+businesssconnector` (three s) for AI_SERVICE_CONNECTOR, `application/xml+connection` for AI_CONNECTION, `application/xml+process` for PROCESS. A mistyped MIME type is an easy way to break a hand-built package; copy the values from a genuine export.

### L-CAI-022  Process inputs must be <parameter> elements; a <field> in <input> fails publish with a bare 'Publish Error'
**Kind:** GOTCHA · **Proven:** 2026-09-24 · **Evidence:** failure isolated by bisecting variant bodies (2026-09-24); optional inputs used in later changes (2026-09-28)
Declare process inputs as `<parameter name="..." type="string">` inside `<input>`; outputs and temp fields are `<field>` elements. A `<field>` inside `<input>` imports fine, but the publish item fails with only "Publish Error". Mark optional inputs with `<options><option name="required">false</option></options>`.

### L-CAI-023  Service connector XML: otherParams before httpHeaders, a body on POST, a form-encoded token call
**Kind:** GOTCHA · **Proven:** 2026-09-25 · **Evidence:** token calls and upserts succeeded after the change (2026-09-25)
In a `restSimpleBinding`, `otherParams` must come before `httpHeaders`, and a POST action needs a `<body>`. Bodies can be literal templates such as `<body>{$payload}</body>` or generated (`<body generateUsing="JSON" .../>`). Send an OAuth client-credentials token request as a form-encoded body (`Content-Type: application/x-www-form-urlencoded`), not as query parameters, so the client secret never sits in a URL; in the working builder the `&` separators of that body were written as `&amp;amp;` inside the Entry XML.

### L-CAI-024  Test XQuery offline, and write regex-bearing XQuery with a file tool, never a heredoc
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** a 0x08 byte caught before a deploy (2026-09-28)
Process logic is XQuery/XPath 3.0 inside `<expression language="XQuery">`; functions seen working include `normalize-space`, `concat`, `string-join`, `tokenize`, `matches`, `replace`, `castable as xs:decimal` and `util:generateUUID()`. Test expressions offline first (for example with the Python elementpath library) against a case table. Shell heredocs and inline scripts altered backslashes (`\b` became a 0x08 byte, `\p` and `\s` vanished), so write such code with a file-editing tool and scan for control bytes (`grep -P '\x08'`) before deploying.

### L-CAI-025  The CAI-native design routes do not author anything: use an import package
**Kind:** WALL · **Proven:** 2026-09-22 · **Evidence:** 500/403/404 probes (2026-07-25 and 2026-09-22)
`POST /active-bpel/asset/v1/processes` returns 500 on any body; `asset/v1/import`, `/deploy` and `/save` returned 500, `designtime/v1/processes` 403 and `services/deploy` 404; `POST /public/core/v3/objects` is 405 (the catalog is read-only). File listeners and human tasks were only ever authored in the designer; Kafka and AMQP event sources, event-bound processes and fault handling are authored by package (L-CAI-116).

### L-CAI-031  Invoke an authenticated process at /active-bpel/rt/...
**Kind:** ROUTE · **Proven:** 2026-07-08 · **Evidence:** live 200 invokes (2026-07-06/07); a client fixed after 403 on every call to an anonymous process on the auth path (2026-07-08); Design guide pp.200-203
`GET|POST https://<pod>-cai.<domain>.informaticacloud.com/active-bpel/rt/<ProcessApiName>` (the vendor form) or `.../active-bpel/rt/<orgIdV3>/<ProcessApiName>` (the form that answered in the field) authenticates with HTTP Basic (an IDMC user name and password) or a session header: the Design guide documents `IDS-SESSION-ID: <v3 sessionId>`, and a field client sent `INFA-SESSION-ID` from the v3 login, cached it and retried once on 401/403. ### L-CAI-032  Discover deployed processes and their contracts
**Kind:** ROUTE · **Proven:** 2026-07-06 · **Evidence:** list 200 with 54-68 deployed services (2026-07-06); swagger, SOAP and event forms documented (Invoke guide pp.12-14)
`GET https://<pod>-cai.<domain>.informaticacloud.com/active-bpel/rt` with a session header lists the deployed services; `.../active-bpel/rt/<orgIdV3>/<Process>/schema/input` returns a process's input contract. ### L-CAI-033  A 403 on invoke is the process's access list, not an org role
**Kind:** GOTCHA · **Proven:** 2026-07-06 · **Evidence:** 403 persisted after an org role grant (2026-07-06); access semantics per Design guide pp.200-202
When an authenticated invoke returns 403 "User not authorized", the caller is not in the process's Allowed Users or Allowed Groups (users there also need the Run privilege). Granting broad org roles, including admin and migration roles, did not help. Set the access list in the designer (or with the untested `asset/v1/update`) and republish.

### L-CAI-034  No access configuration means no service URL at all
**Kind:** GOTCHA · **Proven:** documented, unproven (read 2026-07-25) · **Evidence:** documented: Invoke guide p.7, Design guide pp.200-203 [doc]
If a process has neither Allowed Users/Groups nor Allow anonymous access, publishing generates no service URL, Swagger, OpenAPI or WSDL; the process can then run only as a subprocess, and it does not appear in API Manager.

### L-CAI-035  Send inputs as strings; unknown fields return 400 'extra'; nested webhooks need a bridge
**Kind:** GOTCHA · **Proven:** 2026-07-09 · **Evidence:** raw webhook 400 and bridge calls 200 (2026-07-08); 400 'extra' on an unknown field (2026-07-09)
The field callers sent every input value as a JSON string; a process with no inputs accepts `{}`, and an unknown property returns 400 "extra". A flat input schema rejects a provider's raw webhook (nested payload plus a signature header) with 400: either author the process to accept and verify the provider payload, or run a bridge that pulls authenticated events from the provider API, flattens them and invokes the process.

### L-CAI-036  CAI leaves empty-string outputs out of the response: read a missing key as ''
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** one verifier rollback caused only by null versus '' (2026-09-28)
An output whose value is the empty string does not appear in the JSON response. Callers and verifiers must treat a missing key the same as `''`; a strict null-versus-empty comparison produced a false failure and an unnecessary rollback.

### L-CAI-037  Read invoke status codes as reachability markers
**Kind:** ERROR · **Proven:** 2026-09-26 · **Evidence:** 500, 403 and 200 edge tests (2026-07-04); 404 on a renamed process until callers switched (2026-09-26)
200: the process ran. 500 carrying a downstream error (an invalid test key, a target rejecting the write): the process ran and reached the external system. 403 "User not authorized": the runtime access list blocked the caller. 404: no published process of that name for that tenant (unpublished, renamed, wrong org id or path). 400: the input contract does not match. 429: the rate window or the 10,000-activity limit. A smoke test should assert reachability rather than business success; an orchestration process that returns 200 plus a job id proves outbound CDI orchestration.

### L-CAI-038  Anonymous endpoints run as CAI_Anonymous_<orgIdV3> and are open to anyone with the URL
**Kind:** SECURITY · **Proven:** 2026-10-03 · **Evidence:** the user kept through a 29-user cleanup (2026-09-28); anonymous write endpoints flagged in an architecture review (2026-09-28); an unauthenticated GET probe answered 500 (2026-10-03)
Processes deployed with anonymous access run as the org's system user `CAI_Anonymous_<orgIdV3>`; deleting that user in a user cleanup breaks every public endpoint. Anyone who has an anonymous URL can invoke the process, so anonymous access suits demos and side-effect-free decisions; for production writes use Allowed Users/Groups or API Gateway OAuth. ### L-CAI-050  The 10,000-activity execution limit returns 429 and blocks new instances for 15 minutes
**Kind:** LAW · **Proven:** documented, unproven (read 2026-09-12) · **Evidence:** documented: Invoke guide p.25, Monitor guide p.9; recorded as a known trap (2026-09-12) [doc]

### L-CAI-086  Naive title-casing in CAI logic breaks real names
**Kind:** GOTCHA · **Proven:** 2026-10-03 · **Evidence:** defect list from a scripted story run and a 10-case verification set (2026-09-28); re-import plus a time-travel diff around the first run: 830/830 and 875/875 rows with 0 unintended changes, and typed names held in the database, the login, the CRM and the warehouse for 23 h of lanes (2026-10-03)

The body has `input/parameter`, `output/field`, `tempFields/field` (each with name, type, description and `options/option name=referenceTo|initialvalue`, referenceTo naming a process object) and `flow` steps: start, assignment (`operation to= source=` with an `expression language=` child, often XQuery), service (`serviceName`, `serviceInput/parameter`), subflow (`subflowPath`), end (`httpStatus`), suspend, container (`type=exclusive` decision or parallel, with nested flow), group, catch, eventContainer.
