### L-DBMI-001  DBMI is served on its own `<pod>-ing` host, not the pod `/saas` host
**Kind:** OVERTURNED · **Proven:** 2026-07-26 · **Evidence:** DNS plus same-path A/B test with a bogus-twin control (2026-07-26); full task lifecycle on two pods (2026-09-22 to 2026-09-29)
Database Ingestion (DBMI) REST lives on `https://<pod>-ing.<domain>.informaticacloud.com`: design and job control under `/dbmi/public/api/v2/*`, job status under `/dbmi/api/v1/task/<taskId>/job`. A second prefix, `/mi/public/api/v2/*`, answers with typed DBMI errors and is unmapped. The same path gives a bare 404 on the pod host and a typed DBMI error on `-ing`, and `<pod>-ing` resolves in DNS while a bogus sibling does not. Take `<pod>` and `<domain>` from the login's `serverUrl` or `baseApiUrl`, and sweep the host family before believing any DBMI 404. Supersedes L-DBMI-045.

### L-DBMI-002  Read the `-ing` host's answers: a typed error is a live handler, `No static resource` is an absent route
**Kind:** ERROR · **Proven:** 2026-07-26 · **Evidence:** live probes 2026-07-26; one 2026-09-22 run reports job/status answering a GET that carried a JSON body {"jobId":<n>} (not re-verified)
`GET https://<pod>-ing.<domain>.informaticacloud.com/dbmi/public/api/v2/task/details` with a bogus id returns `{errorCode:404, errorMessage:'DBMI_TASK_WAS_NOT_FOUND'}`: a live handler that missed the id. `No static resource <path>` means the route is absent on that host. `GET .../task/create` returns 405 (the POST exists), and an empty `POST` returns 500 `Cannot invoke "Object.getClass()" because "o" is null` (the handler parsed and ran). `GET .../dbmi/public/api/v2/job/status` returned 415 `Content-Type is not supported` with and without parameters; read status from `GET /dbmi/api/v1/task/<taskId>/job` instead.

### L-DBMI-003  The DBMI task lifecycle is fully headless: create, deploy, start, stop, resume, undeploy
**Kind:** OVERTURNED · **Proven:** 2026-09-28 · **Evidence:** initial load of 24 tables / 682,385 rows (2026-09-22); CDC tasks created, deployed and started 2026-09-26, 2026-09-28 and 2026-09-29, jobs running with 0 errors
On `https://<pod>-ing.<domain>.informaticacloud.com` with `IDS-SESSION-ID: <v2 icSessionId>`: `POST /dbmi/public/api/v2/task/create` (plain task JSON) returns 200/201 `{taskId, frsId}`; `POST /dbmi/public/api/v2/task/deploy/<taskId>` with `{}` returns 202 `data.jobId`; `POST /dbmi/public/api/v2/job/start|stop|resume|undeploy` takes `{"jobId":<n>}`; poll `GET /dbmi/api/v1/task/<taskId>/job` for `status` (`processing_deploy`, `deployed`, `running`, `stopped`, `failed`, `undeployed`, and `completed` for an initial load) and `runId` (the job id). The working helpers also sent `INFA-SESSION-ID` and `icSessionId` with the same value, and one early run used `Authorization: Bearer <jwt>` plus `IDS-SESSION-ID`, so the minimum header set was not isolated. Runs also show in `GET /api/v2/activity/activityLog`. Supersedes L-DBMI-047, L-DBMI-048.

### L-DBMI-004  The task JSON that `task/create` accepts (PostgreSQL to BigQuery CDC)
**Kind:** ROUTE · **Proven:** 2026-09-29 · **Evidence:** the body that created three CDC tasks on 2026-09-28/29
`{"taskType":"dbmi","general":{"name":"<task>","location":"<project>","runtimeEnvironment":"<RE name>","type":"combined"},"source":{"connection":"<pg conn name>","schema":"public","replicationSlotName":"<slot>","replicationPlugin":"pgoutput","publication":"<pub>","restartPointForIncrementalLoad":"LATEST","selectionRules":[{"include":"<table>"}],"customProperties":{"loadType":"CDC_COMBINED","selectionMode":"RULE_BASED","lobsEnabled":"true","pwx.cdcreader.postgresql.connection.repl.slotname":"<slot>","pwx.cdcreader.postgresql.connection.repl.publication":"<pub>","pwx.cdcreader.postgresql.connection.repl.plugin":"pgoutput"}},"target":{"connection":"<bq conn name>","schema":"<dataset>","bucket":"<gcs bucket>","directory":"<dir>","dataTypeRules":[],"customProperties":{"auditColumnsPrefix":"INFA_","targetBucket":"<gcs bucket>","targetDirectory":"<dir>"}},"runtimeOptions":{"applyCycleIntervalSecs":"10","customProperties":{"FlushPeriod":"5","rat.cdcfile.cycle.interval.secs":"10"}}}`. The slot and publication appear twice (top level and in `customProperties`); keep them equal. The quickest complete body is an existing task's: `GET /dbmi/public/api/v2/task/details?taskId=<n>` returns it as `documents[].dbmiTask`.

### L-DBMI-005  `general.location` must be a project; connections and the runtime environment are referenced by name
**Kind:** GOTCHA · **Proven:** 2026-09-26 · **Evidence:** code comment 'create API only accepts the project' (2026-09-26); a copied runtime-environment name failed until the real name was used (2026-09-22)
task/create accepts only a project name in `general.location` (a folder path is rejected): create the task in `<project>`, then move it with FRS `MoveEntities` by its `frsId` and tag it. `general.runtimeEnvironment`, `source.connection` and `target.connection` take names, not ids, and a runtime-environment name copied from another org's template resolves to nothing. `task/details` reports `location` as the full path, so reset it before re-creating a task from a details body.

### L-DBMI-006  The `-ing` plane uses numeric task and job ids; the 22-character `frsId` is the FRS / v3 id
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** GUID GET gave a routing 404 (2026-09-23); FRS moves and deletes by frsId worked (2026-09-26 to 2026-09-29)
DBMI task and job routes take integer ids; calling them with a design-time GUID returns a routing 404 that looks like a missing route. The 22-character `frsId` returned by task/create (also `extraData.taskId` in the job status) is the task's v3 object id: use it for FRS move and delete, `TagObjects` and v3 export. Every deploy creates a new job id.

### L-DBMI-007  There is no DBMI update verb: re-import an edited export, or create a new task and delete the old one
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** a FlushPeriod change took effect through option A (2026-09-26); an imported task that would not deploy was replaced through option B (2026-09-28)
Option A: stop and undeploy the job (an import is refused while the task is deployed), v3-export the task, edit `<name>.DBMI_TASK.dat` (for example `common.runtimeSettings.runtimePropsMap` or `datatypeChangeRules`), replace that file's SHA-256 line in `exportPackage.chksum`, import with OVERWRITE, then deploy and start again (a new job id). Option B: read the task with `task/details`, edit `documents[].dbmiTask`, `POST task/create` a new task, deploy it, and delete the old one with `DELETE https://<pod>.<domain>.informaticacloud.com/frs/api/v1/BaseEntities('<frsId>')` (header `IDS-SESSION-ID`). Option B is also the quickest way to clone a working task.

### L-DBMI-008  `job/resume` on a deployed job that never started returns 409 `WRONG_ACTION_FOR_DEPLOYED_JOB`
**Kind:** ERROR · **Proven:** 2026-09-22 · **Evidence:** single run 2026-09-22; resume of stopped and failed jobs 2026-09-26 and 2026-09-28
Start a freshly deployed job with `job/start`; `job/resume` answers 409 `WRONG_ACTION_FOR_DEPLOYED_JOB`. `job/resume` is for a job that was stopped or failed, and it served as the rollback and auto-recovery verb later.

### L-DBMI-009  A redeploy creates a new job id and briefly gaps the target
**Kind:** GOTCHA · **Proven:** 2026-09-26 · **Evidence:** job id changed on each redeploy; about 3 minutes of view gap (2026-09-26)
After an import of changed settings, a deploy yields a new job id and a CDC_COMBINED task re-baselines; views over the target gapped for about 3 minutes. For a clean initial load, stop and undeploy, drop the target tables and the source-side `public.infa_persistent_<task>_<jobId>` table, then deploy and start.

### L-DBMI-010  DBMI tasks are not v2 tasks: `/api/v2/job` gives UI_13404 and `/api/v2/mttask` gives REPO_19035
**Kind:** ERROR · **Proven:** 2026-09-22 · **Evidence:** five taskType variants all 403 UI_13404 and 403 REPO_19035 (2026-09-22); full managed MCP registry enumeration (2026-09-23)
`POST /saas/api/v2/job` with a DBMI task id returns 403 `UI_13404 'Object identifier is not valid or missing'` for every taskType tried (MI_TASK, DMI, DBMI, DRS, MTT), and so does the agent's runAJob utility. `GET /saas/api/v2/mttask/<id>` on a DBMI id returns 403 `REPO_19035`. No managed MCP tool deploys a DBMI task. Use the `-ing` plane.

### L-DBMI-011  PostgreSQL CDC prerequisites: logical WAL, a replication role, a dedicated publication, a capped slot
**Kind:** RECIPE · **Proven:** 2026-09-26 · **Evidence:** flip proven on a preprod container with the streaming replica unaffected (2026-07-09); all prerequisites applied and CDC live (2026-09-26)
Set `wal_level=logical` (`ALTER SYSTEM SET wal_level='logical'`, then restart; logical is a superset of replica, so a physical streaming replica keeps streaming: check `pg_stat_replication`). Leave free `max_replication_slots` and `max_wal_senders`. Create a `LOGIN REPLICATION` role with CONNECT, SELECT on the captured tables and USAGE + CREATE on the schema where DBMI writes its persistence table, plus a `pg_hba.conf` line `host replication <cdc_user> <agent-cidr> scram-sha-256`. `CREATE PUBLICATION <pub> FOR TABLE ...`, set each captured table `REPLICA IDENTITY FULL`, cap retention with `max_slot_wal_keep_size` (for example 8GB), and create the slot last. On a container, check that the compose command does not pin `wal_level`, snapshot the disk first, and verify `SHOW wal_level` after the restart.

### L-DBMI-012  Four source rules that each failed a DBMI CDC job until fixed
**Kind:** GOTCHA · **Proven:** 2026-09-26 · **Evidence:** each rule failed the job until fixed; the task deployed after the changes (2026-09-24 to 2026-09-26)
(1) DBMI creates `public.infa_persistent_<task>_<job>` itself, so the CDC role needs CREATE on schema `public`. (2) That table must not be in any publication, so no `FOR ALL TABLES` publication may exist: drop it and list the tables explicitly. (3) Every captured table must be `REPLICA IDENTITY FULL` (deletes on tables without a primary key need it too). (4) Create the slot (`pg_create_logical_replication_slot('<slot>','pgoutput')`) after the publication, because pgoutput decodes with the historic catalog.

### L-DBMI-013  The CDC role needs replication and read, not DML on the application tables
**Kind:** SECURITY · **Proven:** 2026-09-28 · **Evidence:** access-map finding (2026-09-28)
A Database Ingestion CDC source role needs REPLICATION, CONNECT and SELECT on the captured tables, plus CREATE on the one schema where DBMI writes its persistence table. A governance review found a CDC role holding full DML on 27 application tables; scope it down.

### L-DBMI-014  An unconsumed slot pins WAL: create it at the switch, cap retention, watch the lag
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** disk about 95% full during planning; retention capped at 8 GB (2026-09-26 to 2026-09-28)
A logical slot that no job consumes keeps WAL until `max_slot_wal_keep_size` is reached, and then the slot is invalidated. Create a migration's new slot only right before the switch (a slot created days early can fill a nearly full disk), and expect a stopped job's slot to start retaining WAL. Check with `SELECT slot_name, active, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) FROM pg_replication_slots;`. Newer evidence: L-DBMI-064.

### L-DBMI-015  One DBMI job per replication slot; never run two CDC jobs into the same target
**Kind:** LAW · **Proven:** 2026-09-28 · **Evidence:** one consumer, 0 errors, confirmed_flush lag 0 after the switch (2026-09-28)
Only one job may consume a logical slot, and an old-org and a new-org job writing the same warehouse tables would double-write. Create or import the new task early and deploy it, but do not start it; at the switch, stop the old job first, then start the new one.

### L-DBMI-016  A slot used by a polling DBMI job shows `active=f` between cycles; never drop a live slot
**Kind:** LAW · **Proven:** 2026-09-29 · **Evidence:** 10-second slot samples showed lag 0 bytes at nearly every sample while active=f (2026-09-28); the host cleanup script was made check-only (2026-09-29)
DBMI polls its slot, so `pg_replication_slots.active` is false between cycles while `confirmed_flush_lsn` keeps advancing and retained WAL stays small. Judge a slot by its lag and by end-to-end freshness, never by the active flag. Cleanup scripts must refuse to drop a slot unless its job is known to be undeployed for good; after a cutover that reused a slot, that slot is the live one.

### L-DBMI-017  CDC_COMBINED task settings for PostgreSQL log-based capture
**Kind:** RECIPE · **Proven:** 2026-09-26 · **Evidence:** design 2026-06-28; live 2026-09-26
Use load type CDC_COMBINED (initial load, then incremental), plugin `pgoutput`, the publication and slot, restart point LATEST, a continuous job, and a BigQuery target typed and merged on the primary key. The target holds current state (MERGE), not a change log, so build views over it. When CDC takes over a table, retire any truncate-and-reload batch job writing the same target, because a full reload fights the stream.

### L-DBMI-018  `FlushPeriod` sets the latency floor: 60 s by default; 5 s cut about 85 s to about 25 s
**Kind:** PERF · **Proven:** 2026-09-26 · **Evidence:** end-to-end timer runs before and after the redeploy (2026-09-26)
The BigQuery writer's `FlushPeriod` defaults to 60 s. A task at the default measured about 85 s from source write to BigQuery; redeployed with `FlushPeriod=5` and `applyCycleIntervalSecs=10` it measured 24.9 s to the CDC table and 21.9 s to a view over it. Set `runtimeOptions.applyCycleIntervalSecs` and, in `runtimeOptions.customProperties`, `FlushPeriod` and `rat.cdcfile.cycle.interval.secs`.

### L-DBMI-019  Tables apply one after another in each cycle; split hot and cold tables into two tasks
**Kind:** PERF · **Proven:** 2026-09-29 · **Evidence:** per-table 15.4 / 22.3 / 32.9 / 34.8 s (2026-09-28); split live from 2026-09-29 03:11Z, measured 10-22 s
Within a cycle DBMI applies tables sequentially: with 13 tables the first landed in about 15 s and the last in 30-35 s. Splitting into a hot task (7 tables users watch; cycle 5 s, flush 2 s) and a cold task (7 back-office tables; cycle 10 s, flush 5 s), each with its own publication and slot, brought source-to-BigQuery latency to 10-22 s.

### L-DBMI-020  Move a CDC stream to another org on the same slot: stop the old job, start the new one, keep the old for rollback
**Kind:** PROCESS · **Proven:** 2026-09-28 · **Evidence:** about 70 s to the first target write and 3 min 13 s until all 13 tables were in continuous CDC (2026-09-28)
Deploy the new org's task ahead of time without starting it. At the switch, stop (do not undeploy) the old job, then start the new job on the same slot and publication. A CDC_COMBINED task with LATEST re-runs the initial unload into the existing target tables and then streams, and the merge apply keeps parity. Verify one consumer, 0 errors, and a source audit maximum equal to the warehouse's. Rollback = stop the new job and resume the old one on the same slot.

### L-DBMI-021  An imported DBMI task keeps the source's slot and publication names, and its first start re-runs the initial load
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** import read-back and the 3-minute re-baseline (2026-09-28)
A DBMI task imported from another org carries the source's replication slot and publication; change them, or reuse them deliberately, before deploying. On its first start a CDC_COMBINED task with cdcStartPoint LATEST re-runs the initial load, rewriting the target tables before it streams.

### L-DBMI-022  Split a running CDC task onto new slots; drop the old slot only after the old job is gone
**Kind:** PROCESS · **Proven:** 2026-09-29 · **Evidence:** split executed 2026-09-29: new tasks live at 03:11Z, old slot dropped at 03:31Z
Create the new publications (`FOR TABLE` per split; add `REPLICA IDENTITY FULL` and SELECT for any newly captured table) and their slots; create and deploy the new tasks without starting them; stop the old job and start the new ones; watch lag and errors; then undeploy the old job and drop its slot. Dropping the old slot ends the rollback path onto it, so do it only after the new tasks are verified.

### L-DBMI-023  Never set datatype rules on a BigQuery-target CDC task
**Kind:** GOTCHA · **Proven:** 2026-09-26 · **Evidence:** 2-hour outage and recovery (2026-09-26)
DBMI datatype change rules (`datatypeChangeRules`; five spellings of `timestamptz` to STRING over three redeploys) did not take effect for a BigQuery target, and a half-applied rule (staging `_EXT` column STRING, target column TIMESTAMP) made the MERGE fail non-retriably, so the job died silently for about 2 hours. Recover by redeploying with `datatypeChangeRules=[]` (a new job id). Supersedes L-DBMI-049.

### L-DBMI-024  DBMI misreads PostgreSQL fractional seconds that end in zero
**Kind:** GOTCHA · **Proven:** 2026-09-29 · **Evidence:** parity 0/0 on the affected marts after the view fix (2026-09-26); still present after an org move (2026-09-29)
PostgreSQL text trims trailing zeros (`.46035`) and DBMI stores it as `.046035`, so about 10% of timestamps are off by less than 1 s, on both the initial-load and the CDC path; whole seconds and minute or day aggregates are right. Fix it downstream: in the views over the CDC tables, take an exact batch copy's timestamp when it is within 1 s of the CDC value. Worth a support case.

### L-DBMI-025  DBMI skips no-op UPDATEs: test CDC with a real change and revert it
**Kind:** GOTCHA · **Proven:** 2026-09-26 · **Evidence:** 22 s each way (2026-09-26)
An UPDATE that changes nothing is not replicated, so it proves nothing. Make a real change and revert it (for example shift a timestamp by one microsecond and back) and time both directions.

### L-DBMI-026  Deletes replicate: purge test rows at the source and the CDC copy follows
**Kind:** GOTCHA · **Proven:** 2026-09-26 · **Evidence:** CDC dataset clean after a source purge (2026-09-26)
Source row deletes are applied to the CDC target, so purging test records at the source (after archiving them) also cleans the CDC dataset and any views over it; no separate warehouse cleanup is needed.

### L-DBMI-027  `session_replication_role=replica` silences triggers, but CDC still captures the change
**Kind:** GOTCHA · **Proven:** 2026-10-01 · **Evidence:** changes reached the warehouse in about 30 s without firing the relay (2026-09-28); a trigger inventory before a ~587-row backfill found a per-row NOTIFY trigger feeding the CAI relay, and the backfill was re-guarded with SET LOCAL plus a SHOW check (2026-10-01)
A bulk fix run in one transaction with `SET session_replication_role = replica` suppresses ordinary triggers (for example `pg_notify` relays that would flood a real-time integration), while the changes are still written to WAL and captured by logical CDC within the normal latency. Take backups and an undo script first. Pre-flight before any bulk UPDATE on a CDC source table: list its triggers (`SELECT tgname, pg_get_triggerdef(t.oid) FROM pg_trigger t JOIN pg_class c ON c.oid = t.tgrelid WHERE c.relname IN ('<table>', ...) AND NOT tgisinternal`); a per-row `pg_notify` trigger feeding a real-time relay would turn a ~590-row key backfill into ~590 CAI-to-SaaS upserts. Then, in ONE explicit transaction: `SET LOCAL session_replication_role = replica`; `SHOW session_replication_role` and abort unless it returns `replica` (SET LOCAL has no effect outside a transaction block, for example on an autocommit connection); create backup tables of the old values; run the UPDATE; commit. Setting the parameter needs a superuser (or a role granted SET on it); if the SET fails, roll back before changing anything, and keep an undo script that restores from the backup tables.

### L-DBMI-028  CDC watchdog: job state, slot lag, end-to-end freshness, bounded auto-resume
**Kind:** PROCESS · **Proven:** 2026-09-30 · **Evidence:** built after one job died silently for 2 hours and another stopped on a transient 100032 (2026-09-26); two CDC jobs passed through awaiting_auto_restart back to running after one host reboot (2026-09-30)
Every 5 minutes: check that `GET /dbmi/api/v1/task/<taskId>/job` says `running`; check that the slot exists and `pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)` is below a threshold; check that the newest source audit row older than 5 minutes is in the warehouse. Auto-resume a failed job (`job/resume`) only when the task log shows a transient warehouse error (`Retrying the job may solve the problem`, `100032`, `backendError`, `rateLimitExceeded`) and no schema or type error (`Value of type`, `cannot be assigned to`, `does not exist`, `Permission denied`), at most 3 times per rolling hour. Alert only on state changes, write one health row per check, and pause the watchdog explicitly during planned redeploys. After an agent-host reboot, deployed CDC jobs report `awaiting_auto_restart` and return to `running` by themselves (about 20 minutes after boot in one case, with slot lag back to 0 and no manual resume): treat `awaiting_auto_restart` as transient for at least 30 minutes after an agent restart before resuming or alerting, and never drop or recreate the slot meanwhile (L-DBMI-016).

### L-DBMI-029  Measure CDC landing latency per table: `APPENDS()` for inserts, change counters against `__TABLES__` for updates
**Kind:** RECIPE · **Proven:** 2026-10-01 · **Evidence:** p50 about 20 s (2026-09-27); the counter-versus-__TABLES__ method before and after the hot/cold split (2026-09-28/29); APPENDS() minus created_at over 24 h windows on two days plus three traced records at 13-21 s (2026-10-01)
Read each row's landed time from BigQuery's `APPENDS()` change-history function on the CDC tables and compare it with the source commit time. DBMI did not persist its commit timestamp (`OP_CMT_TIME`) and `track_commit_timestamp` was off, so the source row's `created_at` served as the commit proxy. A cheaper check compares the newest source `created_at` with the table's `last_modified_time`. Two methods. (1) Inserts: per row, BigQuery `APPENDS()` `_CHANGE_TIMESTAMP` minus the source `created_at`, excluding rows copied by the initial load. (2) Update-heavy traffic, where insert-based probes see nothing: sample PostgreSQL `pg_stat_user_tables` every 2 s (`n_tup_ins + n_tup_upd + n_tup_del` per table) and note when each counter first moves; poll `<dataset>.__TABLES__` `last_modified_time` every 3 s; the first last-modified after the change is the apply time. A cycle applies tables one after another (L-DBMI-019), so report every table, not one, and prove catch-up separately (an audit table's max id equal at the source and in the warehouse). Measured: one task 15-35 s per table; after the hot/cold split 10.7-22.7 s; over 24 h with the split, inserts on five tables landed in an average 25.9 s (fastest 10.0 s, n=305; 20.5 s on the hot table, 26.6-28.9 s on four transaction tables), with a 10-11 s floor on every table; new-entity inserts alone averaged 22.1 s (median 21.2 s, p90 29.7 s, worst 56 s, n=61). Views defined over the CDC tables are evaluated at query time, so a record is visible in them the moment it lands: report them as the CDC figure, not as an extra hop (L-CDI-206).

### L-DBMI-030  Where DBMI task logs live on the agent
**Kind:** GOTCHA · **Proven:** 2026-09-29 · **Evidence:** used by the watchdog and the split watch (2026-09-26 to 2026-09-29); 13 tables reached NORMAL_CONTINUOUS_CDC_TABLE 3 min 13 s after a new job started (initial unload included), and a hot/cold split took 14 tables to continuous CDC with 0 errors (2026-09-28/29)
Task logs are under `<agent_home>/apps/Database_Ingestion/logs/tasks/`, named like `*_<jobId>-CDC_COMBINED-*.log`, and are root-readable only; grep ` ERROR ` in the newest file before resuming a job. A running job's PowerExchange processes show as `PwxAgent_dbmi_<task>_<job>` under the agent's OS user. Per-table progress is logged in the newest `<task>_<jobId>*.log` as `transition event [<EVENT>]. Details: [table=<schema>.<table>`: `M4_UNLOAD_COMPLETE` marks the end of a table's initial unload and `NORMAL_CONTINUOUS_CDC_TABLE` marks it streaming. A start, restart or task split is complete when every table's latest event is NORMAL_CONTINUOUS_CDC_TABLE and the file has no ` ERROR `, ` SEVERE ` or ` FATAL ` lines (`grep -oE 'transition event \[[A-Z0-9_]+\]. Details: \[table=[a-z_.]+' <log>` lists them). Prove an old job is gone by its log's last write time and zero `PwxAgent_dbmi_<task>_<job>` processes, and prove there is one consumer on the slot.

### L-DBMI-031  Failed probe jobs linger in Running Jobs until undeployed
**Kind:** GOTCHA · **Proven:** 2026-09-24 · **Evidence:** Running Jobs clean after undeploying three probes (2026-09-24)
Failed DBMI probe instances stay in Monitor > Running Jobs until they are undeployed (in the UI or with `job/undeploy`); clean them up before demos and before deleting the tasks.

### L-DBMI-032  Initial-load (UNLOAD) tasks fail import validation with 403 FORBIDDEN when the target agent has no DBMI engine
**Kind:** ERROR · **Proven:** 2026-09-28 · **Evidence:** 5 vendor-validation errors plus 180 'skipped because of previous failures' (2026-09-28)
Importing UNLOAD tasks failed with 'Cannot validate vendor for task with type UNLOAD because of the following error: Response: 403 FORBIDDEN. Access denied.', and because an import is all-or-nothing the other 180 objects in the package were skipped. ### L-DBMI-033  A BigQuery DBMI target needs the Simba BigQuery JDBC driver set on the agent, then a restart
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** deploy failure, then success after the copy, the restart and a key fix (2026-09-28)
A deploy fails with 'Failed to load driver class com.simba.googlebigquery.jdbc.Driver' until the Simba BigQuery JDBC set is installed: about 73 jars in `<agent_home>/apps/Database_Ingestion/ext/connectors/thirdparty/`, and `GoogleBigQueryJDBC42.jar` also in `<agent_home>/apps/Database_Ingestion/<version>/dbmi_libs/libs/`, owned by the agent's OS user.
