## Current

**Secure Agent (L-AGENT)**

### L-AGENT-001  Get the installer URL and an org-scoped install token headless
**Kind:** ROUTE · **Proven:** 2026-09-28 · **Evidence:** 200 on three orgs (2026-07-01, 2026-07-25, 2026-09-28); a saved token found expired (2026-08-15)
`GET <serverUrl>/api/v2/agent/installerInfo/linux64` (or `/api/v2/agent/installerInfo/<platform>`), header `icSessionId: <v2 session>`, returns `downloadUrl` and a 122-character `installToken`. The token pins the agent to the org whose session minted it, so mint it in the target org and use it fresh: the vendor guide says install tokens expire after 24 hours, and a saved token was found expired weeks later. The v3 agent paths return 404; use the v2 route. Installing still needs a shell on the host.

### L-AGENT-002  Install and register a Linux Secure Agent in the right order
**Kind:** RECIPE · **Proven:** 2026-09-28 · **Evidence:** Checksum-verified installs registered READY on three orgs (2026-07-01, 2026-07-25/26, 2026-09-28) · **Overturns:** L-AGENT-078
1) Create a non-root OS user (the installer refuses root). 2) As that user, download `downloadUrl`, verify the published SHA-256, `chmod +x` and run `./agent64_install_ng_ext.<build>.bin -i silent`. 3) `cd <agent_home>/apps/agentcore` and start the daemon first: `./infaagent startup` (under nohup or its systemd unit). 4) Register: `./consoleAgentManager.sh configureToken <user> '<installToken>'` answers 'Login succeeded' (`configureTokenWithRuntime` also exists). Registering before the start fails with 'Cannot connect to the Agent'. 5) `./consoleAgentManager.sh getstatus` must say READY and `isConfigured` true. 6) Check the cloud side: `GET /api/v2/agent` shows the agent `active: true` in the expected org, and the agent created its own runtime environment. Then read `agentEngines[]`. An idle agent uses about 1 GB RAM.

### L-AGENT-003  Prove outbound HTTPS to IDMC from the host before installing
**Kind:** GOTCHA · **Proven:** 2026-08-18 · **Evidence:** login 405, package 404, domain root 301 (2026-08-18)
From the future agent host, a GET to the login endpoint returning 405 (it is POST-only), a 404 from a package path and a 301 from the `https://<domain>.informaticacloud.com` root together prove that egress works. A timeout or TLS failure is a firewall or proxy problem to fix before the install.

### L-AGENT-004  Installer disk and log traps
**Kind:** GOTCHA · **Proven:** 2026-07-26 · **Evidence:** Observed during an install (2026-07-26)
The Linux installer is about 382 MB and needs about 2 GB to unpack. A full disk produces blank logs and stuck runs that look like application bugs. nohup logs can come back empty because of buffering; do not read that as silence.

### L-AGENT-005  Vendor host prerequisites for a Secure Agent (documented)
**Kind:** LAW · **Documented:** 2026-08-15 · **Evidence:** Vendor Getting Started guide citations (2026-08-15)
Documented, not re-measured: Windows needs 4 CPU, 16 GB RAM, at least 5 GB free on a 250 GB disk, the MSVC++ 2015 runtime and outbound 443; Linux needs at least 11 GB free, a `libidn.so.11` (symlink it on newer distros) and a non-root install user. Engines are enabled per runtime environment and connectors per add-on connector list; see L-AGENT-039 for the headless route.

### L-AGENT-006  Run consoleAgentManager from the agentcore directory
**Kind:** RECIPE · **Proven:** 2026-07-26 · **Evidence:** Observed 2026-07-26
`consoleAgentManager.sh` sources `./version.sh` relative to the current directory, so calling it by absolute path dies with 'cannot open ./version.sh' and looks like a dead agent. Use `su - <agentuser> -c 'cd <agent_home>/apps/agentcore && ./consoleAgentManager.sh getstatus'` and expect READY.

### L-AGENT-007  Count agent JVMs with pgrep -c -f and the full class name
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** Phantom conflict reproduced 2026-07-26; one MainApp per install dir confirmed with two agents on one host 2026-09-28
Use `pgrep -c -f 'agentcore.impls.MainApp'` and expect exactly 1 per install directory (per agent). The form `pgrep -af 'agentcore.*MainApp' | wc -l` also counts your own SSH command line, returns 2 on a healthy host and invents a lock conflict.

### L-AGENT-008  A real readyToRun:false: two agent JVMs fighting the singleton lock
**Kind:** GOTCHA · **Proven:** 2026-07-26 · **Evidence:** Observed during an install (2026-07-26)
When the per-agent `readyToRun` really is false, the agent can be registered and READY on the host while its package manifest holds no DI packages and no error is raised; `ls <agent_home>/apps/` shows what was delivered. A known cause is two agent JVMs fighting the lock (`SingularApplicationLock: Cannot acquire lock, there is probably another instance running`), for example a systemd unit with `Restart=on-failure` respawning against a manual start. Keep one supervisor.

### L-AGENT-009  A systemd unit for the Secure Agent that survives reboots
**Kind:** RECIPE · **Proven:** 2026-09-28 · **Evidence:** systemctl restart -> active -> READY (2026-07-26); second-agent unit active in its own cgroup (2026-09-28)
`infaagent` forks and resolves paths relative to its own directory, so a naive unit fails silently ('cannot open ./agent_start.sh', `systemctl is-active` inactive while the agent runs). Working unit: `Type=forking`, `RemainAfterExit=yes`, `User=<agentuser>`, `WorkingDirectory=<agent_home>/apps/agentcore`, `ExecStart=<agent_home>/apps/agentcore/infaagent startup`, `ExecStop=<agent_home>/apps/agentcore/infaagent shutdown`, `KillMode=control-group`, `TimeoutStopSec=300`. Leave out `Restart=`: `agent_start.sh` already respawns agentcore, and a second supervisor fights the singleton lock. Stop any manual instance, confirm one JVM, `systemctl restart`, and confirm READY.

### L-AGENT-010  Without systemd, an @reboot crontab entry keeps the agent alive across reboots
**Kind:** WORKAROUND · **Proven:** 2026-07-08 · **Evidence:** Crontab entry verified after hardening (2026-07-04 to 2026-07-08)
An agent with neither a systemd unit nor an @reboot entry stays down after a host reboot and every schedule silently stops, with no alert. A user crontab line `@reboot sleep 30 && <agent_home>/apps/agentcore/infaagent startup` (older installs: `infaagent.sh startup`) is a zero-cost, reversible self-heal; verify with `crontab -l`. Keep a break-glass ladder: restart, reboot, re-register, reinstall, each checked from both sides (per-agent API and on-host `getstatus`). Prefer the systemd unit (L-AGENT-009).

### L-AGENT-011  An agent started through a cloud run-command lives in the extension's cgroup and dies on reboot
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** cgroup inspection before and after moving the agent to its unit (2026-09-28)
Starting the agent from `az vm run-command` puts agentcore in the run-command extension's transient scope (for example an `...RunCommandLinux.slice` / `enable_<n>.scope` cgroup). Nothing supervises it, it is exposed to the extension's lifecycle, and it does not come back after a reboot. Start agents only through their systemd unit and check the cgroup (`systemctl status <unit>` or `/proc/<pid>/cgroup` showing `/system.slice/<unit>.service`).

### L-AGENT-012  Restart the agent detached from your session
**Kind:** RECIPE · **Proven:** 2026-07-06 · **Evidence:** 8 engines RUNNING and JDBC test 200 after a nohup restart (2026-06-27); 23 engine processes back after a setsid restart (2026-07-06)
`<agent_home>/apps/agentcore/infaagent shutdown`, then `nohup <agent_home>/apps/agentcore/infaagent startup &` (or `setsid ./agent_start.sh`, or tmux). A dropped SSH or IAP session in the middle of a startup can leave the agent down. After the restart, confirm all engines RUNNING (DIS `subState` 0) and re-test one connection.

### L-AGENT-013  Make restarts safe: an orphan reaper in ExecStartPre/ExecStopPost plus a port guard, both scoped to their own install
**Kind:** RECIPE · **Proven:** 2026-09-30 · **Evidence:** Forced crash and restart: 0 orphans, 20/20 engines RUNNING in ~6 min (2026-09-26); after a host reboot an unscoped guard blocked every start of the first agent, and with the owner and path filter both agents started (2026-09-30)
`agent_start.sh` respawns agentcore in place, which can leave engine JVMs and the Process Server's embedded Postgres behind; they hold ports and lock files and the next start stalls. Install a reaper as `ExecStartPre` and `ExecStopPost` in a drop-in (`/etc/systemd/system/<unit>.service.d/10-reap-orphans.conf`) plus a */5 cron check: it kills leftover processes of the agent user (TERM, 30 s, KILL) and refuses to start, loudly, while ports 7005/14479 or `*.mv.db` files are still held. Proven: kill -9 of agentcore and its respawn loop, then `systemctl restart`: 0 orphans and 20/20 engines RUNNING in about 6 min, with CDC and CAI unaffected. Add a Process Server port guard (L-AGENT-073). When a second agent on the host also runs a Process Server (give its embedded Postgres its own port, for example 5434, and its own port guard, L-AGENT-089, L-CAI-072), scope every reaper and guard to its own install: count a port holder only if the PID belongs to that agent's OS user (`stat -c %U /proc/<pid>`), and count `*.mv.db` lock files only under that agent's home. An unscoped guard ('any holder of 7005/14479, any *.mv.db') refused every start of the first agent once the second agent's Process Server held 7005; it surfaced only at the next reboot. After a reboot check the agent process (`pgrep -u <agentuser> -c -f agentcore.impls.MainApp`, L-AGENT-007), not the unit: a `Type=forking` + `RemainAfterExit=yes` unit reads `active (exited)` even when agentcore is dead.

### L-AGENT-014  A locked user account does not stop the Secure Agent
**Kind:** GOTCHA · **Proven:** 2026-08-19 · **Evidence:** Schedules kept running during a lockout (2026-08-19)
The agent authenticates with its own agent token, so already-scheduled tasks keep running while the interactive user is locked out. REST job triggers, exports and UI work stop until the login works again. Keep login-independent work going and do not retry logins in a loop.

### L-AGENT-015  Run a second Secure Agent on the same host
**Kind:** RECIPE · **Proven:** 2026-09-28 · **Evidence:** Second agent READY under systemd, 7 services RUNNING, 0 ERROR lines, peak unit memory 5.2 GB with memory.events high=0, first agent's pid unchanged (2026-09-28)
Give it its own OS user, home and install directory (its own singleton lock and environment) and a separately named systemd unit: `Type=forking`, `RemainAfterExit=yes`, `KillMode=control-group`, `User=<agentuser2>`, no `Restart=`, and an `ExecStartPre` guard that refuses to start while a manual instance runs (match with a `[.]` pattern such as `pgrep -f '<agent_home2>/apps/agentcore[.]...'` so pgrep does not match the guard itself; the first attempt was refused by its own guard). Add `MemoryHigh`/`MemoryMax` and `CPUWeight`/`IOWeight` so it cannot starve the first agent or the apps. Deny the new user read access to the applications' secret files, and share file-lane directories through a group-writable directory instead of the first agent's home. Expect exactly one agentcore MainApp per install directory.

### L-AGENT-016  Keep the Process Server off on a second agent that shares a host
**Kind:** GOTCHA · **Proven:** 2026-09-29 · **Evidence:** Host watch showed no port clash with the Process Server off (2026-09-28/29)
The on-agent CAI Process Server binds 7080/7443, internal ports such as 7005 and 14479, and an embedded Postgres on 5432. On a host that already runs an agent and a Postgres it clashes, and a first agent's pre-start guard that refuses while 7005/14479 are held would then fail. If CAI can run on the hosted Cloud Server, leave the Process Server deselected on the second agent. Other engines picked free ports (the second agent skipped a port the first one held). Diff `ss -ltnp` before and after each service lands.

### L-AGENT-017  Set agent memory and CPU limits with systemctl set-property, and make sure every agent process and heap fits inside the cap
**Kind:** RECIPE · **Proven:** 2026-10-03 · **Evidence:** Limits raised live 2026-09-29 00:00Z; unit never throttled; second 8 GB swapfile active; an agent moved into its slice went from 8.8 GB to 3.58 GB RSS, and killing 3 orphan JVMs cut memory pressure from 62% to 4% (2026-10-03)
`systemctl set-property <unit> MemoryHigh=12G MemoryMax=14G CPUWeight=100 IOWeight=100` applies live without a restart. Persistent set-property drop-ins land in `/etc/systemd/system.control/<unit>.d/` and take precedence over `/etc/systemd/system/<unit>.d/`; with `--runtime` the change is lost at reboot. Check throttling in the unit's `memory.events` (`high=0` means never throttled) and PSI (`/proc/pressure/cpu`, `memory`). Add swap for idle JVM pages if RAM is tight (a second swapfile with `nofail` in fstab). A cap works only if (1) every agent process runs inside it: an agent first started from an interactive SSH session lived in that session's scope, uncapped (8.8 GB RSS, 41 processes), while under its own unit it used 3.6 GB, so helper scripts that start or redeploy agent components must run through `systemd-run --scope --slice=<agent-slice>`; (2) the configured `-Xmx` of every agent JVM (agentcore, the DIS Tomcat, Mass Ingestion runtimes, other engines) plus the DTMs fits under it: about 9.5 GB of configured heap inside a 4 GB cap throttled constantly even when idle (`memory.events` high about 12 million, CPU throttled in 24% of periods at a 0.5-vCPU quota), so deselect unneeded services and lower their heaps, or raise the cap; and (3) there are no duplicate JVMs: three orphaned copies of the agent's Administrator app JVM (none bound to its port) pushed the slice over MemoryHigh (memory.pressure full avg10 62%), and killing them dropped pressure to 4% and freed about 1 GB. Read `memory.events`, `memory.pressure` and `cpu.stat` (`nr_throttled`) under `/sys/fs/cgroup/<slice>/` to see the cap biting.

### L-AGENT-018  Two agents on one 4-vCPU host contend for CPU, not memory
**Kind:** PERF · **Proven:** 2026-09-29 · **Evidence:** Lane 7.7 min -> 3.5 min; PSI 16-19% -> ~10% (2026-09-29)
With two agents, catalog Metadata services and app containers on 4 vCPU, pipelines slowed from CPU contention while memory was not throttled (`memory.events high=0`). Lower the idle agent's `CPUWeight`/`IOWeight`, give the working agent `MemoryHigh`/`MemoryMax` headroom, add swap for idle JVM pages, and deselect the Metadata services when scans are done (that freed about 3.7 GB RAM and cut CPU PSI from about 16-19% to about 10%). A 16-task lane went from 7.7 min to 3.5 min after the tuning.

### L-AGENT-019  Cap parallel task fan-out at about the host's vCPU count
**Kind:** PERF · **Proven:** 2026-09-29 · **Evidence:** Measured lane times before and after (2026-09-29)
Mapping tasks on a small agent host are CPU-bound. Staged fan-out at concurrency 4 on a 4-vCPU host shared by two agents roughly halved lane times (a 16-task lane 462 s -> 215 s; sign-up to golden record about 5 min -> 93 s). Going wider risks contention and DTM heap pressure.

### L-AGENT-020  Agent health comes from the v2 agent routes, not from v3 objects
**Kind:** ROUTE · **Proven:** 2026-07-26 · **Evidence:** 200 on several orgs; 25 engine rows captured per snapshot (2026-07-04 to 2026-07-26)
On `<serverUrl>` with `icSessionId`: `GET /api/v2/runtimeEnvironment` lists runtime environments with nested `agents[]`; `GET /api/v2/agent` lists agents; `GET /api/v2/agent/<agentId>` gives `active`, `readyToRun`, `version` (agent core, for example 76.x), `upgradeStatus`, `lastUpgradeCheck` and `packages[]`; `GET /api/v2/agent/details/<agentId>` gives `agentEngines[]` with `agentEngineStatus.status`, `desiredStatus`, `appname`, `displayName`, `subState` and the engine version. No v3 object type returns live agent status or version. A health script should be read-only and exit with the number of unhealthy agents.

### L-AGENT-021  The runtime-environment list reports a stale readyToRun:false; read health per agent
**Kind:** GOTCHA · **Proven:** 2026-07-26 · **Evidence:** 3/3 reproductions on one org (2026-07-26); the same false negative on another org's agents (2026-07-04 to 2026-07-09) · **Overturns:** L-AGENT-082
`GET /api/v2/runtimeEnvironment` returned `agents[].readyToRun: false` for agents that `GET /api/v2/agent/<agentId>` reported as true, reproducibly (3 reads of 3), while the host said READY and one agent JVM ran. The list value is not refreshed per heartbeat. Trust the per-agent read, cross-check with on-host `getstatus`, and confirm with a connection test before diagnosing anything from the list.

### L-AGENT-022  readyToRun exists twice, and only catalog-source creation checks it
**Kind:** GOTCHA · **Proven:** 2026-07-04 · **Evidence:** 22 mapping tasks ran state=1 with both agents reading readyToRun false (2026-07-04); catalog-source create 500 (2026-06-27)
The agent object (`GET /api/v2/agent/<agentId>`) can say `readyToRun=true` while the nested `agents[].readyToRun` in `GET /api/v2/runtimeEnvironment/<reId>` still says false; they sync separately. Mapping-task runs (`POST /api/v2/job`) ignore both flags and complete. The CDGC create-catalog-source call validates the runtime-environment view and returned 500 'Error while validating Runtime Environment detail [<reId>] under global config option [Execution]' while the nested flag was false; existing catalog sources still scanned.

### L-AGENT-023  Licensed, assigned, deploying and running-and-resolvable are four different states
**Kind:** LAW · **Proven:** 2026-07-26 · **Evidence:** API RUNNING while the router refused (2026-07-26) · **Overturns:** L-AGENT-083
1 LICENSED: Administrator > Licenses (no licence inventory API). 2 ASSIGNED: the service is selected on the runtime environment (L-AGENT-039). 3 DEPLOYING: `agentEngines[].agentEngineStatus.status` sits at DEPLOYING while packages download. 4 RUNNING and resolvable: only a passing connection test or a job proves it. The API can say RUNNING while the agent log says UNKNOWN and the cloud router still answers 'No running service found of type ...'. Engine versions (for example DIS 77.x, Connector_Service 21.x) move independently of the agent core version (76.x).

### L-AGENT-024  A confirmation is not a completion: engines deploy for many minutes
**Kind:** LAW · **Proven:** 2026-09-28 · **Evidence:** 45+ min DEPLOYING (2026-07-26); 18 min to RUNNING after a trimmed PUT (2026-09-28)
After services are enabled (UI toast or a selections PUT), engines sit DEPLOYING while installers download and unpack: 45+ minutes for a large set on a small host, about 18 minutes for a trimmed set (PUT at 22:10Z, engines RUNNING 22:28Z). Poll `GET /api/v2/agent/details/<agentId>` and wait for a passing connection test before using the runtime.

### L-AGENT-025  After an enablement the agent pulls packages itself; no reinstall
**Kind:** GOTCHA · **Proven:** 2026-07-26 · **Evidence:** 1 -> 23 engines, 9 RUNNING and 14 DEPLOYING (2026-07-26)
After a licence change or service enablement the agent polls IDMC and downloads the new engine packages on its own, with no restart or reinstall: one agent went from 1 engine to 22-23 engines, all DEPLOYING within minutes.

### L-AGENT-026  An error that changes between attempts is deployment progress, not a new wall
**Kind:** GOTCHA · **Proven:** 2026-07-26 · **Evidence:** Observed error progression during a bring-up (2026-07-26)
While engines deploy (20+ minutes), connection tests fail with an error that moves down the stack: 'No running service ... Data_Integration_Server 77.*', then '... Connector_Service 21.*', then a timeout or a driver-level error. Each shift means the previous layer is fixed; wait and re-read instead of reconfiguring. Under host memory pressure the same rotation appears because the engine the handshake needs is being OOM-killed (L-AGENT-052).

### L-AGENT-027  An isolated 500 CMN_001 on one package download retries itself
**Kind:** GOTCHA · **Proven:** 2026-07-26 · **Evidence:** Observed 2026-07-26
An isolated `500 CMN_001` on a single `appspec/dependency/package/.../urls/...` fetch during engine deployment is retried automatically (backoff up to 80 s) and does not stall the other packages. Do not intervene.

### L-AGENT-028  Alert on real engine failures only, not on transient states
**Kind:** GOTCHA · **Proven:** 2026-07-05 · **Evidence:** Flapping stopped (2026-07-05); a persistent RESTARTING loop seen on two agents (2026-07-04)
Treat RESTARTING and DEPLOYING as transients and RUNNING-while-desired-STOPPED as not an outage; alert only on STOPPED or FAILED when `desiredStatus` is RUNNING, and on a RESTARTING loop that persists across restart cycles. Counting transients as unhealthy made critical alerts flap.

### L-AGENT-029  Agent-health alert rules need a scheduled exporter and LF textfiles
**Kind:** GOTCHA · **Proven:** 2026-07-04 · **Evidence:** Empty series fixed; synthetic agent-down alert delivered (2026-07-04)
An exporter script plus loaded alert rules still gives an empty series if nothing runs the exporter. Schedule it (for example every 5 min), write the node_exporter textfile atomically with LF line endings (CRLF breaks the textfile collector), check for one non-empty series per agent, and inject a synthetic agent-down event to prove delivery end to end.

### L-AGENT-030  One login sees every runtime environment: loop them all and count them first
**Kind:** GOTCHA · **Proven:** 2026-07-08 · **Evidence:** Pre-fix collector captured 1 RE; post-fix 2 env rows (2026-07-04 to 2026-07-08)
A single org login enumerates all runtime environments, so one collector can monitor several environments. Iterate every RE, agent and connection (remove any `break` after the first element) and stamp an environment label or `re_id` on every row. Enumerate the REs from the API before asserting 'all N agents healthy'; an assertion written for a third agent that does not exist is wrong by construction.

### L-AGENT-031  403 APP_13401 and 500 CMN_001 under /api/v2/agent/* are router artifacts
**Kind:** LAW · **Proven:** 2026-07-26 · **Evidence:** Bogus twins byte-identical (2026-07-26) · **Overturns:** L-AGENT-085
`GET /api/v2/agent/<bogus>` returns 403 `APP_13401` and `GET /api/v2/agent/<bogus>/<id>` returns 500 `CMN_001`, byte-identical to the answers from `POST /api/v2/agent/service`. They prove neither the presence nor the absence of a handler; never cite them either way. Bogus-twin error codes, not only 200s.

### L-AGENT-032  Preflight in five calls, then read the verdict off the branch
**Kind:** PROCESS · **Proven:** 2026-07-26 · **Evidence:** Used on two orgs (2026-07-26)
Before any agent work: `POST https://<domain>.informaticacloud.com/saas/public/core/v3/login` (org, pod); `GET /api/v2/org` (both id shapes); `GET /api/v2/agent` (any agents?); `GET /api/v2/agent/<agentId>` (per-agent `readyToRun`); `GET /api/v2/agent/details/<agentId>` (`agentEngines[]`). Verdicts: `agents: []` = entitlement unresolved, install an agent; only `OpsInsightsDataCollector` = telemetry only, agent-bound calls fail 403 APP_105060, select services; `Data_Integration_Server` DEPLOYING = wait, a rotating error is progress; DI RUNNING but the connection test fails = adapter or driver gate; `readyToRun:false` from the list = re-read per agent.

### L-AGENT-033  Bootstrap from zero to a running job
**Kind:** PROCESS · **Proven:** 2026-09-28 · **Evidence:** Run on a new sub-org (2026-07-25/26); step 7 made headless (2026-09-28)
1 log in and pick the plane; 2 confirm org and pod (`GET /api/v2/org`); 3 read the gate (agents, `agentEngines[]`, per-agent `readyToRun`); 4 get the install token; 5 size the host, install and register (needs a shell); 6 read the runtime environment the agent created; 7 select services, then connectors (headless since 2026-09-28, L-AGENT-039), then stage drivers; 8 create and test connections against tables that hold rows; 9 create or clone tasks and schedules; 10 run with `POST /api/v2/job`; 11 monitor with activityLog/activityMonitor. All steps except 5 are REST.

### L-AGENT-034  Establish the four gates in order: host, engine, adapter, driver
**Kind:** LAW · **Proven:** 2026-09-28 · **Evidence:** Gate order from several bring-ups; the four error signatures observed 2026-07-26 to 2026-09-28
A working connection needs four independent things, and each fails with its own error that looks like 'the connection is broken': HOST (RAM, disk, swap, OS libraries, egress, only the engines you need), ENGINE (the service selected and RUNNING, not DEPLOYING), ADAPTER (the connector enabled on that runtime environment and deployed to the agent), DRIVER (third-party JDBC jars staged where the connector reads them). Establish them in that order; only then do connection bodies and credentials matter. Read what the error names (engine, `com.informatica.adapter.<x>`, 'Unable to load driver') and fix that gate.

### L-AGENT-035  Runtime environments: list and create on v2
**Kind:** ROUTE · **Proven:** 2026-07-26 · **Evidence:** 200/400/415 live; v3 plural 200 vs 404 A/B across pods (2026-07-25/26)
`GET /api/v2/runtimeEnvironment` lists runtime environments and `POST /api/v2/runtimeEnvironment` creates one (an empty body returns 400, so the verb exists). A Secure Agent creates its own runtime environment when it registers. The Informatica Cloud Hosted Agent is the only runtime environment usable without a Secure Agent. `GET /public/core/v3/runtimeEnvironments` returned 200 on one pod and 404 on another, and the singular `/public/core/v3/runtimeEnvironment` answered 415; prefer the v2 forms.

### L-AGENT-036  A runtime environment is a network position: choose it by where the data lives
**Kind:** DECISION · **Proven:** 2026-07-26 · **Evidence:** Vendor runtime docs plus live 404s (2026-07-26)
Hosted Agent: runs inside Informatica, nothing to install, SaaS-to-SaaS only where the connector supports it; it cannot reach a private network, and a connection bound to it creates with 200 and then cannot see a private host. Secure Agent group: a host you own; the only option that reaches a private database; you own patching, disk, RAM and uptime. Serverless runtime: Informatica-managed compute inside your own AWS or Azure account (your VPC/VNet, subnets and an IAM role); it cannot reach other clouds or data centres, bills IPUs per runtime-hour, and its creation is UI-only (`/public/core/v3/serverlessRuntimeEnvironments` and `/api/v2/serverlessRuntimeEnvironment` both 404 while a control call proves the plane).

### L-AGENT-037  An agent reaches only what its own network reaches
**Kind:** GOTCHA · **Proven:** 2026-07-08 · **Evidence:** Cross-cloud tests timed out; mirrors repointed to local sources tested green (2026-06-27 to 2026-07-08)

### L-AGENT-077  An agent in a lifecycle restart loop is fully down in each trough

### L-AGENT-088  Edit an agent's System/Custom Configuration headless through the legacy agent.do form
**Kind:** RECIPE · **Proven:** 2026-09-29 · **Evidence:** A custom DIS Tomcat row plus a DTM JVM option were saved, read back, pushed by the cloud into `tomcat.cfg`/`pmrdtm.cfg`, and followed by an automatic DIS restart about 1.5 min later (2026-09-29)

### L-AGENT-099  The Data Integration Server runs only 2 DTMs at once by default: measure the queue, then raise maxDTMProcesses cloud-side
**Kind:** PERF · **Proven:** 2026-09-29 · **Evidence:** Default pool, 472 sessions: queue wait p50 13.9 s, p90 39.7 s, p99 70.1 s, max 76.3 s; 61% waited over 10 s; at most 2 concurrent DTMs. After the cloud-side row (N=4) plus a 2 GB DTM heap: the startup log showed poolSize=4; a 15-minute burst sampled every 5 s reached 4 concurrent DTMs, minimum MemAvailable 10.1 GB, agent unit peak 7.55 GB under a 12 GB MemoryHigh; a 40-task full refresh ran 40/40 in 321 s and an event lane's record-to-golden time fell from 62-85 s to 47 s
Every mapping-task session waits for a slot in the Data Integration Server (DIS) DTM pool. Its size is the Tomcat property `maxDTMProcesses`; with no such line in `tomcat.cfg` the documented default 2 applies, and DIS logs it at startup in `<agent_home>/apps/Data_Integration_Server/logs/tomcat/tomcat_<disVersion>.log` as `maxDTMProcesses(poolSize)=2`. Each session logs 'Submit job to thread pool queue', 'Creating DTM process' and 'DTM process started'; the gap between the first and the last is its queue wait. With the default pool an orchestrator that starts 4 tasks at once never gets more than 2 concurrent DTMs, so its speed-up is capped however many tasks it submits. CPU was not the limit: a warehouse-bound DTM spends most of its 14-20 s waiting on the warehouse load or query job and only about 2 s on JVM start. Fix: add the Custom Configuration row Data Integration Server / TOMCAT_CFG / `maxDTMProcesses` = N (the Tomcat type does not list this property, so it must be a custom row; headless through the agent.do form, L-AGENT-088), together with the DTM heap (`JVMOption1=-Xmx2048m`, type DTM, L-AGENT-056), so both survive version rolls. Size N to memory (about 0.5-1 GB per DTM plus heap headroom inside the agent's memory limit) and to the vCPUs (4 on a 4-vCPU host shared with a second agent); on hosts too small for 2 DTMs go the other way (`maxDTMProcesses=1`, L-DQ-098). Apply it in a drained window: the save restarts DIS by itself about 1.5-2 min later and may roll it to a pending build; the old JVM kept dispatching until the new one's tunnel opened (no dispatch gap was seen) and lingered 5-8 min, so verify on the running DIS and DTM command lines (`ps -o args`) and the new startup log line, not on the newest version directory. Re-measure the queue-wait histogram (aim for p90 under 10 s), sample concurrent DTM child processes, and add a soak check that alerts when the pool size or the heap drifts from the intended values.

### L-CONN-001  Create connections with type TOOLKIT_CCI and the connector name in instanceName
**Kind:** ROUTE · **Proven:** 2026-09-12 · **Evidence:** 200 on three orgs and several connectors (2026-06-27, 2026-07-26, 2026-09-12); APP_10519 for flat bodies · **Overturns:** L-CONN-076

### L-CONN-002  The create validator names one missing field per call: iterate until 200
**Kind:** RECIPE · **Proven:** 2026-07-26 · **Evidence:** Iterative 105054 responses ending in 200 (2026-06-27, 2026-07-26)

### L-CONN-006  Update a connection by POSTing the full body to /api/v2/connection/<connId>
**Kind:** ROUTE · **Proven:** 2026-09-28 · **Evidence:** REPO_10200 without the id, 200 with it (2026-08-20); 8 connections updated and tested (2026-09-28)

### L-CONN-007  GET returns secrets masked, so every update must re-supply them
**Kind:** GOTCHA · **Proven:** 2026-09-23 · **Evidence:** Private key blanked by an update, test green after re-supplying it (2026-09-23)
`GET /api/v2/connection/<connId>` returns the password or private key masked. POSTing the body back to change one attribute (for example `useLegacySQLForCustomQuery`) blanks the secret and breaks the connection unless the secret field is re-supplied. ### L-CONN-008  Set connection secrets headless on the host that holds them
**Kind:** RECIPE · **Proven:** 2026-09-28 · **Evidence:** 8 of 8 imported connections tested 200 on the target agent (2026-09-28); 3 connections fixed after a password rotation (2026-09-16)

### L-CONN-009  Repoint connections after a database move without changing their ids

### L-CONN-010  Renaming a shared connection is risky
**Kind:** GOTCHA · **Proven:** 2026-09-24 · **Evidence:** Decision note after a key was blanked (2026-09-24)
A rename is an update that re-sends the whole object: for key-based connections (BigQuery V2) a rewrite without the secret blanks the key, and other tools and sessions may reference the connection by name. Rename only in a coordinated window, re-supply the secret, and re-test.

### L-CONN-011  Before renaming or retiring a database user, find every IDMC connection that logs in as it
**Kind:** LAW · **Proven:** 2026-09-26 · **Evidence:** One connection missed for 6 hours; lanes green again after the update (2026-09-26)
A shared database role is often used by several IDMC connections, plus CDC tasks, BI tools and backups. When it is renamed or retired, every connection still logging in as the old user fails at run time, and every dependent task and taskflow fails each cycle ('password authentication failed for user <old>'). List all connections whose `userName` is the old role (not only the one named after the app), update them in the same window with the password re-supplied, and run a health watcher that alerts on state changes.

### L-CONN-014  Test a connection with GET /api/v2/connection/test/<connId>: a free metadata handshake
**Kind:** ROUTE · **Proven:** 2026-09-23 · **Evidence:** 200 'test successful' on dozens of connections (2026-06-27 to 2026-09-28); POST variants 500/404
`GET <serverUrl>/api/v2/connection/test/<connId>` (header `icSessionId`; some native CCI tests append `?type=TOOLKIT_CCI`, and one July record got 400 without it) returns 200 'test successful' or an error such as 403 APP_105060. It is a read-only metadata handshake: no data run, 0 IPU, so it is the tool for reachability matrices across runtime environments. `POST /api/v2/connection/test` returned 500 (APP_21000 seen) and `/api/v2/connection/<connId>/test` 404. The managed MCP `connectionmanagement.test_connection_by_id` is a reliable alternative. `GET /api/v2/connection/<connId>` carries a cached `status` of the last test (success, failed, or absent).

### L-CONN-015  A passing test is not the proof; a run that lands rows is
**Kind:** GOTCHA · **Proven:** 2026-08-19 · **Evidence:** Test and run results diverged on JDBC V2 connections (2026-08-18/19)
A connection test only proves the handshake. It can pass with a wrong password (JDBC V2), and it can fail while the path works for jobs. The definitive proof of a connection is a mapping run that lands rows in the target, checked by count.

### L-CONN-016  Connection and connector reads
**Kind:** ROUTE · **Proven:** 2026-10-03 · **Evidence:** 200 live (2026-07-04 to 2026-07-25); browse 200 [] with and without ?type=table on two working PostgreSQL connections, the test 200 in 1.4 s with sessions 10 -> 11 and xact_commit +8 (2026-10-03)
`GET /api/v2/connection` lists connections (with the cached test `status`); `GET /api/v2/connection/<connId>` reads one; `GET /api/v2/connection/source/<connId>?type=table` browses source objects (200 or 403 per connection, and it can surface target-side errors such as a throttled warehouse), but it can also return 200 with an empty list for a working connection (two native PostgreSQL connections whose databases held tables, a known-good BigQuery connection), so an empty browse proves nothing: confirm objects through a consumer (profile source fields, a mapping preview, a catalog Metadata Extraction); `GET /api/v2/connector` returns the connector type catalog; `GET /api/v2/connector/metadata?connectorName=<name>` returns a connector's schema, and `200 []` means the connector is not activated. The v3 `/public/core/v3/connections` path is 404: connections are v2 only. To prove that a connection test really reached the database and was not a cached status, diff the database's own counters around `GET /api/v2/connection/test/<connId>`: on PostgreSQL the test opened one session and committed about 8 transactions (`pg_stat_database.sessions` +1, `xact_commit` +8) in 1.4 s.

### L-CONN-020  Copying adapter jars into the agent does not enable a connector
**Kind:** GOTCHA · **Proven:** 2026-09-22 · **Evidence:** Jar-copy attempts failed (2026-09-20/22); package auto-downloaded after enablement (2026-09-14)
Connector enablement is a control-plane push: once the connector is selected for the runtime environment, the control plane registers its attributes (which clears APP_105060) and pushes a new DIS appspec, and the agent downloads the package and deploys the jars itself. Adapter jars copied by hand into plugin folders are not registered and are reconciled away on restart, and `consoleAgentManager` has no install verb.
