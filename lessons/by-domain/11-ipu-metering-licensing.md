## Current

**IPU, metering and licensing (L-IPU)**

### L-IPU-001  An IPU is one fungible consumption credit spent across eligible services
**Kind:** LAW · **Documented:** 2026-09-03 · **Evidence:** Documented (CPDS v39.1, pricing pages, accessed 2026-09-03)
The CPDS defines the Informatica Processing Unit as 'a unit of capacity that can be used across eligible Cloud Services'. A subscription is one pool (aggregated across the customer's orgs and sub-orgs), and each service draws it down per its own scalar (compute hours, rows, GB, API calls, daily assets, events, queries) at a published, usually tiered, IPU-per-metric-unit rate. Consumption is measured monthly. Cross-service rules: a job that uses another service's components is charged at the highest applicable rate, and a natural-language query that triggers another service also consumes that service's IPUs. Compute Units assume a minimum of four CPU cores. New eligible services are activated for the pool automatically.

### L-IPU-002  Subscription shapes: IDMC IPU (monthly), Flex IPU (annual), Unlimited Flex, Overage Protection
**Kind:** LAW · **Documented:** 2026-09-03 · **Evidence:** Documented (CPDS v39.1 product notes)
IDMC - IPU: the subscribed IPUs are consumed across a monthly period, nothing carries over, and exceeding the quantity means subscribing to more IPUs for the rest of the term. IDMC - Flex IPU: consumed across an annual period, no carry-over, and consumption beyond it without more IPUs is charged the overage fee in the Order. Unlimited - IDMC - Flex IPU: no maximum quantity, for deployment in a single parent org. IPU and Flex IPU must be provisioned separately and may not be deployed in the same org. Overage Protection (IPU only, not Flex) triggers a joint review when consumption exceeds the subscription by up to 25% in any two consecutive months or three of five, or by 100% in one month, with quarterly reviews.

### L-IPU-003  Published consumption rates for the main services (CPDS v39.1, tier 1)
**Kind:** LAW · **Documented:** 2026-09-03 · **Evidence:** Documented (CPDS v39.1 matrix, rate-card file)
These are public rates, not prices: Data Integration 0.16 IPU per compute hour for the first 2,000 hours a month, then 0.025; Data Quality 0.38 then 0.152; Advanced (elastic) DI 0.19; SQL ELT (advanced pushdown) 0.048 IPU per million rows for the first 100M; Application Integration 1.453 IPU per thousand API calls for the first 20K (tiering down to 0.015); API Center 13.33 per million calls; Database Ingestion CDC 6.5 per million rows for the first 15M; bulk database or application ingestion 0.1 per GB for the first 2 TB; file ingestion 0.03 per GB; DGC Scanner 0.32 per compute hour; CLAIRE GPT 50 per thousand queries. Advanced Serverless variants cost more per unit (DI 0.16 -> 0.28). The rate card converts usage to IPUs; what an IPU costs is set in the customer's Order. Re-verify against the current CPDS before quoting. Newer evidence: L-IPU-063.

### L-IPU-004  The Measurement Guide defines the metered unit; the rate card gives the multiplier
**Kind:** GOTCHA · **Documented:** 2026-09-11 · **Evidence:** Documented (Measurement Guide 39.1); guide and rate card reviewed 2026-09-11
For Data Integration jobs (mapping task, mapping, synchronization, data transfer) one compute hour is one job running one hour on the integration service using up to four CPU cores; jobs are measured to the second with no minimum, and more than four cores pro-rates (for example 45 minutes on 6 cores = 1.125 compute hours). Serverless compute hours are the serverless compute-unit factor times elapsed time. A CAI 'API call' is one execution of a process, subprocess, guide or OData endpoint (each subprocess call adds one), not one outbound HTTP call, and processes on a Secure Agent also accrue compute hours. The same feed therefore meters differently as a CAI process (per call) or as a CDI mapping with a REST connector (compute hours): confirm the build style before sizing.

### L-IPU-005  Development, taskflow orchestration and reads are free; runs, previews and scans are metered
**Kind:** LAW · **Proven:** 2026-09-03 · **Evidence:** Documented (Measurement Guide); observed 0-IPU author-time work (2026-07-04 to 2026-07-26)
The Measurement Guide says development in any org incurs no compute hours except when it invokes test or run jobs; UI data preview does incur compute hours; Taskflow and Linear Taskflow orchestration of other jobs incurs no compute hours (the tasks it runs do). Recorded as 0 IPU in practice: creating or editing mapping tasks, connections, schedules and catalog-source configs, migration clones and imports, connection create/test/delete, user groups and role bindings, and metering-export reads. Billable: task runs, catalog scans and profiles, DaaS lookups, serverless runtime hours, and every backing service call behind a managed MCP tool (MCP itself was not metered during the preview, so an agent looping on prompts can burn real IPUs while the MCP line reads zero). Do not stall author-time work behind a spend gate.

### L-IPU-006  Outside the IPU pool: MDM SaaS (records), Operational Insights (instance), connectors (tiers)
**Kind:** OVERTURNED · **Documented:** 2026-09-03 · **Evidence:** Documented (CPDS v39.1 pp. 7 and 28, effective 2026-06-05) · **Overturns:** L-IPU-048
MDM SaaS (Customer 360 and the other 360 apps) is licensed by unconsolidated records per data domain, not IPUs. It bundles Data Integration (Business 360 connector, full transforms), Data Synchronization with unlimited Secure Agents, ingestion of Business 360 events, DQ assets, Application Integration, API Gateway, 100 named users, sandboxes and hierarchy management, but only where MDM is the sole source or target; Address Verify still needs a Premium Address pack or IPUs, and integration between non-MDM systems, standalone ingestion, standalone CAI/API Center and all of CDGC use the IPU pool. Operational Insights is subscribed per instance. Connectors are tier-licensed (Tier A included; Tiers B, C and D per end point) and do not draw from the pool.

### L-IPU-007  Data Integration and Data Quality meter separately but draw one pool
**Kind:** LAW · **Documented:** 2026-08-14 · **Evidence:** Vendor metering documentation (2026-08-14)
DI and DQ have distinct meters (both compute hours), and both draw the same IPU balance with no double metering. DQ has no run engine of its own: DQ assets run inside a CDI mapping on the agent, billed as DQ hours. Adding CDI to a DQ deal grows consumption from the same pool rather than competing for budget.

### L-IPU-008  Classify each flow before sizing IPUs, and ask for counts and sizes, not runtimes
**Kind:** RECIPE · **Proven:** 2026-09-21 · **Evidence:** Sizing worksheet method (2026-09-21); one sizing engagement recomputed with the calculator's engine and checked against industry benchmarks (2026-09-21)
A live database source with ongoing changes = CDI plus CDC (one Database Ingestion and Replication task does the initial snapshot and the change capture). One-time batch reads, file drops, ETL and DQ = CDI (DQ bills as DQ hours inside a CDI mapping). Application writes and API ingests = CAI API calls. A BI tool live-querying the warehouse = no IPU. Ask for records per month and row size, files per month and file size, calls per month and complexity, never for runtimes. Work volumes down from business drivers (sites x active customers x activity per customer x cadence), not from discovery sample files: in one engagement the sample-derived anchor was about 3x too low and published industry benchmarks matched the driver-derived figure. Give the customer three plain input columns that mirror the calculator's own questions ('What the calculator asks for', 'How much per month', 'How big / how complex') plus a computed output column they never fill in; for compute-hour lines ask for the calculator's complexity level (Simple, Moderate, Complex), never a runtime; define a record as one row and its size as the KB it takes, not a column count. Report steady state (about 36 IPU a month in that case) and a peak band that combines growth, a faster cadence and batched versus unbatched API writes (about 100 to about 147, L-IPU-009), and check feasibility against the target API's own concurrency limits.

### L-IPU-009  At small volumes, run counts and API-write batching drive IPU, not gigabytes
**Kind:** PERF · **Proven:** 2026-09-21 · **Evidence:** Calculator re-implemented and run on a worked example (2026-09-21)
Below about a gigabyte a month, ingestion is close to 0 IPU and scheduled compute hours for DQ and ETL dominate. For API-write-heavy targets, batching is the lever: one call per document with nested lines instead of one call per line (about 4x), then bulk batches, moved one flow from about 20 to about 4.8 to about 0.1 IPU per month; a whole small pipeline came to about 24-36 IPU per month pooled. Present the value as orchestration and data quality, not volume.

### L-IPU-010  Estimator traps: a service name that does not match the rate card prices at 0 with no error
**Kind:** GOTCHA · **Proven:** 2026-08-03 · **Evidence:** A CDC line priced at 0 (2026-08-03)
Estimators that look up the service string on the rate card (for example an Excel MATCH) silently price a line at 0 when the name differs: the rate card abbreviates the CDC lines ('App Ingestion and Replication - Change Data Capture', 'DB Ingestion...') while the Measurement Guide uses full names. Keep separate constants for the rate-card name and the metering name, and recalculate in Excel to catch zeros.

### L-IPU-011  Continuous CDC moves the cost into IDMC consumption
**Kind:** GOTCHA · **Proven:** 2026-06-28 · **Evidence:** Planning estimate (2026-06-28)
Moving from batch to continuous CDC keeps warehouse cost small (and cappable) but makes IDMC the growing cost line, because continuous ingestion keeps consuming IPUs (CDC meters per million rows, front-loaded: 6.5 for the first 15M). Model CDC explicitly, in IPUs per month from the expected change volume.

### L-IPU-012  BI live queries and pure warehouse SQL consume 0 IPU
**Kind:** LAW · **Proven:** 2026-09-24 · **Evidence:** Design notes (2026-09-22 to 2026-09-24)
A BI tool live-querying curated warehouse views (for example with a read-only service account) needs no IDMC step and consumes 0 IPU, and marts built purely by warehouse SQL outside IDMC also consume 0 IPU. IPU is consumed by IDMC task runs (pushdown included), CAI and the other metered services.

### L-IPU-013  Serverless runtime trades IPUs for operations; a Secure Agent has no runtime-hour charge
**Kind:** GOTCHA · **Proven:** 2026-07-26 · **Evidence:** Vendor runtime docs (2026-07-26); CPDS matrix
A Secure Agent carries no IPU charge for being up (jobs on it still meter their compute hours, and you pay for the host). Serverless and Advanced Serverless variants cost more IPUs per unit (for example DI 0.16 -> 0.28 per compute hour) and serverless runtime environments bill per runtime-hour; they also cannot reach private data outside their own cloud account.

### L-IPU-014  Target-side capacity bills separately from IPUs
**Kind:** GOTCHA · **Proven:** 2026-07-04 · **Evidence:** Azure pricing read (2026-07-04)
Warehouse or target capacity is its own bill. A pay-as-you-go Microsoft Fabric capacity bills per second while Active, idle or not, and costs nothing only while paused (July 2026, East US 2 public pricing: an F2 was about $0.36 per CU-hour, about $262 a month 24x7). For parity tests or demos keep a small capacity paused, resize up only for the window, then scale back and pause.

### L-IPU-016  A monthly IPU quantity read as annual (or the reverse) is wrong twelvefold
**Kind:** GOTCHA · **Proven:** 2026-08-17 · **Evidence:** Error caught in a one-pager (2026-08-17)
Tools that store an IPU quantity or its cost as a bare number invite a 12x error: one estimate reported a monthly commitment as a yearly figure. Keep the unit in variable names and outputs, and model consumption as IPUs per month.

### L-IPU-019  Size with the published consumption rates; what an IPU costs comes from the customer's Order
**Kind:** SECURITY · **Proven:** 2026-09-03 · **Evidence:** Pricing-reference review (2026-09-03)
Explain and size consumption only with the published rates (the CPDS IPU-per-unit rates). What an IPU costs, any volume terms and overage or Flex rates are set in the customer's Order, so send commercial questions to the Informatica account team instead of quoting figures in technical material.

### L-IPU-020  Treat job runs as spend: get and record explicit approval before burning IPUs
**Kind:** PROCESS · **Proven:** 2026-09-23 · **Evidence:** Approval recorded in the tracker (2026-09-23)
Every run consumes IPUs, so real runs stay on demand and minimal until the org owner explicitly approves IPU use; record the approval verbatim in the tracker. In a shared org every IPU spent draws on the owner's entitlement, so note that in the approval record. Prefer an on-demand run over raising schedule frequency for demos.

### L-IPU-021  Read IPU consumption headless with the async ExportMeteringData job
**Kind:** OVERTURNED · **Proven:** 2026-10-03 · **Evidence:** 201 -> SUCCESS -> ZIP on three orgs (2026-07-04 to 2026-07-26); SUMMARY 201 then SUCCESS in about 4.5 min with the corrected header, PROJECT_FOLDER over 33 days 400 LS_298 within a second (2026-10-03) · **Overturns:** L-IPU-045, L-IPU-046
`POST <serverUrl>/public/core/v3/license/metering/ExportMeteringData` (header `INFA-SESSION-ID`) with `{"jobType":"SUMMARY","startDate":"2026-06-01T00:00:00Z","endDate":"2026-07-26T00:00:00Z"}` (jobType `SUMMARY`, `ASSET` or `PROJECT_FOLDER`) returns 201 and a job id. Poll the job until SUCCESS (about 3-4.5 minutes), then GET `.../<jobId>/download` for a ZIP with one CSV per org (read it as bytes). CSV header: `OrgId,MeterId,MeterName,Date,BillingPeriodStartDate,BillingPeriodEndDate,MeterUsage,IPU,Scalar,MetricCategory,OrgName,OrgType,IPURate` (the period columns are `BillingPeriodStartDate` and `BillingPeriodEndDate`). Dates need full ISO-8601 with a zone (a bare `2026-06-01` gives 400 V3API_007) and `jobType` alone gives 400 LS_147. It needs no extra entitlement and the reads cost 0 IPU. The poll path is recorded two ways: `GET /public/core/v3/license/metering/ExportMeteringData/<jobId>` and `GET /public/core/v3/license/metering/jobs/<jobId>`. Windows: a `PROJECT_FOLDER` export over 33 days was refused with 400 `LS_298` ('... can not be apart 30 days') and created no job, while `SUMMARY` accepted the same 33 days (and longer windows): split detail exports (PROJECT_FOLDER, and plan ASSET the same way) into windows of 30 days or less. A trial org returns the header only (L-IPU-023).

### L-IPU-022  The metering summary GETs return 404; use the export
**Kind:** GOTCHA · **Proven:** 2026-07-26 · **Evidence:** 404 on every summary path (2026-07-04 to 2026-07-26)
`GET /public/core/v3/license/metering/MeteringUsageSummary`, `AssetUsageSummary`, `/metering/summary` and `/consumption-summary` answered 404 'No static resource' on orgs where the async export worked. Do not read that 404 as 'metering is not entitled'.

### L-IPU-023  Trial and embedded sub-orgs accrue zero billed IPU even when jobs run
**Kind:** GOTCHA · **Proven:** 2026-07-09 · **Evidence:** 0-row metering CSV with successful runs (2026-07-04 to 2026-07-09)
A sub-org on a trial or embedded model ran a daily 22-mapping pipeline successfully while the metering export stayed header-only (0 records, IPU total 0.0). A $0 cost verdict from such an org is trial-conditional; the real rate is only in the Order. Check the org type and entitlement model before expecting non-zero IPUs, and estimate with a labelled proxy meanwhile (L-IPU-024).

### L-IPU-024  Build a labelled IPU proxy from the activity log when billed IPU reads 0
**Kind:** RECIPE · **Proven:** 2026-10-03 · **Evidence:** Proxy 3.92 IPU vs 3.95 processing hours over 200 runs (2026-07-04); 3,700 rows read in 4 pages: 0 top-level rows had runtimeEnvironmentId or agentId, 4,115 of 4,121 entries had agentId (2026-10-03)
`GET <serverUrl>/api/v2/activity/activityLog?rowLimit=1000&offset=<n>` returns runs (flatten `entries[]` for taskflows) with `startTimeUtc`, `endTimeUtc`, task type and row counts. Top-level rows carry `objectId`, `objectName`, `type` (MTT, WORKFLOW, MAPPING), `runId`, `state`, `startedBy` and `runContextType` (`REST_API_V2` or `SCHEDULER`) but no `runtimeEnvironmentId` and no `agentId`: `agentId` sits only in each row's `entries[]`, so map `entries[].agentId` to its runtime environment, or attribute by object-name prefix. The log pages 1,000 rows per call and about 3,700-3,800 rows covered the last ~4 days; count jobs as task rows plus taskflow rows plus each taskflow's children (2,329 rows were 2,775 jobs). Compute processing hours per run, apply an editable rate (for example 1.0 IPU per processing hour, or the DI 0.16 compute-hour rate), and group by day, task type and environment. Label every proxy row `estimate=true, billed=false, basis=activityLog-duration, model_version=proxy-v1`, and emit it next to the billed rows from the export so dashboards switch to billed data when it appears.

### L-IPU-025  An IPU meter that cannot read the activity log reports 0 instead of failing
**Kind:** GOTCHA · **Proven:** 2026-07-07 · **Evidence:** False green reproduced and fixed (2026-07-07)
An estimator that reads the activity log emitted a success status with 0.0 consumption when the log call returned 403 or nothing. Treat zero or unsampled consumption as unknown, not green, and fail on collector errors.

### L-IPU-026  Near-zero metered usage means nothing has ever run in the org
**Kind:** GOTCHA · **Proven:** 2026-07-26 · **Evidence:** Metering export on a new sub-org (2026-07-26)
A metering export whose only line is a trivial API Center charge (for example 0.0000133 IPU) independently confirms that no integration job has ever executed in the org; use it as corroborating evidence before diagnosing 'broken' runs.

### L-IPU-027  The Administrator Metering console shows usage; reporting is not instant
**Kind:** LAW · **Documented:** 2026-09-03 · **Evidence:** Documented (Measurement Guide, pricing pages)
Usage is tracked automatically in the product: the Administrator Metering console shows consumption, administrators can set consumption threshold alerts, and usage is measured monthly. Row-metered pushdown (SQL ELT, PowerCenter pushdown) is visible within about 15 minutes of job completion; several inventory-style meters (catalog, governance, scanner) are counted per day. Billing periods need not align with calendar months (a period can end mid-month), so read `BillingPeriodStart`/`BillingPeriodEnd` rather than the calendar.

### L-IPU-028  Administrator CSV exports give the agent, licence and connector-endpoint inventory
**Kind:** RECIPE · **Proven:** 2026-09-09 · **Evidence:** Export files taken from two orgs (2026-09-09)
The Administrator console's CSV downloads (the menu path was not recorded) produced: Agents (UUID, Agent Group Name, Agent Name, Available Processors, Created On, Updated On, Status, Version, Agent ID); License (UUID, License Type Name, Service Name, Edition Name, Category such as Mappings / Packages / Connectors / Bundles, License Type such as SUBSCRIPTION, Expiration Date); CAI Connections (UUID, Connection Name, Connector Type, Publication Status, OData Enabled, Runs On Agent Only); Unique Endpoints (UUID, Connection, Connection Type, Pricing Tier, connector property, Service URL, Database, Schema, Host, Username, Created, Last Used, Days Since Last Used). The License export is the licence inventory that REST does not offer, and Unique Endpoints with its Pricing Tier column is the input for connector tier licensing per end point. Treat these files as customer data.

### L-IPU-029  There is no licence inventory API; one per-org licence read exists
**Kind:** WALL · **Proven:** 2026-09-28 · **Evidence:** 404s on two orgs (2026-07-25/26); license/org 200 with the v3 id and V3API_016 with the v2 id (2026-09-28)
`/public/core/v3/licenses` -> 404 'No static resource'; `/api/v2/license` -> 404 on a sub-org (200 on another org); `/api/v2/org/<id>/license[s]` -> 404; `/api/v2/org/<id>` -> 403 REPO_10404 from a sub-org user. `GET <serverUrl>/public/core/v3/license/org/<orgIdV3>` returns per-org licence detail (200) when given the 22-character v3 org id (the 6-character v2 id gives V3API_016); TRIAL licences came back without names and `customLimits: []`. Read the licence list in Administrator > Organization > Licenses (for a sub-org, the parent's Sub-Organizations > Licenses) or its CSV export (L-IPU-028).

### L-IPU-030  Read the org's active licences and limits from the licence service's EffectiveLicenses()
**Kind:** ROUTE · **Proven:** 2026-09-28 · **Evidence:** active[] read (2026-07-09); limits all -1 in two orgs (2026-09-28)
`GET https://<pod>.<domain>.informaticacloud.com/license-service/api/v1/OrgLicenseAssignment('<orgIdV3>')/EffectiveLicenses()` with headers `IDS-SESSION-ID: <session>` and `Accept: application/json` (the call the console itself makes) returns `active[]` (each `{id, name}`; one org listed 469 active licences, including CLAIRE GPT, clairegpt.core and ai.agent.engineering.designer while the login `products[]` said only Integration Cloud) and `limits{}` (licence id -> value). Every limit read -1 in two orgs (32 and 76 limits), including one that had just hit a monthly job cap, so this call does not reveal the cap (L-IPU-041).

### L-IPU-031  Entitlement ground truth: privileges, feature flags, licences, engines and selections, never products[] or a bare 404
**Kind:** OVERTURNED · **Proven:** 2026-09-24 · **Evidence:** Capabilities proven usable on orgs whose products[] said only Integration Cloud (2026-07-04 to 2026-09-24) · **Overturns:** L-IPU-049, L-IPU-050
The v3 login `products[]` may name only the base entitlement ('Integration Cloud') while CDGC, MCC, CDQ, DAM, Data Prep, DBMI, CAI, MDM, CLAIRE GPT and API Manager ride under it. Verify each capability against: the identity-service Login (roles, `effectivePrivileges`, `feature.<cap>.*` flags; L-IPU-032); `EffectiveLicenses()` `active[]` (L-IPU-030); the engines deployed on each agent (`GET /api/v2/agent/details/<agentId>`); the runtime-environment selections (what can be enabled); and real design objects of the type in `GET /public/core/v3/objects`. A bare 404 on a guessed path means wrong path or host; `objects?q=type=='X'` returning 0 proves nothing (the filter is not validated); the connector catalog is not entitlement. With no agent installed, entitlement is unresolved, not disproven. This retired about 90 false 'buy a licence' escalations on one org.

### L-IPU-032  Read privileges and roles to answer 'is this licensed?'
**Kind:** RECIPE · **Proven:** 2026-07-26 · **Evidence:** Privilege counts on two orgs (2026-07-06, 2026-07-25)
`POST https://<domain>.informaticacloud.com/identity-service/api/v1/Login` returns the user's `effectivePrivileges`, roles and `feature.*` flags; `GET <serverUrl>/public/core/v3/privileges` (for example 897 effective privileges) and `GET /public/core/v3/roles` (for example 59) return 200 too. Count privileges by product prefix (MDM/B360, CDGC/catalog, Marketplace, API Manager/apim, DBMI such as `create.dbmi.task`, DQ/VERIFIER, DAM/cdam, CLAIRE GPT, metering such as `metering.admin`) and list roles such as Customer360, CLAIRE GPT User or Data Marketplace Admin, then combine with the agent engine list.

### L-IPU-033  Licensed, entitled, selected and running are separate layers
**Kind:** LAW · **Proven:** 2026-09-28 · **Evidence:** Layer misdiagnosed on an org that held 321 licences (2026-07-26); selections made headless (2026-09-28)
Licensed: the contract record (Administrator > Licenses, its CSV export, `EffectiveLicenses()` `active[]`). Entitled in the org: the privileges, feature flags and the services or connectors the runtime environment lets you select. Selected on a runtime environment: `enabled: true` in the selections. Deployed and running: `agentEngines[]` RUNNING, and resolvable only when a connection test or job passes. Each fails with a different signature; most 'licensing' problems turn out to be the selection or engine layer (no service selected, or the agent not ready).

### L-IPU-034  Check the parent org first: allocation is often an assignment, not a purchase
**Kind:** OVERTURNED · **Proven:** 2026-07-26 · **Evidence:** Parent login and engine read; 1 -> 22 engines (2026-07-26) · **Overturns:** L-IPU-051
A sub-org exposing a single engine looked unlicensed. The parent org enumerated 22 sub-orgs and its shared agent ran 22 engines (DI, Metadata Foundation and Platform, Database Ingestion, process-engine); enabling services on the sub-org's own agent then delivered all 22 engines with no reinstall. Probe the parent before calling anything a purchase.

### L-IPU-035  Sub-org licence allocation is UI-only
**Kind:** WALL · **Proven:** 2026-07-26 · **Evidence:** UI-only walls list (2026-07-26)
Licences are allocated down to a sub-org in the parent org: Administrator > Sub-Organizations > Licenses. No REST verb was found and no receipt text has been captured.

### L-IPU-036  Sub-orgs inherit entitlements from the parent org
**Kind:** LAW · **Proven:** 2026-07-04 · **Evidence:** Sub-org runs succeeded with 0 billed IPU (2026-07-04)
A sub-org may show a narrow `products[]` in its own login and still use capabilities entitled on the parent. Check the parent org id and its entitlements. Trial or embedded sub-orgs accrue zero billed IPU even when capabilities run (L-IPU-023).

### L-IPU-037  An absent privilege is weak evidence of a missing SKU
**Kind:** GOTCHA · **Disputed:** 2026-07-25 · **Evidence:** Privilege facet and a 404 only (2026-07-04, 2026-07-25)
The API developer portal was flagged as the one likely genuine entitlement gap in the API family: API Manager privileges were present, no Developer Portal privilege existed among about 660 privileges (only B2B partner-portal ones), and `GET /public/api/v1/apiPortal` returned 404. That rests on an absent privilege, which is weak evidence; confirm in Administrator whether a distinct developer-portal add-on exists before escalating.

### L-IPU-038  CLAIRE GPT was entitled although no agent engine served it
**Kind:** OVERTURNED · **Proven:** 2026-07-09 · **Evidence:** EffectiveLicenses active entries plus a live 201 (2026-07-09) · **Overturns:** L-IPU-052
CLAIRE GPT looked like the one genuine purchase: no agentic engine among an agent's 17, and probes of `/data360/claire-gpt/*`, `copilot`, `agent/v1` on the wrong hosts returned 404. `EffectiveLicenses()` listed CLAIRE GPT and clairegpt.core as active, and a live query on the service's own host returned 201. CLAIRE GPT is a cloud service, so its entitlement shows in licences and privileges, not in agent engines.

### L-IPU-039  In a shared org, some UI roles can be licence-locked for a demo user
**Kind:** GOTCHA · **Proven:** 2026-09-24 · **Evidence:** addRoles error text (2026-09-24)
A shared org's demo user could not see Monitor > All Jobs, Data Integration > My Jobs or the Application Integration Console ('insufficient permissions'), and adding Monitor or Operator roles failed with 'license status is not enabled'. Work around it with Monitor > Running Jobs, the Operational Insights dashboards, or apps that read the job APIs directly.

### L-IPU-040  Database Ingestion priced as a fixed floor plus 24x7 runtime is unverified
**Kind:** GOTCHA · **Disputed:** 2026-07-05 · **Evidence:** Tracker task-title claim (2026-07-05) vs CPDS v39.1 matrix
One July source described DBMI pricing as a fixed floor plus 24x7 runtime rather than volume, and advised against CDC when batch met the cadence. That structure came from a tracker task title and was never verified; the CPDS meters Database Ingestion CDC per million rows processed (tiered) and bulk loads per GB. Size CDC from the CPDS rates.

### L-IPU-041  A monthly job limit (seen at 10,000 jobs) stops every Data Integration job and cannot be read over the API
**Kind:** WALL · **Proven:** 2026-09-28 · **Evidence:** Error text on every run 04:24-11:55Z, jobs succeeding again from 12:39Z (2026-09-28); API reads in two orgs
