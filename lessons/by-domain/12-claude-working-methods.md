## Current

### L-METHOD-001  Credentials come from environment variables or a 0600 file outside any repo, never literals
**Kind:** LAW · **Proven:** 2026-09-28 · **Evidence:** Standing rule of the reference skill and of the September host tooling; secret-scan gates on committed tooling came back clean
Read IDMC credentials at run time from environment variables (for example `IDMC_USER` / `IDMC_PASS`) or from a mode-0600 file that lives outside every repository and shared folder, one file per org. Never put a credential literal in a script, a committed config, a command line, a tracker comment or chat. Session caches, OAuth env files and service-account key files are credentials too: gitignore them and keep them 0600. A path to a secret is fine to share; its contents are not.

### L-METHOD-002  Put every IDMC call behind one org-aware session module
**Kind:** PROCESS · **Proven:** 2026-09-28 · **Evidence:** A host was flipped between orgs with one switch-file write; post-flip verification returned the new org id and pod base
Give every script on a host one small module that exposes `sess()`, `get()`, `post()`, `call(method, path, body, v3=False)` and `v3_login()`, plus the constants `ORG` and `HOST`. The org comes from an env var (for example `IDMC_ORG`), else the first word of a switch file, else a safe default; each org has its own creds file, session cache and login host. Moving a whole host to another org is then one write to the switch file plus remapped id files; a single cron job can stay pinned to the old org by setting the env var on its line, and scripts that must only ever touch one org assert `ORG` at import time.

### L-METHOD-003  Cache the session for at most 25 minutes and log in again exactly once on a 401
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** Stable across the host tooling and a full org-to-org migration; the absolute 30-minute death was observed repeatedly · **Supersedes:** L-METHOD-099
The v2 `icSessionId` (and any JWT minted from it) dies about 30 minutes after it is granted, whatever the activity. Cache `{sid, serverUrl, orgId, t}` in a 0600 file and log in again when the cache is older than 1500 s (one helper refreshes at 24 min); keep a separate cache for the v3 `sessionId` used by catalog, profiling and MCP-management calls. On an API 401, delete the cache and log in exactly once more, then return the error. A long-running service does the same in memory.

### L-METHOD-004  Lockout guard: serialize logins and block on a rejected login until the creds change
**Kind:** SECURITY · **Proven:** 2026-09-28 · **Evidence:** Mocked-network tests 11/11 for the host helper and 14/14 for the service: a rejected login followed by 10-20 attempts made 0 network calls; a 503 did not block
Take an exclusive `fcntl.flock` on a lock file before logging in, then re-check the session cache (another process may just have logged in). If the server rejects the login (HTTP 4xx other than 429), write a block file holding the SHA-256 fingerprint of the creds file; while the fingerprint still matches, every process refuses to log in ("fix the creds or delete the block file"). 5xx and 429 do not block. A long-running service whose scheduler ticks every few seconds pauses logins for hours after an auth rejection (for example 21,600 s) and for about 60 s after a transient failure, and shows the block on its health endpoint. A password-rotation script writes the new value in place, deletes the block file and the caches, and verifies with exactly one login.

### L-METHOD-005  Test login guards and patched services offline before deploying them
**Kind:** PROCESS · **Proven:** 2026-09-28 · **Evidence:** 11/11 cases for the org-aware helper and 14/14 for the staged service
Before deploying a login or lockout change, unit-test the helper against a fake `urlopen` (success, 401, 503, rejected logins) in a temporary HOME with fake creds files, and count the network calls. Run a patched service in a throwaway container built from the live image with `--network none` and a fake login server. Deploy only when every case passes.

### L-METHOD-006  The helper returns (status, body) and does not raise: check the status
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** Recorded as the known trip in a shared operations helper
A `call()` that returns `(HTTP status, parsed JSON or text)` for 2xx and error answers alike lets an error payload be read as data when the caller treats the return value as the body or ignores the status. Unpack the tuple and require the expected status before using the body; a small `body()` helper that raises on non-2xx removes the trap.

### L-METHOD-007  Derive every host from the login answer; never string-replace a pod literal
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** Stale builders after an org move still held the old pod's host literals and ids
Take the pod base from the v2 `serverUrl` or the v3 `products[].baseApiUrl` and derive service hosts from it, for example the CAI host by splitting the base host at the first dot (`<pod>-cai.<rest-of-host>`). Builders that computed the CAI host by replacing a pod literal (`"<pod1>.<dom1>"` to `"<pod1>-cai.<dom1>"`) silently stopped working when the org moved to another pod, and hard-coded hosts and ids in builders kept pointing at the old org after a migration. The login host is the domain host `https://<domain>.informaticacloud.com`, never the pod host.

### L-METHOD-008  Establish the org first, and make destructive scripts prove it from a live read
**Kind:** LAW · **Proven:** 2026-09-28 · **Evidence:** An owner asked which org a cleanup was deleting from; the live read answered it
At the start of every session derive the org name, both org-id shapes (6-character v2, 22-character v3), the pod, the domain label and the base URL from `POST https://<domain>.informaticacloud.com/saas/public/core/v3/login` (`products[].baseApiUrl`), `GET /api/v2/org` and `GET /api/v2/agent`; a proven row from one org or pod is not evidence for another. Before any delete or bulk write, assert the org from a live read (`GET /api/v2/org` must return the expected `id`), not from a variable, because the same script may run under the other org's switch file.

### L-METHOD-009  Address IDMC objects by id, never by name
**Kind:** LAW · **Proven:** 2026-09-28 · **Evidence:** Same-named tasks existed in unrelated older folders; a migration flip tool cross-checked 138 name/id pairs with 0 mismatches
Task, taskflow and connection names repeat across folders, projects and orgs, so resolve every object to its id and act on the id: v2 ids for `/api/v2/*`, the 22-character `frsGuid` for v3 and FRS calls. Resolve by path with `POST /public/core/v3/lookup {"objects":[{"path":"<project>/<folder>/<name>","type":"MTT"}]}` and require exactly one match; a v2 mapping task's v3 id is its `frsGuid`, which only the detail GET returns. In migrations and cleanups remap by id and block any file that would keep an unmapped id.

### L-METHOD-010  How a session changes a mapping task headless, end to end
**Kind:** PROCESS · **Proven:** 2026-09-29 · **Evidence:** The pattern behind every SQL change and the consolidation swap; parity diffs of 0 rows before switching
Back up first: the v2 task JSON, the old SQL as a file and a v3 export of the task. `GET /api/v2/mttask/<id>`, drop the read-only fields (`orgId`, `createTime`, `updateTime`, `createdBy`, `updatedBy`, `agentId` when retargeting, and each parameter `id`), change only the field you mean (for SQL, replace an anchor inside `$Source$.customQuery` after asserting it occurs exactly once), `POST /api/v2/mttask/<id>` and read the task back. Diff old and new SQL against current data in the warehouse before the live task runs it, then run with `POST /api/v2/job {"@type":"job","taskId":"<taskId>","taskType":"MTT"}` and poll `GET /api/v2/activity/activityLog?taskId=<taskId>&rowLimit=1` until the `runId` matches. Bigger changes go side by side (new folder, parity-only target, parity plus an idempotency double run) before any swap.

### L-METHOD-011  Where MCP fits: enumerate the real registry, then choose REST or MCP per call
**Kind:** PROCESS · **Proven:** 2026-09-23 · **Evidence:** An early 'most capabilities walled' verdict came from the two servers wired into a session; the full registry falsified several walls
MCP is a calling convention, not a network position: it never replaces a Secure Agent, never reaches a private database the agent cannot, and its backing calls still bill IPUs. Before calling anything MCP-walled, list the org's managed servers (`GET https://hdm.<domain>.informaticacloud.com/a2e-mcp-asset-mgmt-svc/api/v1/mcp-servers?type=MANAGED`; one org exposed 19 servers and about 140 tools) instead of reasoning from the servers wired into your session. Prefer REST for writes and for anything REST already does; use MCP where it adds something (lineage reads, fuzzy identity match, the hosted DQ agent on uploaded files, address verification) or as one uniform tool surface through a local gateway that holds a single OAuth client. Check which org and host a locally configured MCP server logs in to before trusting an empty answer: one local server was pointed at a different org and showed nothing.

### L-METHOD-012  Keep a GET-only probe harness and a dry-run ops script instead of one-off probes
**Kind:** RECIPE · **Proven:** 2026-07-26 · **Evidence:** The July endpoint corpus was built with such a harness; walked-back conclusions came from ad-hoc probes
Wrap preflight and probing in a script you keep: it logs in on every plane, is GET-only by default, gates writes behind an explicit flag (for example `--allow-write` for a create-and-delete round trip), offers `--dry-run` that prints a body without sending it, and encodes the traps once (bogus-twin fake-200 filter, empty-POST verb probe, per-agent health read instead of the runtime-environment list, the verified connection body). Re-run it and stamp `last_verified` before relying on a live row. Fresh one-off probes re-learn every trap.

### L-METHOD-013  Write-capable tooling: dry run by default, --execute to act, backup plus UNDO log plus manifest
**Kind:** PROCESS · **Proven:** 2026-09-28 · **Evidence:** The backup sets were used for a real flip-back and for several rollbacks
Scripts that change live systems run as a dry run unless `--execute` is given and print exactly what they would do. With `--execute` they first back each file or object up into a timestamped directory (preserving mode, so 0600 stays 0600), append one line per change to an UNDO log (`restore <backup> -> <path>` or `delete <path> (created)`), write a manifest, and offer `rollback --backup <ts>`. Cron changes are made by commenting lines out with a tag, so the undo is mechanical. For IDMC objects the backup is a v3 export package (undo = re-import with REUSE).

### L-METHOD-014  Patches are anchored and idempotent; prove a patch chain by re-running it on its own output
**Kind:** PROCESS · **Proven:** 2026-09-28 · **Evidence:** A 15-step chain was a byte-identical no-op on the live artifact after the fixes
Change live code and generated artifacts only by edits on exact anchors: skip when the new text is already present; otherwise require the anchor to occur exactly N times and fail with "file changed since the plan; re-read it" if it does not. When several patches rewrite one artifact, keep ONE canonical chain in a fixed order, add "also accept the later rewrite" markers, normalize encodings (CRLF, encoded newlines) before comparing, rename superseded scripts so nobody runs them, and prove the chain on a fresh download of the published artifact: every step must SKIP and the bytes must be identical. Fold the chain into the generator when you can.

### L-METHOD-015  After editing a safety switch, assert it actually changed
**Kind:** LAW · **Proven:** 2026-09-28 · **Evidence:** Validate ran as apply
A purge script's "validate" mode once ran as "apply" because a string replacement silently failed to match. After any edit to a dry-run/apply flag, a feature flag or a guard, read the new value back (or print it) and assert it before running the script.

### L-METHOD-016  Deploys export the current version, apply, verify and roll back in the same run
**Kind:** PROCESS · **Proven:** 2026-09-28 · **Evidence:** Name-rule redeploys of CAI processes ran this way
A deploy script exports the current version first (the undo), applies the change, runs the verification calls and restores the export automatically if any check fails, all in one run, so a failed deploy never waits for a human to notice. For IDMC design objects this is export, swap, import OVERWRITE, publish, verify or roll back.

### L-METHOD-017  Risky runtime behaviour goes behind env flags with an instant rollback
**Kind:** PROCESS · **Proven:** 2026-09-29 · **Evidence:** Staged execution switched on with a flag script; the rollback path was documented in the cutover report
New execution modes (staged instead of linear lanes, a new plan file, a coalescing knob) default to off in code and are switched by env vars. A small flag script edits the env file in place, waits until the service is idle, recreates only that container and prints the running value; `off` is the rollback and needs no rebuild. Never switch runtime flags in the middle of a run.

### L-METHOD-018  Rebuild a controller that starts its own jobs without a race
**Kind:** PROCESS · **Proven:** 2026-09-28 · **Evidence:** The flip waited for idle (0 s) and came up healthy
Build the new image while the old container keeps serving; poll its current-run endpoint until it reports idle (give up after about 15 minutes); then recreate at once, so no run can start between the idle check and the swap.

### L-METHOD-019  Single-writer locks for cron-driven runners, with real liveness checks
**Kind:** PROCESS · **Proven:** 2026-09-24 · **Evidence:** A recurring 409 on a dead run stopped after the liveness check
A runner that cron may start while an earlier run is still going takes a non-blocking exclusive lock (`fcntl.flock(fd, LOCK_EX | LOCK_NB)`) on a per-mode lock file and exits 0 with "another run holds the lock; skipping"; wrap long cron jobs in `flock -n` and `timeout` as well. A single-flight marker such as `state == RUNNING` jams forever when a run is killed, so record the pid and a heartbeat and treat a dead pid as free; `kill -0` also succeeds for a zombie (`<defunct>`), so check that `ps -o stat= -p <pid>` does not start with Z, and keep a manual finalize script as a fallback.

### L-METHOD-020  Keep one source of truth for builders, plans, id files and generated documents
**Kind:** GOTCHA · **Proven:** 2026-09-29 · **Evidence:** A diff of three builder copies showed divergent fixes; a hand edit to a generated skill was lost on rebuild
When the same generator lives in two or three directories, a fix lands in one copy and the others keep the bug (a deleted template reference, a missing lane, retired behaviour); plan files baked into an image and copied elsewhere drifted, and one copy still held the old org's ids after a migration. Keep one source per org and generate or symlink the rest, or at least diff the copies after every change. The same holds for generated documents and skills: edit the source, not the rendered copy, or the next build silently reverts the edit.

### L-METHOD-021  A tool call the user rejected may already have run: read back before reporting
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** 68 FRS deletes had already landed when a call was rejected mid-run
When a user interrupts or rejects a tool call, the request may already have reached the server. Before saying that nothing happened, read the affected objects back and report what actually changed.

### L-METHOD-022  Log every IDMC write in one central tracker with its id and exact undo
**Kind:** PROCESS · **Proven:** 2026-09-26 · **Evidence:** One central log served every session through a week of parallel work
Keep one tracker project as the single log of all IDMC activity and freeze older projects as read-only archives with cross-reference comments. Log each write with the object id and its exact undo, each wall with its exact call and date, and each probe with its cleanup. The actionable queue is open issues with no `blocked:*` label, and every blocked label names the human or gate it waits on. For writers that may re-run, embed a unique idempotency marker inside the comment body (the HTML), because some trackers regenerate the plain-text field on save.

### L-METHOD-023  Four evidence states are never merged: WORKS, DOC, REJECTED, UNTESTED
**Kind:** LAW · **Proven:** 2026-07-25 · **Evidence:** 569 of 830 endpoint-verb combinations were untested in the July corpus; earlier wrong calls traced to merging untested with rejected
WORKS = a live status code observed on a stated org and date ("proven as of <date>"). DOC = a named Informatica guide states it but nobody exercised it ("documented, unproven"; never report it as working). REJECTED = refused with a code (`405` = read-only at any permission level). UNTESTED = absent from all evidence: unknown, not unsupported. A blank or `--` cell means untested, not absent; `405` means absent. List every verified verb per endpoint and keep `untested: PUT, PATCH` apart from `rejected: PUT 405`. Never upgrade DOC to WORKS without a live response.

### L-METHOD-024  Bogus-twin every input you control, including error codes and 503s
**Kind:** LAW · **Proven:** 2026-07-26 · **Evidence:** Four artifact classes proven with twins
Probe a nonsense sibling next to the real input: the path (`/.../bogusZZZ`), the object name (`entity/ZZFAKEENTITY`), the host (an unroutable IP) and the error-producing route (`/api/v2/agent/bogusZZZ`). If the twin answers identically (the same zero-byte 200, 403, 500 or nginx 503), the response is an artifact and says nothing about the real input. Recorded artifacts: 403/500 router answers under `/api/v2/agent/*`; an MDM 403 that fires before the metadata lookup; nginx 503 on the `-apim` / `-apigw` hosts for every path; `error [error [null]]` from a connection test aimed at an unroutable host.

### L-METHOD-025  A 200 can be fake: never report a zero-byte 200 or a 200 that carries login HTML
**Kind:** LAW · **Proven:** 2026-07-26 · **Evidence:** Bogus-twin A/B on a real org; a record read reported as 200 was login HTML and fooled a slide and a first check
A `200` with `Content-Length: 0` and no `Content-Type` means a gateway routed the prefix and nothing is serving: `GET /data360/search/api/v99/bogusZZZ` also returned 200 with 0 bytes, while the control `GET /api/v2/bogusZZZnope` returned `404 "Resource not found"` (that plane is real). A `200` carrying the identity-service login page means the wrong plane or header, or a stale session. Assert on the body shape, not the status.

### L-METHOD-026  Read what kind of 404 it is before concluding anything
**Kind:** LAW · **Proven:** 2026-07-26 · **Evidence:** Status decoder plus ingestion-host and MDM-host probes
`404` with a JSON or text body usually means a wrong path or host: keep hunting (the most common false negative). `404` with an empty body, or `No static resource <path>`, means the route is absent. A typed product error inside a 404 (for example `DBMI_TASK_WAS_NOT_FOUND`) is a live handler answering a lookup. `403` and `405` point at a role gap or a read-only resource, never at entitlement. The MDM host returns `404 CMN00005` for bogus siblings too, so treat it as "no such route" unless a bogus twin differs.

### L-METHOD-027  There is no HEAD or OPTIONS: probe a write verb with an empty POST
**Kind:** LAW · **Proven:** 2026-07-26 · **Evidence:** How an ingestion task create, a reference-data search and a runtime-environment create were shown to exist
IDMC offers no preflight discovery. POST an empty body: `400` / `415` / `422` means the verb exists and the body is wrong; a `500` naming a null field (for example `Cannot invoke Object.getClass() because o is null`) means the handler parsed and ran; `405` means the verb does not exist. An empty body cannot create anything, so the probe is safe.

### L-METHOD-028  Vary the Content-Type before declaring an upload route absent
**Kind:** LAW · **Proven:** 2026-07-26 · **Evidence:** A four-encoding matrix on one org; a false 'the clone path is closed' conclusion had come from the JSON 404
A write route has two axes. On `POST /public/core/v3/import/package` one org answered `application/json` with `404 MigrationSvc_025`, `application/zip` and `application/octet-stream` with `415`, and `multipart/form-data` with `400 MigrationSvc_030` (handler reached). Try `application/json`, `multipart/form-data`, `application/zip` and `application/octet-stream`; only `405` on every encoding is a verdict. The JSON 404 is the dangerous cell because it reads as "wrong path".

### L-METHOD-029  Sweep the host family first; uniform 404 with no 405 means the route is absent
**Kind:** LAW · **Proven:** 2026-07-26 · **Evidence:** A DNS sweep found the ingestion service live on the -ing host after it had been recorded as UI-only; six MDM deploy shapes and twelve model-authoring shapes all gave 404 with no 405 · **Supersedes:** L-METHOD-097
IDMC fans services onto per-product hosts (`<pod>.<domain>` with `/saas`, `idmc-api.<domain>`, `cdgc-api.<domain>`, `hdm.<domain>`, `<pod>-cai`, `<pod>-mdm`, `<pod>-ing`, `<pod>-dqprofile`, `<pod>-dqcloud-api`), so resolve candidate hosts by DNS (free, no auth; a bogus suffix must not resolve) before believing any service-level 404. Then use 404 versus 405 as the stopping rule: any `405` means the route exists with the wrong verb (keep going); uniform `404` across many plausible shapes, each matching its bogus twin, means the route is absent (stop and design the click in).

### L-METHOD-030  Read back after every write; a 200 whose value reverts is a silent rejection
**Kind:** LAW · **Proven:** 2026-09-28 · **Evidence:** Read-backs caught reverted retargets, a 204 no-op PATCH and an empty-shell schedule GET
After every write, read the object back and compare the field you changed: a v2 `POST .../{id}` is checked with a `GET` of the same id (for example `scheduleId` after a bind); a v2 `DELETE` returns 200 and a read-back 403 means gone; a deleted schedule's GET returns an empty 200 shell, so check the list instead; FRS deletes report per item (`FRS_200` ok, `FRS_082` still published, `FRS_087` project not empty) and a read-back gives `FRS_070`; an FRS PATCH of `customAttributes` returned 204 and changed nothing. A `200` whose value reverts on read-back (a mapping-task connection retarget across connector types did this) is a silent rejection.

### L-METHOD-031  POST to start, GET to poll, and read per-item status inside a 200 envelope
**Kind:** LAW · **Proven:** 2026-07-26 · **Evidence:** The pattern behind every headless win in the corpus
Scans, CAI publish, migration export and import, metering export and MDM jobs work the same way: a `201` / `202` with a job id is success of the submission, not of the work. Poll the job (a `GET` on the starter path returns 405 by design). Items can fail inside a `200` envelope (CAI publish `itemDetail[].itemState`, catalog `207 Multi-Status`, import per-object states), so read every item before reporting.

### L-METHOD-032  A verb census is a dated snapshot: PUT is proven on runtime-environment selections
**Kind:** OVERTURNED · **Proven:** 2026-09-28 · **Evidence:** Service and connector selections changed and read back over PUT; July census had counted PUT 0 proven / 14 documented / 12 rejected / 140 untested · **Supersedes:** L-METHOD-096
`PUT /runtime/api/v2/runtimeEnvironment/<reId>/selections/ui` on the pod host with `IDS-SESSION-ID` (the v2 session) works, so "no PUT anywhere in IDMC" is false. The practical idiom still holds for most resources: on the v2 plane `POST /api/v2/<resource>/{id}` with the full GET body is the update; elsewhere DELETE and re-POST; any documented PUT or PATCH stays unproven until a live call succeeds. Treat every verb census as dated: DELETEs on six v2 resources, FRS deletes and v3 user deletes were also proven after the July count.

### L-METHOD-033  Entitlement comes from deployed engines, privileges and selections, never from products[] or a 404
**Kind:** LAW · **Proven:** 2026-09-24 · **Evidence:** About 90 issues had been falsely escalated as buy-a-licence in one program; in another, 'no catalog entitlement' fell when catalog sources, scans and a glossary were created headless · **Supersedes:** L-METHOD-102
Never conclude a capability is unlicensed from a REST probe or from the login `products[]` list, which is a launcher label (orgs that listed only "Integration Cloud" held catalog, CAI and ingestion capabilities). Read the engines on each agent (`GET /api/v2/agent/details/<agentId>`: `agentEngines[].appname` and `agentEngineStatus.status`), the privileges from the identity-service login, the runtime-environment service selections, and whether a real create call validates. With no agent installed, entitlement is unresolved, not disproven.

### L-METHOD-034  Search the existing evidence before calling anything a wall
**Kind:** LAW · **Proven:** 2026-07-26 · **Evidence:** Incident reconstructed from session history
Before concluding "not possible" or "not entitled", grep the KB's evidence, section content and endpoint-verb matrix for the endpoint and for the exact error string. The canonical failure: a session got `403 APP_10519` creating a PostgreSQL connection with `type: "PostgreSQL"`, swept 13 spellings and recommended a licensing ticket, while the verified body (`type: "TOOLKIT_CCI"`, connector name in `instanceName`) was already on disk and the org held hundreds of licences.

### L-METHOD-035  Date every wall and re-test it when anything changes
**Kind:** LAW · **Proven:** 2026-09-28 · **Evidence:** At least six verdicts overturned between 2026-09-20 and 2026-09-28
IDMC verdicts flipped repeatedly within days (authoring UI-only, connector enablement UI-only, catalog unentitled, CDC deploy UI-only, CAI publish needs a designer Save); in one July corpus live verdicts flipped on a 3-5 day cadence. Record each wall with the exact verb, host, path, headers, body shape, error code, org and date, and re-probe when the agent build, pod, header, path, content type or available tools change. Do not re-grind a wall without a new angle, and prefer "let me verify on your org" over quoting a dated row to a customer.

### L-METHOD-036  Say the right kind of no: six headless verdicts and four kinds of cannot
**Kind:** DECISION · **Proven:** 2026-07-26 · **Evidence:** Decision guide of the reference corpus
Use HEADLESS (a live status proved it), HEADLESS-DOC (documented, unexercised), NEEDS SHELL (no browser, but a host shell: agent install, driver staging), UI-ONLY (licensed and working; a human clicks), UNTESTED (unknown) and WRONG-HOST RISK (recorded absent, host family never swept). Classify every "cannot" as a hard wall (empty-body 404 or 405 on every verb: design a click in), a read-only resource (405 on this verb: use the update idiom), not on this host (404 with a body: try the other host) or nobody checked (never quote it as a limit). Commercially, UI-ONLY (one click in something the customer already owns) and GAP (not there) must never be confused.

### L-METHOD-037  The wall is usually a UI-only final step or a gate, rarely licensing
**Kind:** LAW · **Proven:** 2026-07-08 · **Evidence:** Of 44 catalogued walls in one program almost none were licensing; many September 'UI-only' steps later proved headless
When a capability looks blocked, assume first that reads and runs work and the missing piece is a UI-only final action (a publish, a deploy, an accept), a spend gate or a production-cutover gate. Prepare everything headless up to that step (specs, worklists, clones), hand over one precise UI step, and later re-test the step's headless route by capturing the UI's own API call. Keep purchase conversations for engines genuinely absent from every agent.

### L-METHOD-038  Suspect your own input first: walls that were operator errors
**Kind:** GOTCHA · **Proven:** 2026-09-24 · **Evidence:** Each reached a written verdict before being walked back · **Supersedes:** L-METHOD-101
Several written "walls" were inputs. `IDS_085` came from a truncated username or the wrong login domain, not a lockout. A v3 scan found "0 objects" because the type filter was wrong (`type=='DBMI'` returns 0 while the type is `DBMI_TASK`) and the objects sat in another user's project. A CAI publish `BAD_REQUEST "Invalid asset path"` came from the path format (`Explore/<project>/<folder>/<name>.PROCESS.xml` works). A 404 came from the wrong Content-Type. Before escalating, re-check host, full username, exact type names, path format and encoding, and remember that the v3 `q` type filter is not validated.

### L-METHOD-039  Report stage by stage: authored, deployed, running, integrated; never round up
**Kind:** LAW · **Proven:** 2026-09-23 · **Evidence:** An acceptance bar of 'CAI, CDI and DQ actually integrated into each application' was met only when the apps consumed IDMC outputs
Say exactly which stage is proven. Authored (a design object exists) is not deployed (published or deployed to a runtime), deployed is not running (a run completed with rows), and running is not integrated (the live application reads IDMC-produced data, reacts to a CAI decision or shows DQ results). Use three tiers: built in (out of the box), built with IDMC assets and proven (deployed asset plus successful runs, checked in the live org before you claim it), and buildable in IDMC but not yet built. Reserve 'DIY' for code that runs outside IDMC (Python, Cypher, shell). Read back the live org before rating, because 'proven' needs a deployed asset and runs.

### L-METHOD-162  Three-tier MCP tool design: read, preview-then-confirm write, destructive with a resolved preview
**Kind:** PATTERN · **Reported:** 2026-11-19 · **Evidence:** Public third-party code read 2026-11-19 (confidence high: code plus its tests, change notes or live-check notes); not probed here
Write tools return a preview (per field current vs proposed, or the resolved name and status of every run they would kill) unless `confirm=true`, so exploration never changes production. Docstrings are the contract the model reads: state the blast radius, say where each id legally comes from (v3 federated id vs v2 id), and keep the order of operation in the module and tool docstrings. A stale docstring (resume said 'SUSPENDED or FAILED') counts as a bug. Delete tools that duplicate a push signal. Audit the principle against the code: here `run_mapping_task` was the one ungated write, and the README lists it as a defect. Refines L-METHOD-013.

### L-METHOD-163  Keep secrets out of the chat: server-side plan files, name assertions and recursive masking
**Kind:** SECURITY · **Reported:** 2026-11-19 · **Evidence:** Public third-party code read 2026-11-19 (confidence high: code plus its tests, change notes or live-check notes); not probed here
Credential or auth changes are read from a plan file on the server (`{connections:[{connection_id, expect_name, updates, role}]}`), so secrets never pass through the transcript. Each entry applies only if the live connection name equals `expect_name`. Placeholder entries (FILL_ME) are skipped. Every value whose key contains password, pwd, secret, token or passphrase is masked recursively in tool output ('***set***'). The opposite anti-pattern, seen in another server: a login tool that takes the password as a tool argument.

### L-METHOD-164  Do not front a write-capable IDMC MCP with an unattended claude -p --dangerously-skip-permissions bot
**Kind:** SECURITY · **Reported:** 2026-11-19 · **Evidence:** Public third-party code read 2026-11-19 (confidence high: code plus its tests, change notes or live-check notes); not probed here
A Slack Socket Mode bot passed every channel message to `claude -p <msg> --mcp-config <cfg> --dangerously-skip-permissions`. The MCP config exposes create, update and delete for CDGC assets, catalog sources and marketplace objects. Any channel member, or text injected into a catalog description the model reads, can then trigger writes with no approval. ### L-METHOD-165  Pin a server to one project: allowlist by v3 location and return the API chain it ran
**Kind:** PATTERN · **Reported:** 2026-11-19 · **Evidence:** Public third-party code read 2026-11-19 (confidence low: a comment or README claim); not probed here
A server fixed to one project through an env variable lists `type=='TASKFLOW' and location=='<project>'` through v3 objects. ### L-METHOD-166  Catalog discovery round model: parallel searches, then details with a fast or slow path
**Kind:** PATTERN · **Documented:** 2026-11-19 · **Evidence:** The vendor's own Claude plugin skill, read 2026-11-19; not probed here
Round 1 issues the topic search and every dimensional or fiscal term search in parallel. If Round 1 already returned the column UUIDs you need, Round 2 runs the parent's details (hierarchy, selfAttributes, dataClassification, stakeholdership) and the per-column glossary checks together (2 rounds). Otherwise Round 2 fetches hierarchy, and Round 3 runs the glossary checks on the UUIDs it returned (3 rounds). Never re-search for a column the hierarchy already listed, and batch segments into one call per asset. Budgets per intent run from 0-1 calls (FRESHNESS, COMPLIANCE_FLAG) to 3-5 (BROAD_DISCOVERY, up to 10 on a first-turn fitness prompt).

### L-METHOD-167  Vendor answer format: verdict first, then evidence, gaps table and next actions
**Kind:** PATTERN · **Documented:** 2026-11-19 · **Evidence:** The vendor's own Claude plugin skill, read 2026-11-19; not probed here
Each answer has four parts in order: Verdict (plain conclusion with warnings, never 'I searched and found...'), Evidence and decision parameters (assets examined, rules applied, winners and rejects, tables), Gaps (type, asset/field, detail, severity) and Next actions (user steps plus steward-side curation asks). Use asset names, not UUIDs, and translate classType to plain language. For audit packs, cover every area briefly (source, definitions, PII, data-subject rights, policy, ownership, lineage, gaps) before going deep.

### L-METHOD-168  Intent taxonomy: 15 catalog intents with routing and per-intent call budgets
**Kind:** PATTERN · **Documented:** 2026-11-19 · **Evidence:** The vendor's own Claude plugin skill, read 2026-11-19; not probed here
Intents: BROAD_DISCOVERY, AUTHORITY_COMPARE, FIELD_MEANING, FIELD_RELIABILITY (a named field), TRUST_ASSESSMENT (a dataset), FRESHNESS, RELATIONSHIPS, IMPACT_ANALYSIS, PROVENANCE, ROOT_CAUSE, OWNERSHIP, SENSITIVITY, POLICY, SAFE_USAGE and COMPLIANCE_FLAG, each with signal words and a disambiguator. Route one intent directly, two intents both (primary first), zero or three-plus by signal score with BROAD_DISCOVERY as fallback; skip search when the prompt references assets already in state. Keep a discovery state (scope, assets with UUIDs, facts, gaps, relationships) and never re-fetch a stored UUID.

### L-METHOD-169  Delegate only fully-specified catalog calls to smaller models
**Kind:** PATTERN · **Documented:** 2026-11-19 · **Evidence:** The vendor's own Claude plugin skill, read 2026-11-19; not probed here
Keep intent classification, synthesis, trust scoring, root cause and the final answer in the main model. Delegate single search/details calls with fully determined parameters to a small model, and multi-step chains that need interpretation between steps to a mid model; skip delegation entirely in short conversations (1-2 turns, 1-2 calls).

### L-METHOD-170  Community CDGC scripts that phone home: grep for outbound telemetry before running
**Kind:** GOTCHA · **Reported:** 2026-11-19 · **Evidence:** Public third-party code read 2026-11-19 (confidence high: code plus its tests, change notes or live-check notes); not probed here
Several public CDGC utility scripts from one author send an infaLog 'phone home' POST to a third-party workers.dev endpoint with a hard-coded X-Auth-Key, including the org id or user name, the pod URL, the script version and the machine hostname, on every login. Before running any community IDMC script, grep it for requests to hosts other than *.informaticacloud.com (workers.dev, webhook, telemetry, X-Auth-Key) and strip them. Credentials were not seen in the payload. Refines L-MCP-124.

## Superseded / overturned (kept so nobody re-learns them)

### L-METHOD-096  Zero PUT is proven anywhere in IDMC; never design on PUT, overturned 2026-09-28
**Was believed:** 2026-07-25 to 2026-09-27 · **Overturned by:** L-METHOD-032
The July census counted PUT at 0 proven / 14 documented / 12 rejected / 140 untested across 166 endpoints and concluded that every update is `POST /{id}` on the v2 plane or DELETE plus re-POST. A PUT on runtime-environment selections was proven on 2026-09-28; the update idiom still holds for most resources.

### L-METHOD-097  A documented path that returns 404 means the capability is absent or unlicensed, overturned 2026-07-26
**Was believed:** to 2026-07-25 · **Overturned by:** L-METHOD-029
Service-level 404s were read as absence without retrying on unlisted hosts. A free DNS sweep of the host family found the ingestion service live on the `-ing` host, which turned a whole-product "UI-only" verdict into a wrong-host error.

### L-METHOD-098  IDMC lets you read almost everything, run almost everything and design almost nothing, overturned 2026-09-29
**Was believed:** 2026-07-13 to 2026-09-22 · **Overturned by:** L-METHOD-093
The July core insight: design-time authoring, publish and deploy had no REST verb except cloning. September evidence moved most of it: migration clones authored ingestion and CAI objects (09-22), CAI publish and ingestion create/deploy/start went over REST (09-25 to 09-28), glossary writes, deletes and a PUT on service selections worked (09-28), and multi-transformation mappings were imported as IMF JSON (09-29). Still standing in these sources: MDM model deploy, CDQ rule logic, classification accept, CAI API activate.

### L-METHOD-099  The session cache can assume a 30-minute idle timeout, overturned 2026-09-28
**Was believed:** 2026-06 to 2026-07 · **Overturned by:** L-METHOD-003
Early helpers treated the IDMC session as expiring after 30 minutes of inactivity. The v2 session dies about 30 minutes after it is granted, whatever the activity, so a cache must refresh by age (at most 25 minutes).

### L-METHOD-100  Claim protocol v1: a wip label plus a self-expiring claim comment, overturned 2026-07-05
**Was believed:** 2026-07-04 · **Overturned by:** L-METHOD-064
A claim moved the issue to In Progress, added a `wip:<agent>` label and posted an `[[AGENTCLAIM agent=<a> exp=<isoZ>]]` comment with a 45-minute TTL, released by a sign-out command and a reaper cron. It coexisted with two other schemes, which caused double claims and a reaper that could not see foreign leases.

### L-METHOD-101  Clone-authored design objects do not persist in a shared org, overturned 2026-09-24
**Was believed:** 2026-09-23 to 2026-09-25 · **Overturned by:** L-METHOD-038
A read-only v3 scan found none of the objects authored by migration clones the day before and concluded they had been removed. The scan used the wrong type name (`DBMI` instead of `DBMI_TASK`, which returns 0 rather than an error) and missed objects sitting in another user's project.

### L-METHOD-102  An org whose login lists only Integration Cloud has no catalog or CAI entitlement, overturned 2026-09-24
**Was believed:** 2026-09-21 to 2026-09-22 · **Overturned by:** L-METHOD-033
Plans in one program marked catalog and MDM work "entitlement-blocked" because the login `products[]` showed only Integration Cloud. Runtime-environment selections showed CAI, ingestion and catalog enabled, and catalog sources, scans and a glossary were then created headless.

### L-METHOD-103  July open questions that must not be asserted to a customer, overturned 2026-09-28
**Was believed:** 2026-07-25 · **Overturned by:** L-METHOD-011, L-METHOD-035
In July these were open: MDM read-by-id (200 versus 404), CLAIRE GPT and AI Agent Engineering entitlement, the taskflow publish route and the API developer-portal gap. ## Other general lessons (not IDMC-specific)

Kept short: these came from the same sessions but concern app code, QA harnesses, BI tools, office documents or desktop housekeeping rather than IDMC.

### L-METHOD-104  QA suites: deterministic, hermetic and never weakened
**Kind:** PROCESS · **Proven:** 2026-10-01 · **Evidence:** Three consecutive clean runs with residue=0 verified; story suites over three channels with per-record traces and net-zero purges (2026-09-29 to 2026-10-01)
Tests create their own data and delete it at teardown, with the cleanup lane proving residue=0 on every surface the suite writes (app database, identity provider, warehouse after a full resync, object store, mail catcher). Accept "passes every time" only after three consecutive clean full runs with root causes of nondeterminism removed first. Fix the application, never widen an assertion to pass; separate harness bugs from product-behaviour deltas and route the latter to a product decision; a run-everything button is aggregation of existing runners, not new tests; gate test fixtures out of transforms; promote critical watched behaviour into assertions; put a fail-closed guard in front of any test that can hit production (unknown environment = production, live payment keys refused, dry run by default); prove backup and restore before any destructive pass. For an IDMC-backed application, create test identities in a run-specific namespace (for example `qa.<run>.<n>@example.com`) and drive the real public endpoints on every channel. Before cleaning up, run a read-only trace for the namespace that prints, per source row, the event time, the CDC landing lag (APPENDS), the IDMC landing task and time, the golden-table appearance, the CRM record id and the BI publish time, so every hop is proven per record (one story: 18 of 18 rows reached CDC at a median 33.5 s and the landing tables, 11 of 11 the curated tables). Then purge net-zero on every surface with a script that refuses any pattern outside the namespace and dry-runs by default: application tables in foreign-key order, the identity provider, the mail catcher, the CRM (contacts and children by external id, then empty the recycle bin), while source deletes flow through CDC (L-DBMI-026). Budget IDMC jobs per story and read the job budget before and after (L-IPU-058).

### L-METHOD-105  Reorganizing files while other sessions run
**Kind:** GOTCHA · **Proven:** 2026-07-17 · **Evidence:** Five same-day reorg archives and a file moved mid-operation by a parallel session
Several sessions reorganizing the same tree race, lose moves and write contradictory maps and undo logs: check for other active sessions and recent archive folders first, prefer additive work, and keep fixes surgical. Many files are outputs of generators with hard-coded paths (move the generator's target, not just the file), and apparent duplicates may be builder inputs. When the tree is not fully tracked by git, a reversible undo log (one line per move) is the only undo path.

### L-METHOD-106  Workbooks generated by code
**Kind:** GOTCHA · **Proven:** 2026-09-11 · **Evidence:** An unopenable workbook fixed by rewording one cell; blank formula cells filled after COM recalc
openpyxl stores any text starting with `=` as a formula: a label becomes `#NAME?`, and a prose note can make Excel refuse to open the file (`0x800A03EC`, even with repair) while openpyxl still loads it; never start text with `=` or force text format. openpyxl writes formulas without cached values: open the file through COM with a fresh instance (`DispatchEx`), run `CalculateFull()`, save, and scan for error values before sharing.

### L-METHOD-107  Customer decks: reuse native slides and edit only the words
**Kind:** RECIPE · **Proven:** 2026-07-29 · **Evidence:** A rejected deck redone from native slides
Hand-built shapes read as machine-generated. Render the best-matching branded deck to images, import its native slides through PowerPoint COM copy and paste (keeps masters, fonts, native tables and logos), change only the text runs with python-pptx, reshape native tables rather than drawing new ones, and drop the wrong customer logo.

### L-METHOD-108  BI and dashboard verification traps
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** A false 'broken histogram' disproved by reading the image; alert storms quieted at the root
A PDF export's text layer can list bar-chart values in reverse order and hide clipped text: rasterize the page and read the image. "One dashboard per area with drill-down" means collapsible rows in one dashboard, not a folder of linked dashboards. Retire an old dashboard stack additively (panel-by-panel parity port, relabel, redirect, keep the old one until the owner approves). Stop alert spam at the root (dead collectors, SLAs aligned with real cadence, empty-by-design sources classified as no-activity, every alert channel found). Publish a freshness contract per catalog aspect so no one treats a catalog as a live data source.

### L-METHOD-109  Code-edit traps
**Kind:** GOTCHA · **Proven:** 2026-07-09 · **Evidence:** A route restored and 142 tests passing; a false 'live shadow' flag cleared
Inserting a helper between a decorator and its `def` binds the decorator to the helper and silently unregisters the original route; anchor edits on the decorator plus def as one unit. A gate that decides a legacy script is live by substring-matching a marker string also flags a retired file that only mentions the marker in a comment: match the activation, not the string.

### L-METHOD-110  Rewrite synthetic history consistently
**Kind:** RECIPE · **Proven:** 2026-09-28 · **Evidence:** 0 payment/order mismatches and balanced ledgers after re-pricing 514 rows
When a synthetic-data generator's rule was wrong and history must be corrected, regenerate the affected rows with the generator's current rule seeded by the row id (deterministic), update every linked record (payments, ledger pairs) in the same transaction, keep status, timestamps and keys unchanged, take a dump and an undo SQL first, and verify the reconciliations (payments equal ledger, debits equal credits) afterwards.

### L-METHOD-111  Patch generated queries with a marked wrapper, not by editing strings other patch steps anchor on
**Kind:** PATTERN · **Proven:** 2026-09-30 · **Evidence:** 2 earlier steps aborted after a text edit; fixed by acceptance markers; wrappers never broke an anchor
When a chain of idempotent patch scripts edits the same generated artefact, a later step that rewrites an earlier step's REPLACEMENT text makes the earlier step abort on the next run ('anchor found 0 times'), so a keeper that re-applies the chain raises an alert. Prefer a wrapper that leaves the inner text intact: `/* marker */ select o.* replace (<new expr> as col) from (/*i*/ <original> /*i*/) o`, re-built from the inner text on every run. When a later text edit is unavoidable, teach the earlier step to accept the new text as 'already applied'. A step that must CHANGE text it wrote before needs in-place old-to-new edits; 'exists, so SKIP' never updates. Always prove: the chain on the live artefact gives 0 aborts and output identical to input.

### L-METHOD-112  A remote-exec helper that retries on missing output re-runs non-idempotent commands; background jobs must be detached
**Kind:** GOTCHA · **Proven:** 2026-09-30 · **Evidence:** a duplicate build started 11 s after the first; killed before its publish step
A helper that runs a command over a tunnel and retries up to three times when it sees no result marker re-ran a whole command that had started a publish build, so the build ran twice. For anything that is not idempotent: call with a single attempt, start long jobs with `setsid nohup ... < /dev/null &` so they never hold the helper's pipe, and read their log in a separate call.

### L-METHOD-113  `pkill -f <pattern>` in a remote command kills its own shell; a local file named like a stdlib module shadows it
**Kind:** GOTCHA · **Proven:** 2026-09-30 · **Evidence:** silent empty output twice; 'xml' shadowing reproduced; /tmp empty after a resize reboot
A command line that contains the pattern it passes to `pkill -f` (or to a grep feeding kill) matches itself, so the shell dies and the rest of the command never runs, with no output. Kill by PID or with a pattern the command line cannot contain (for example `[w]orker_`). Separately, a helper script saved as `xml.py` in a folder shadows the standard `xml` package for every script run from that folder (ModuleNotFoundError: 'xml' is not a package). A VM reboot clears /tmp, so staged work files there vanish.

### L-METHOD-114  Two consumers of one lock with different freshness thresholds: back-date the lock to release only the looser one
**Kind:** PATTERN · **Proven:** 2026-09-30 · **Evidence:** rebuilder ran at +10 min with a back-dated lock; keeper logged 'fresh lock' until removal
When a publish lock is honoured by a keeper (blocks if the lock is under 60 min old) and by an extract rebuilder (blocks under 30 min), setting the lock's mtime to 31 minutes ago lets the rebuilder run while the keeper stays blocked. Useful to let a downstream copy follow while the upstream is still being republished. Remove the lock when done.

### L-METHOD-115  Validate a big dashboard change with a pruned throwaway workbook before the slow main publish
**Kind:** PATTERN · **Proven:** 2026-09-30 · **Evidence:** 400011 caught by the throwaway; 19 tabs audited in one session
Prune the dashboard being changed into its own small workbook, publish it under a '(delete me)' name (about 4 minutes), render it headless, then publish the main workbook (15-20 minutes) and delete the throwaway. A publish error or a layout problem shows up in minutes instead of after a full cycle. To audit every tab of a slow workbook, open it once and switch tabs with the Embedding API (`workbook.activateSheetAsync`): one cold start instead of one per tab.

### L-METHOD-116  An executive-grade addition per dashboard section: one live number that ties to the tile beside it
**Kind:** PATTERN · **Proven:** 2026-09-30 · **Evidence:** 8 additions verified against their tiles
What lands with executives is one number per section, stated as money, time or risk, computed live from the same SQL as the tile next to it (embed the tile's own query at patch time so the numbers cannot drift): revenue run-rate, share of calls served without error, hours of manual clean-up the automatic fixes saved, what the AI catalogued by itself, upside of converting a list, seconds from sign-up to CRM contact, total value in play across the decisions, and concentration of spend. Avoid period trends when the history is short or the data-generation cadence changed; say what each assumption is (for example 3 minutes per manual fix).

### L-METHOD-118  Browser checks read CSS-transformed text: compare case-insensitively
**Kind:** GOTCHA · **Proven:** 2026-09-30 · **Evidence:** two false FAILs on correct pages, confirmed by their screenshots (2026-09-30)
Playwright's `inner_text` returns the text as rendered, so a heading or label styled `text-transform: uppercase` comes back upper-cased and an exact-case check fails on a correct page. Normalise case and whitespace before comparing, and look at the screenshot before calling a UI check a defect.
