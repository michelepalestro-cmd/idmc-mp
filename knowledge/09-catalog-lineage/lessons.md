## Current

### L-CDGC-001  Mint the CDGC Bearer JWT from the identity service with client_id=cdlg_app
**Kind:** ROUTE · **Proven:** 2026-09-29 · **Evidence:** Every catalog-source, glossary, link and scan call of a two-org rebuild used it (200s); search with it returned 5,089 assets
`POST https://<domain>.informaticacloud.com/identity-service/api/v1/jwt/Token?client_id=cdlg_app&nonce=<random>&access_code=` with headers `IDS-SESSION-ID: <sessionId>` and `Cookie: USER_SESSION=<sessionId>` and an empty body returns `{"jwt_token": "..."}` (about 2,100 characters). The session id is the v3 login `userInfo.sessionId` (or the identity-service `Login` sessionId). A JWT lives 30 minutes from grant while the identity session lasts hours, so cache the JWT for about 20 minutes and re-mint it on any 401. A GET form (`?client_id=<id>&nonce=<uuid>` with `IDS-SESSION-ID`) is also recorded; `client_id=idmc_api` is the value used for managed MCP servers.

### L-CDGC-002  Send the three identity headers on every CDGC call
**Kind:** LAW · **Proven:** 2026-09-29 · **Evidence:** Bearer-only run = 500; with the three headers = 201 + jobId; creates validated only with IDS-SESSION-ID
CDGC routes sit behind `ccgf-auth-pep`. Send `Authorization: Bearer <jwt>`, `IDS-SESSION-ID: <sessionId>` and `X-INFA-ORG-ID: <orgIdV3>` (plus `Content-Type`/`Accept: application/json`) on every call; search also needs `X-INFA-SEARCH-LANGUAGE: elasticsearch`. Some GETs tolerate Bearer only, but runs, creates and updates do not: a missing header shows up as 401, as 500 "Login sessionID is missing" from ccgf-auth-pep (or 406) on a scan run, or as a runtime-environment validation failure on catalog-source create (Informatica KB 000221244).

### L-CDGC-003  A helper that sends only the v3 session header gets 401 on data360
**Kind:** GOTCHA · **Proven:** 2026-06-28 · **Evidence:** 401 through the generic helper vs 201 through the CDGC helper on the same run call
Calling data360 through a generic helper that sends only `INFA-SESSION-ID` returned 401, while the same call with the minted Bearer JWT plus `IDS-SESSION-ID` and `X-INFA-ORG-ID` succeeded. Route every data360/ccgf call through one CDGC auth helper that owns the JWT cache.

### L-CDGC-004  With JWT-on-login enabled, the v3 sessionId itself can serve as the CDGC Bearer
**Kind:** RECIPE · **Proven:** 2026-08-20 · **Evidence:** sessionId began with ey and was accepted by CDGC GETs (2026-06-27) and by reads plus publish writes (2026-08-20)
When Administrator > Authentication sets the org's authentication type to JWT, `POST /saas/public/core/v3/login` returns a JWT in `userInfo.sessionId` (starts with `ey`, about 1,700 characters). CDGC accepted that value as `Authorization: Bearer` (with the same value in `IDS-SESSION-ID` and the org id in `X-INFA-ORG-ID`) for reads and for content/publish writes. Where the org is not on JWT-on-login, mint the Bearer through `jwt/Token` (L-CDGC-001).

### L-CDGC-005  Host map: which CDGC plane answers on which host
**Kind:** OVERTURNED · **Proven:** 2026-09-29 · **Supersedes:** L-CDGC-137 · **Evidence:** 200/201/207 per route between 2026-06-28 and 2026-09-29; DNS failure for <pod>-cdgc (2026-07-26)
`idmc-api.<domain>.informaticacloud.com` serves `/data360/search/api/v1/search`, `/data360/search/v1/assets...`, `/data360/content/v1/assets...`, `/data360/executable/v1/...`, `/data360/observable/...`, `/data360/catalog-source-management/v1/...` and `/data360/marketplace/api/v1|v2/...`. `cdgc-api.<domain>.informaticacloud.com` serves `/ccgf-catalog-source-management/api/v1/datasources...`, `/ccgf-contentv2/api/v1/publish`, `/ccgf-searchv2/api/v1/search` and `/cdmp-marketplace/api/v1/provisioning/*` (the executable run path and Marketplace dataAssets also answered there). `ccgf-api.<domain>.informaticacloud.com` served `/ccgf-orchestration-management-api-server/...` to a browser session. `<pod>-cdgc.<domain>` has no DNS, and the platform pod host does not serve data360: a 404 there is a wrong-host result, not a missing feature.

### L-CDGC-006  Zero-byte or twin-identical 200s on data360 are gateway artifacts, not a capability or licence verdict
**Kind:** OVERTURNED · **Proven:** 2026-07-27 · **Supersedes:** L-CDGC-130 · **Evidence:** Five hypotheses tested live (verb, host, header set, entitlement, path); bogus twins identical across 9 combinations
On some orgs every `data360/*` and `cdmp-marketplace/*` path answers 200 with `Content-Length: 0` and no Content-Type, and a bogus twin path gets a byte-identical 200. That proves nothing: the plane is only partially mounted (some paths 404, others zero-byte 200). Run a bogus-twin control on every data360 probe and assert on body shape. In the observed case the org held CDGC privileges, so it was a deployment question, not an entitlement ticket; `cdgc-api` of another domain answered a clean 401 to the foreign-org token, which proves that route is real elsewhere.

### L-CDGC-007  CDGC entitlement truth: RE services, agent engines, privileges and a real create, never products[] or guessed 404s
**Kind:** OVERTURNED · **Proven:** 2026-09-28 · **Supersedes:** L-CDGC-129 · **Evidence:** Catalog sources created and scans COMPLETED, glossary written, on an org whose login listed only Integration Cloud
Do not conclude CDGC is unavailable from the login `products[]` list (it often shows only "Integration Cloud") or from 404s on guessed paths. Check the runtime environment's service selections (`Data Governance and Catalog` enabled:true in `GET .../runtime/api/v2/runtimeEnvironment/<reId>/selections/ui`), the agent engines `Metadata_Platform_Service` and `Metadata_Foundation_Agent` RUNNING (`GET /api/v2/agent/details/<agentId>`), privileges such as `create.mcp.CatalogSourceConfiguration`, `execute.mcp.CatalogSourceConfiguration` and `create.PROFILE` with the Governance Owner/Administrator roles, and whether a real catalog-source create validates. An empty catalog means unpopulated, not unentitled.

### L-CDGC-008  Roles for one login that delivers CDI, CAI, CDQ, CDGC and CLAIRE work
**Kind:** RECIPE · **Proven:** 2026-09-24 · **Evidence:** Runbook prerequisite for repeating a full build in a new org; UI playbook
A login that drives governance and CLAIRE as well as integration needs Admin, Designer, Governance Administrator and CLAIRE GPT User. In the UI the stakeholder picker stays empty unless the governance roles (Data Owner, Data Steward) are populated in Administrator first.

### L-CDGC-009  Governance is org-scoped, not runtime-environment-scoped
**Kind:** LAW · **Proven:** 2026-07-06 · **Evidence:** Live probe: identical governance objects across two REs of one org; the governance diff was empty
Catalog sources, the published glossary, CLAIRE classifications, DQ rules and the MDM model belong to the org. Two runtime environments in one org share one governance layer by construction; only RE-bound objects (agents, per-environment connections, task sets) and the warehouse each catalog source targets differ. Isolating governance between environments needs a second org.

### L-CDGC-010  Every CDGC route is probe-derived: no vendor CDGC API guide was held
**Kind:** GOTCHA · **Proven:** 2026-07-25 · **Evidence:** Provenance review of the endpoint corpus
No Informatica CDGC REST guide was available, so every data360/ccgf route in this KB comes from live probes and browser network captures, not vendor documentation. Treat them as lower confidence than vendor-documented CAI or CDQ routes, record host, header, verb, code and date for each verdict, and re-probe when the platform build changes.

### L-CDGC-011  Metadata Command Center is REST-driven; INFACore is a client-side SDK with no server endpoint
**Kind:** OVERTURNED · **Proven:** 2026-07-09 · **Supersedes:** L-CDGC-131 · **Evidence:** MCC catalogsources GET 200 while INFACore probes 404
INFACore is a pip-installable Python/CLI SDK that authenticates to IDMC and drives a Secure Agent. It has no server-side endpoint, so a probe for an "INFACore service" 404s even when INFACore is usable; do not gate work on that 404. Drive catalog work through MCC's backing REST: catalog-source management plus the executable and observable routes.

### L-CDGC-012  MCC configures and runs; Data Governance and Catalog shows the content
**Kind:** GOTCHA · **Proven:** 2026-09-24 · **Evidence:** UI walks with screenshots (2026-06-27, 2026-08-20, 2026-09-24)
Metadata Command Center (MCC) is where catalog sources are registered, configured, run and monitored (Monitor > job > per-capability tasks and logs) and where lineage connection assignment lives (Configure > Lineage). Data Governance and Catalog (DGC) is where assets are searched and browsed and where lineage, glossary, classifications, DQ and stakeholders are shown. Its Customize/admin pages show "nothing to display" even when the catalog is full: drill Explore > source > schema > tables before calling a scan failed. Data Marketplace is a third app.

### L-CDGC-013  The CDGC asset and search APIs rate-limit with 429: walk them sequentially
**Kind:** GOTCHA · **Proven:** 2026-09-27 · **Evidence:** Coverage-feed code with adaptive pacing and 429/401 handling
data360 asset reads and searches answer 429 when called too fast. Run tree walks (Resource > Database > Schema > Table/View > Column, plus each column's classifications) one call at a time with an adaptive pace: start near 0.8 s between calls, add about 0.3 s and sleep about 15 s on each 429 (cap near 4 s), ease back slowly on success, and re-mint the JWT on 401. A Salesforce source holds the whole org schema (hundreds of objects, tens of thousands of fields), which exceeds a practical call budget, so walk only the objects you need.

### L-CDGC-014  Create a catalog source: multipart part dataSource on ccgf-catalog-source-management
**Kind:** OVERTURNED · **Proven:** 2026-09-29 · **Supersedes:** L-CDGC-128 · **Evidence:** 415, then 500, then success; 5 sources created and verified by GET in one dm-us org (2026-09-28/29), 3 in a dmp-us org (2026-09-24/25)
`POST https://cdgc-api.<domain>.informaticacloud.com/ccgf-catalog-source-management/api/v1/datasources` (no trailing slash: a trailing slash gives 404) as `multipart/form-data` with exactly one part named `dataSource` (`Content-Type: application/json`) holding the definition. Headers: Bearer JWT, `X-INFA-ORG-ID` and `IDS-SESSION-ID` (without `IDS-SESSION-ID` the runtime-environment validation fails). A plain JSON body returns 415; a definition without `custom` and `endOfLife` returns 500 "Custom flag cannot be null". Success returns the source with its new `id`; read it back with `GET .../datasources/<id>`. No MCC step is needed to register a source.

### L-CDGC-015  Build a create body by cloning a working source of the same type and remapping every id
**Kind:** RECIPE · **Proven:** 2026-09-29 · **Evidence:** Created sources verified by GET with no source-org ids left; the earlier clone bug found by read-back
GET a working source of the same type and keep `name, description, type, endOfLife, custom, overrides, typeOptions, capabilities, typeCapabilities, globalConfigOptions, customAttributes`. Drop `id, createdBy, lastModifiedBy, createdTime, lastModifiedTime, seedVersion, clonedCatalogSourceId, modelVersion` (and `isDeleted`). Remap the connection id (`typeOptions` > `ConnectionId`), the runtime environment (`globalConfigOptions` > Execution > Runtime Settings > `Runtime Environment`) and any catalog id, then string-scan the JSON and assert that no old-org or old-connection id remains. A clone helper that captured but never swapped its connection argument once created a source still bound to the old warehouse.

### L-CDGC-016  List catalog-source types with GET datasourceTypes
**Kind:** OVERTURNED · **Proven:** 2026-10-03 · **Supersedes:** L-CDGC-124 · **Evidence:** Types listed before the creates of 2026-09-24; both routes 200 with the catalog identity headers, and the PostgreSQL type with its Data Quality and Data Classification configurations read (2026-10-03)
`GET .../ccgf-catalog-source-management/api/v1/datasourceTypes` lists the types the org can create (for example PostgreSQL, Google BigQuery, IICS). Confirm the type exists before cloning a definition. The older `GET /data360/catalog-source-management/v1/catalogsourcetypes` still returns 404; in July 2026 that 404 was read as "types can only be picked in the MCC wizard". Each listed type carries `iicsConnectionTypes`, `optionGroups` and `documentationInfo` (for PostgreSQL: `sourceSystemVersions` '10.x through 14.x', authentication modes Database and Kerberos, Data Quality exception management 'Yes'; page with `?offset=0&limit=200`). `GET .../api/v1/type/<TypeName>/capability/<CapabilityName, URL-encoded>/configuration` (for example `type/PostgreSQL/capability/Data%20Quality/configuration`) returns that capability's option groups, each option with its `name`, `dataType`, `required`, `defaultValue`, `staticValues` and `conditions` (the typeCapabilities layer, L-CDGC-143): for Data Quality the `Data Quality Scope` group offers `Sampling Type` (All Rows, Limit N Rows as the default, or Custom Query), `No of rows to limit` (default 1000), `Sampling Query` and `Runtime Environment`; Data Classification returned no option groups at the type level, so there is no classification auto-accept threshold to set there (L-CDGC-061). Build catalog-source bodies from these reads rather than guessing option keys.

### L-CDGC-018  The catalog-source list can come back empty: keep your own name-to-id map
**Kind:** GOTCHA · **Proven:** 2026-09-26 · **Evidence:** 0 items vs 4 in the UI (2026-06-27); empty list for the service login (2026-09-26)
The list call has returned 0 items while MCC showed the sources: once before the full header set was sent, and once for a service login after a wave of renames. ### L-CDGC-019  The data360 catalog-source-management prefix is not reliably routed: create, update and purge on the ccgf plane
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** 200 (July); empty 404 with identical bogus twin (2026-08-20); 200 (2026-09-28)
The same `data360/catalog-source-management/v1/catalogsources` prefix answered 200 in July 2026, returned an empty-body 404 identical to its bogus twin on idmc-api, the pod host and cdgc-api for one org on 2026-08-20 (while search with the same JWT returned 200), and answered 200 again on that org on 2026-09-28. ### L-CDGC-020  Update a catalog source: GET, back up, edit, multipart PUT
**Kind:** OVERTURNED · **Proven:** 2026-09-29 · **Supersedes:** L-CDGC-127 · **Evidence:** Filter and change-option edits took effect on the next scans (2026-09-25 bisect helper; 2026-09-28/29 update helper)
`GET .../ccgf-catalog-source-management/api/v1/datasources/<id>`; save the JSON as the undo file; edit it; strip the read-only fields (`id, createdBy, lastModifiedBy, createdTime, lastModifiedTime, seedVersion`, and for a clone `clonedCatalogSourceId, modelVersion`); send it as multipart part `dataSource` with `PUT .../datasources/<id>` (fall back to PATCH if PUT is refused). Include filters, the Metadata Change Option, profiling filters and lineage filters were changed this way and took effect on the next scan, so a source's object selection and capability configuration are no longer MCC-only.

### L-CDGC-021  Anatomy of a catalog-source definition
**Kind:** RECIPE · **Proven:** 2026-09-29 · **Evidence:** GET bodies of five sources of four types (2026-09-28/29)
A GET returns: `type` (e.g. `PostgreSQL`, `Google BigQuery`, `IICS`, `Salesforce`, `Microsoft Fabric Data Warehouse`); `typeOptions.configurationProperties[]` option groups of `{key, values[], additionalMetadata}` (a database or SaaS source carries `ConnectionId` = the v2 connection id; an IICS source carries `IICS URL`, `IICS User`, `IICS Password`); `capabilities[]` of `{capabilityName, configurationProperties[]}` (Metadata Extraction has group "Metadata Extraction OptionGroup" with `Metadata Change Option` Retain|Delete and `Type of scan` Full; Data Profiling can carry group "Data Profiling Scope"); `typeCapabilities[]` holding per-capability filters ("Metadata Filter Config", "Profiling Filter Config", "Lineage Discovery Filter Config"); `globalConfigOptions[]` with `Execution` (group "Runtime Settings" > `Runtime Environment` = `<reId>`; group "Metadata Sync Settings" > `Mode of Execution` = `Full Sync`) and `Configuration` (group "Metadata and Data Filters" > `Filter Options` = `Filter Conditions`); plus `custom`, `endOfLife`, `overrides[]`, `customAttributes`.

### L-CDGC-022  Create validates the runtime environment; readyToRun=false never blocked scans
**Kind:** OVERTURNED · **Proven:** 2026-09-24 · **Supersedes:** L-CDGC-136 · **Evidence:** 500 on create (2026-06-27); scans ran with readyToRun=false (2026-06-28); creates validated with IDS-SESSION-ID (2026-09-24)
The create call validates the runtime environment named in `globalConfigOptions` Execution. In June 2026 it returned 500 "Error while validating Runtime Environment detail [<reId>] under global config option [Execution]" while the RE-nested `readyToRun` was false, and restarts or a brand-new RE did not clear it; the same session noted the calls probably lacked `IDS-SESSION-ID`/`X-INFA-ORG-ID`. In September 2026 creates validated once `IDS-SESSION-ID` was sent. `readyToRun=false` never blocked scans of existing sources or mapping-task runs. On a validation failure, re-send with the full header set before touching the RE.

### L-CDGC-023  Catalog PostgreSQL with the native connector, not JDBC
**Kind:** DECISION · **Proven:** 2026-07-08 · **Evidence:** Native Sync logs Success with failed:0; JDBC runs COMPLETED WITH ERRORS
JDBC-based PostgreSQL scans cannot read the system catalogs (`Object(s) [pg_sequence/pg_constraint/pg_foreign_server/...] not found`), finish COMPLETED WITH ERRORS and miss sequences, constraints and foreign keys. Native PostgreSQL scans (connectorGuid `com.informatica.adapter.postgres`) read them, parse PL/pgSQL function bodies and finish Success. Use the native connector for cataloging (it is also the one DBMI/CDC needs) and retire JDBC catalog sources.

### L-CDGC-024  Catalog scanners read JDBC drivers from their own folders
**Kind:** RECIPE · **Proven:** 2026-06-27 · **Evidence:** Connection test and scan both succeeded only after placement in all folders
A JDBC driver jar that makes the connection Test pass (`<agent_home>/ext/connectors/thirdparty/informatica.jdbc_v2/common/`) is not seen by the catalog scanners. Also place it under `Metadata_Foundation_Agent/.../data/browse/drivers/` (plus a per-database subfolder) and `Metadata_Platform_Service/.../lib/drivers/` (and `Database_Ingestion/.../dbmi_libs/libs/` for DBMI), then restart the agent.

### L-CDGC-025  Microsoft Fabric catalog-source type, and types without a Data Quality capability
**Kind:** GOTCHA · **Proven:** 2026-07-09 · **Evidence:** MCC picker listing; typeCapabilities inspection
The type for a Fabric warehouse is "Microsoft Fabric Data Warehouse" (connectorGuid `com.informatica.adapter.fabricdw`), one of three native Fabric types in the MCC picker; no extra entitlement was needed. ### L-CDGC-026  PostgreSQL catalog filters are schema.*, because the scanner adds connection and database
**Kind:** GOTCHA · **Proven:** 2026-09-24 · **Evidence:** Two runs FAILED on db.schema.*; COMPLETED after the change
A scan that fails with "None of the Assets met filter criteria" usually has filters written as `db.schema.*` (for example copied from a Snowflake source). The PostgreSQL scanner prefixes `<connection>.<database>.` itself, so the filter value must be `schema.*` (e.g. `public.*`). For warehouse sources, confirm the expected form per type: one BigQuery profiling filter was written with both `<dataset>.*` and `<project>.<dataset>.*`.

### L-CDGC-027  Scope a scan with the Metadata Filter Config option group
**Kind:** RECIPE · **Proven:** 2026-09-25 · **Evidence:** Bisect runs on a failing IICS scan; CLAIRE answered from stale copies until the include filter was set
In `typeCapabilities` > "Metadata Extraction", add one `configurationProperties` group named "Metadata Filter Config" per pattern, with `Filter Pivot` = ["Include Metadata"], `Filter Type` (e.g. ["Data Integration"] for an IICS source, or the dataset/schema type for a database or warehouse), `Filter Value` = ["<path pattern>"] and `Filter Conditions` = ["All Types"]. Include-filter warehouse sources to their live datasets so CLAIRE does not answer from stale copies in other datasets. To isolate a failing object, a bisect helper can set one pattern, PUT, scan Metadata Extraction only, print the task statuses and restore the saved original.

### L-CDGC-028  Set Metadata Change Option = Delete before a rescan, or removed and renamed objects stay
**Kind:** GOTCHA · **Proven:** 2026-09-29 · **Evidence:** After Retain->Delete and a rescan, 0 stale assets were left (2026-09-29); a renamed database left only the new tree (2026-09-26)
With the default `Retain`, a rescan keeps catalog objects that no longer exist in the source: a renamed database or schema leaves both trees, and deleted objects linger (and confuse CLAIRE). Set `Metadata Change Option` to `Delete` in `capabilities` > "Metadata Extraction" > "Metadata Extraction OptionGroup" (multipart PUT, L-CDGC-020) before rescanning, and extend a warehouse source's include filter to any datasets added since (e.g. CDC or real-time views) so they are cataloged too.

### L-CDGC-029  IICS catalog source for CDI lineage: project include filter plus Lineage Discovery
**Kind:** RECIPE · **Proven:** 2026-09-25 · **Evidence:** Connection-assignment recommendations appeared only with Lineage Discovery enabled
A source of type `IICS` catalogs Data Integration assets for lineage. Set its Metadata Filter Config to Include / `Data Integration` / `<project>` / `All Types`, enable Metadata Extraction plus Lineage Discovery (without Lineage Discovery there are no connection-assignment recommendations and no stitched lineage), and rescan after adding new task types or lanes. Run it on a runtime environment you control, not a shared demo runtime.

### L-CDGC-030  The IICS catalog source stores a user password: rotation breaks it and its JSON is secret-bearing
**Kind:** SECURITY · **Proven:** 2026-09-29 · **Evidence:** Cutover rotation list item; inspection of saved GET bodies (value length only, never printed)
An IICS source keeps `IICS URL`, `IICS User` and `IICS Password` in `typeOptions` and signs in as that user, so its scans fail when that password rotates. Use a dedicated service login you own (never a personal or borrowed login) and put the source on the rotation checklist. A GET returns the password option as a long opaque string (about 300 characters, probably encrypted; not verified), so treat saved source JSON backups as secret-bearing files.

### L-CDGC-032  Salesforce catalog source for lineage: ViewSetup and ViewRoles, then assign the connection
**Kind:** RECIPE · **Proven:** 2026-09-25 · **Evidence:** CLAIRE showed a custom object with 23 upstream assets across 5 hops
The Salesforce integration user behind the connection needs ViewSetup and ViewRoles. After the scan, assign the IDMC Salesforce connection in MCC > Configure > Lineage > Assign Connections so mapping tasks stitch to the Salesforce objects. The source holds the whole org schema (hundreds of standard objects), so downstream tooling should filter to the objects it uses.

### L-CDGC-033  Scope warehouse sources: profiling a whole 26-dataset project took about two hours
**Kind:** PERF · **Proven:** 2026-09-24 · **Evidence:** Measured scan durations
Scope a BigQuery source to the datasets you need with an include filter: profiling a whole 26-dataset project took about two hours. For scale, a native PostgreSQL scan of one application database took about 51 minutes in June 2026.

### L-CDGC-034  Run a scan: POST data360/executable/v1/catalogsource/<id> with a non-empty capabilityNames
**Kind:** OVERTURNED · **Proven:** 2026-09-29 · **Supersedes:** L-CDGC-120 · **Evidence:** 201 + jobId in June, July and September 2026 on three orgs
`POST https://idmc-api.<domain>.informaticacloud.com/data360/executable/v1/catalogsource/<catalogSourceId>` with the three identity headers and `{"capabilityNames":["Metadata Extraction","Data Profiling","Data Classification","Lineage Discovery"]}` (only capabilities configured on the source) returns 201 (200 also seen) with `jobId` and `trackingURI`. The same body worked on `/data360/catalog-source-management/v1/catalogsources/<id>/sync` and on the `cdgc-api` host. Every scan is IPU-metered.

### L-CDGC-035  Capability names are the UI display names, e.g. Metadata Extraction
**Kind:** OVERTURNED · **Proven:** 2026-09-28 · **Supersedes:** L-CDGC-134 · **Evidence:** Runs accepted with display names (2026-08-20, 2026-09-24..29)
Use display names in `capabilityNames` and in definitions: "Metadata Extraction", "Data Profiling", "Data Classification", "Lineage Discovery", "Data Quality", "Data Observability". ### L-CDGC-036  One source can run every capability in one scan; Data Quality also runs alone once its Scope groups carry a runtime environment
**Kind:** RECIPE · **Proven:** 2026-09-30 · **Evidence:** One run produced catalog, profiling and DQ per source (2026-06-27); DQ-only run 406 (2026-07-09); DQ-only runs COMPLETED with Score Propagation after the Scope groups were added (2026-09-30)
A source configured with Metadata Extraction, Lineage Discovery, Data Profiling, Data Quality and Data Observability produces catalog, lineage, profiles, DQ results and observability in one run when all are listed in `capabilityNames`. Data Observability depends on profiling and is skipped when profiling fails. Submitting `{"capabilityNames":["Data Quality"]}` alone returned 406 in July, but it runs on its own (Rule Profiling, Batch Profiling and Score Propagation, about 15 min for a warehouse source) once the source's `typeCapabilities` carry the Data Profiling Scope and Data Quality Scope groups with a runtime environment (L-CDGC-143).

### L-CDGC-037  Poll one job at observable/v1/jobs/<jobId>; list jobs at observable/api/v1/jobs
