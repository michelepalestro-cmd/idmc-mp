**Secure Agent (L-AGENT)**

### L-CONN-001  Create connections with type TOOLKIT_CCI and the connector name in instanceName
**Kind:** ROUTE · **Proven:** 2026-09-12 · **Evidence:** 200 on three orgs and several connectors (2026-06-27, 2026-07-26, 2026-09-12); APP_10519 for flat bodies · **Overturns:** L-CONN-076
`POST <serverUrl>/api/v2/connection`, headers `icSessionId` and `Content-Type: application/json`, body `{"@type":"connection","name":"<name>","type":"TOOLKIT_CCI","instanceName":"<connector name exactly as Administrator shows it>","runtimeEnvironmentId":"<reId>","connParams":{...}}` (some proven bodies also carry the connector GUID, `agentId`, `agentGroupId` and `orgId`). The `type` is never the connector name: `"PostgreSQL"`, `"ClickHouse"` or a shortName such as `"PostgreSQLadapter"` return 403 APP_10519 'The connection type is not valid', which is easily misread as a licensing problem. A short type string alone fails; the full body works. Read the object back after the create. Exception: a SharePoint Online connection needs type TOOLKIT (L-CONN-128).

### L-CONN-002  The create validator names one missing field per call: iterate until 200
**Kind:** RECIPE · **Proven:** 2026-07-26 · **Evidence:** Iterative 105054 responses ending in 200 (2026-06-27, 2026-07-26)
POST what you have and read the answer: 403 APP_105054 (or a 400/422) names one missing or misnamed `connParams` attribute per response, so add it and repeat; 405 means stop (no such verb); 403 APP_10519 means the `type` is wrong, go back to `TOOLKIT_CCI`. If one type string yields a different error from the rest (ODBC gave `UI_13427 Code page is not valid` while others gave APP_10519), your request reaches real validation and the others fail at the type gate, not at licensing. This loop found keys (`dbName`, `jdbcdriverclassname`, `connectionstring`) that appear in no local vendor PDF.

### L-CONN-003  Read a connector's field names from the agent-side manifest instead of guessing
**Kind:** RECIPE · **Proven:** 2026-09-16 · **Evidence:** Settled the JDBC V2 and native PostgreSQL key sets (2026-06-27, 2026-07-26); BigQuery V2 from a working GET (2026-09-16)
Every CCI connector ships its attribute list on the agent: `grep -o '"attributeName":"[a-zA-Z_]*"' <agent_home>/downloads/package-<CONNECTOR>.<ver>/CCIManifest.txt`, or the plugin XML under `<agent_home>/downloads/package-<CONNECTOR>*/package/rdtm/plugins/*.xml`, which also states whether the type can carry credentials (`HASUSERNAME`/`HASUSERPASSWORD`). The other reliable sources are one UI-created connection of the same type, or a working connection read with `GET /api/v2/connection/<connId>`: copy its key set and change only what you need.

### L-CONN-004  Clone a working connection over v2, and build mirrors from the running stack
**Kind:** RECIPE · **Proven:** 2026-09-03 · **Evidence:** Clone tested green (2026-09-03); 4 mirror connections created (2026-07-04/08)
GET a working connection, change its name and database (and host if needed), POST it to `/api/v2/connection` without an id, then test it; this gave a clean second source without touching the live one. For environment mirrors, read the dev database credentials from the running containers (`docker inspect` env) instead of waiting for production passwords, name mirrors predictably (base name plus a suffix), bind them to the mirror's runtime environment and make the script idempotent. Creating, testing and deleting connection objects costs 0 IPU and needs no licence change.

### L-CONN-005  A new add-on connector type is registered in the org by one UI-created connection
**Kind:** WALL · **Proven:** 2026-07-08 · **Evidence:** 403 on four body shapes, then 200 after one UI-created connection (2026-06-28 to 2026-07-08)
The connector package can be on the agent while the cloud-side connector type is not yet registered for the org; then `POST /api/v2/connection` fails with 403 'no connector with type=<shortName>' (for example `GoogleBigQueryV2`) or APP_10519 'connection type not valid', for every body shape (full CCI with GUID and instanceName, type=shortName, no instanceName, instanceName=GUID). Creating ONE connection of that type in Administrator > Connections registers it; afterwards the same REST body creates and manages connections of that type. Proven in July 2026 for BigQuery V2 and native PostgreSQL; not re-tested since connector selection became headless (L-AGENT-039), which may or may not register the type.

### L-CONN-006  Update a connection by POSTing the full body to /api/v2/connection/<connId>
**Kind:** ROUTE · **Proven:** 2026-09-28 · **Evidence:** REPO_10200 without the id, 200 with it (2026-08-20); 8 connections updated and tested (2026-09-28)
`GET /api/v2/connection/<connId>`, change the fields, strip `createTime`, `updateTime`, `createdBy` and `updatedBy`, and POST the whole body back to `/api/v2/connection/<connId>` (there is no PUT on this resource). `POST /api/v2/connection` without the id is create-only and fails with REPO_10200 (name already exists) for an existing connection. Read the connection back after the update: a 200 whose value reverts is a silent rejection.

### L-CONN-007  GET returns secrets masked, so every update must re-supply them
**Kind:** GOTCHA · **Proven:** 2026-09-23 · **Evidence:** Private key blanked by an update, test green after re-supplying it (2026-09-23)
`GET /api/v2/connection/<connId>` returns the password or private key masked. POSTing the body back to change one attribute (for example `useLegacySQLForCustomQuery`) blanks the secret and breaks the connection unless the secret field is re-supplied. Rule: never POST a connection update without the secret, and re-test after every update.

### L-CONN-008  Set connection secrets headless on the host that holds them
**Kind:** RECIPE · **Proven:** 2026-09-28 · **Evidence:** 8 of 8 imported connections tested 200 on the target agent (2026-09-28); 3 connections fixed after a password rotation (2026-09-16)
GET the full body; set `connParams.password` (or `connParams.privateKey`; for Salesforce the top-level `username`, `password` and `securityToken`); POST it back to `/api/v2/connection/<connId>`; then `GET /api/v2/connection/test/<connId>`. Read each secret from a 0600 file at run time inside the script, on the host that holds it, so it never reaches a transcript or command line. Connections that arrive by migration import carry no passwords: bind them to the target runtime environment, set every secret this way and test each one on the target agent before any run.

### L-CONN-009  Repoint connections after a database move without changing their ids
**Kind:** RECIPE · **Proven:** 2026-07-12 · **Evidence:** 4 of 4 connection tests SUCCESS with ids preserved (2026-07-12)
After moving source databases, update each connection in place with `POST /api/v2/connection/<connId>` and the full body (new host and port, secret re-supplied), so mapping tasks and catalog sources that reference the connection id stay bound. Test before relying on it. Catalog scans that failed after the move recover on their next run.

### L-CONN-010  Renaming a shared connection is risky
**Kind:** GOTCHA · **Proven:** 2026-09-24 · **Evidence:** Decision note after a key was blanked (2026-09-24)
A rename is an update that re-sends the whole object: for key-based connections (BigQuery V2) a rewrite without the secret blanks the key, and other tools and sessions may reference the connection by name. Rename only in a coordinated window, re-supply the secret, and re-test.

### L-CONN-011  Before renaming or retiring a database user, find every IDMC connection that logs in as it
**Kind:** LAW · **Proven:** 2026-09-26 · **Evidence:** One connection missed for 6 hours; lanes green again after the update (2026-09-26)
A shared database role is often used by several IDMC connections, plus CDC tasks, BI tools and backups. When it is renamed or retired, every connection still logging in as the old user fails at run time, and every dependent task and taskflow fails each cycle ('password authentication failed for user <old>'). List all connections whose `userName` is the old role (not only the one named after the app), update them in the same window with the password re-supplied, and run a health watcher that alerts on state changes.

### L-CONN-012  Give IDMC its own database user, with least privilege
**Kind:** GOTCHA · **Proven:** 2026-08-20 · **Evidence:** Connections tested 200 with a dedicated user (2026-08-20); open item recorded (2026-07-26)
When other services share a database's default user, create a dedicated user for IDMC connections instead of changing the default user's password, which would break the other services. Connections created during a proof of concept often reuse the containers' own credentials; replace them with least-privilege, read-only users before the integration is more than a POC. Newer evidence: L-CONN-135.

### L-CONN-013  Take database credentials from the running application, and do not trust a green JDBC V2 test
**Kind:** GOTCHA · **Proven:** 2026-06-27 · **Evidence:** Native test failed with the assumed password and passed with the runtime one (2026-06-27)
A JDBC V2 connection test reported success while the stored password was wrong (JDBC V2 may not pass the password at all, L-CONN-048); a native-connector test exposed the real authentication failure. Take credentials from the running application's own configuration (for example `docker exec <app> printenv DATABASE_URL`) rather than guessing.

### L-CONN-014  Test a connection with GET /api/v2/connection/test/<connId>: a free metadata handshake
**Kind:** ROUTE · **Proven:** 2026-09-23 · **Evidence:** 200 'test successful' on dozens of connections (2026-06-27 to 2026-09-28); POST variants 500/404
`GET <serverUrl>/api/v2/connection/test/<connId>` (header `icSessionId`; some native CCI tests append `?type=TOOLKIT_CCI`, and one July record got 400 without it) returns 200 'test successful' or an error such as 403 APP_105060. It is a read-only metadata handshake: no data run, 0 IPU, so it is the tool for reachability matrices across runtime environments. `POST /api/v2/connection/test` returned 500 (APP_21000 seen) and `/api/v2/connection/<connId>/test` 404. The managed MCP `connectionmanagement.test_connection_by_id` is a reliable alternative. `GET /api/v2/connection/<connId>` carries a cached `status` of the last test (success, failed, or absent).

### L-CONN-015  A passing test is not the proof; a run that lands rows is
**Kind:** GOTCHA · **Proven:** 2026-08-19 · **Evidence:** Test and run results diverged on JDBC V2 connections (2026-08-18/19)
A connection test only proves the handshake. It can pass with a wrong password (JDBC V2), and it can fail while the path works for jobs. The definitive proof of a connection is a mapping run that lands rows in the target, checked by count.

### L-CONN-016  Connection and connector reads
**Kind:** ROUTE · **Proven:** 2026-10-03 · **Evidence:** 200 live (2026-07-04 to 2026-07-25); browse 200 [] with and without ?type=table on two working PostgreSQL connections, the test 200 in 1.4 s with sessions 10 -> 11 and xact_commit +8 (2026-10-03)
`GET /api/v2/connection` lists connections (with the cached test `status`); `GET /api/v2/connection/<connId>` reads one; `GET /api/v2/connection/source/<connId>?type=table` browses source objects (200 or 403 per connection, and it can surface target-side errors such as a throttled warehouse), but it can also return 200 with an empty list for a working connection (two native PostgreSQL connections whose databases held tables, a known-good BigQuery connection), so an empty browse proves nothing: confirm objects through a consumer (profile source fields, a mapping preview, a catalog Metadata Extraction); `GET /api/v2/connector` returns the connector type catalog; `GET /api/v2/connector/metadata?connectorName=<name>` returns a connector's schema, and `200 []` means the connector is not activated. The v3 `/public/core/v3/connections` path is 404: connections are v2 only. To prove that a connection test really reached the database and was not a cached status, diff the database's own counters around `GET /api/v2/connection/test/<connId>`: on PostgreSQL the test opened one session and committed about 8 transactions (`pg_stat_database.sessions` +1, `xact_commit` +8) in 1.4 s.

### L-CONN-017  Delete a connection with DELETE /api/v2/connection/<connId>, after a used-by check
**Kind:** ROUTE · **Proven:** 2026-09-28 · **Evidence:** Create/delete round trip (2026-07-04/09); connection deletes in a headless org cleanup (2026-09-28)
`DELETE <serverUrl>/api/v2/connection/<connId>` returns 200 and leaves no orphan (an Amazon S3 v2 create-then-delete round trip proved it); a read-back 403 or 404 means gone. Check users first: REPO_10242 means mappings still reference the connection, and 'used by another asset' means a catalog source holds it. In a cleanup, delete connections late, after the tasks, mappings and catalog sources that use them.

### L-CONN-018  403 APP_105060 is a family: read the message to know which gate failed
**Kind:** ERROR · **Proven:** 2026-09-28 · **Evidence:** Each message seen on live tests (2026-07-26 to 2026-09-22)
The same code carries different causes, and the connection definition is usually fine. 'Unable to resolve channel service. No running service found of type <Engine> <ver>.* service for AgentGroup: <reId>' means that engine is not selected, still deploying or down on that runtime environment (L-AGENT-076). 'Unable to fetch Connector attributes, Ensure adapter ID is valid and the service is enabled [com.informatica.adapter.<x>]' means the connector adapter is not enabled or not deployed on that agent (L-CONN-019). 'No running service found of type Connector_Service' usually means the connection is bound to another runtime environment (L-CONN-023). Check `agentEngines[]` and the runtime-environment selections before touching the connection.

### L-CONN-019  'Unable to fetch Connector attributes [com.informatica.adapter.<x>]' means the adapter is not on the agent
**Kind:** ERROR · **Proven:** 2026-09-22 · **Evidence:** Adapter registry listed on-host without the connector (2026-07-26); 200 after the connector was re-added (2026-09-22)
The create validates in the cloud, so the connection saves fine, but Test and runs fail with this message until the connector's runtime package is enabled and deployed on the agent that serves the connection. Enabling engines does not enable connectors. Check the agent's registry under `<agent_home>/apps/Connector_Service/<ver>/connectors/cci/plugins/` (the ADAPTER_HOME its log prints) and `<agent_home>/ext/connectors/thirdparty/`. Fix: select the connector on the runtime environment (L-AGENT-039); in June 2026, creating one connection of that type in the UI also triggered the package download.

### L-CONN-020  Copying adapter jars into the agent does not enable a connector
**Kind:** GOTCHA · **Proven:** 2026-09-22 · **Evidence:** Jar-copy attempts failed (2026-09-20/22); package auto-downloaded after enablement (2026-09-14)
Connector enablement is a control-plane push: once the connector is selected for the runtime environment, the control plane registers its attributes (which clears APP_105060) and pushes a new DIS appspec, and the agent downloads the package and deploys the jars itself. Adapter jars copied by hand into plugin folders are not registered and are reconciled away on restart, and `consoleAgentManager` has no install verb. This differs from third-party JDBC driver jars for a connector that is already enabled, which are staged by hand (L-CONN-049).

### L-CONN-021  GET /api/v2/connector is a type catalog, not what the agent can run
**Kind:** OVERTURNED · **Proven:** 2026-07-26 · **Evidence:** Counts 153/342/352 across orgs (2026-06-27 to 2026-09-23); adapter registry inspected (2026-07-26) · **Overturns:** L-CONN-079
`GET /api/v2/connector` returned 153 types on one org, 342 on another and 352 on a third; the Product Availability Matrix lists about 301. It is not what the agent installed: a connection POSTs 200 against any listed type whose adapter was never deployed and fails only at test time, and a package can sit in `downloads/` with no adapter extracted (downloaded, extracted and registered are three states). Sources disagree on whether the list is org-specific (June) or Informatica's sellable catalog (July); either way the per-agent truth is the runtime environment's `connectors.selections[]` with `enabled` flags (L-AGENT-039) plus the agent's adapter registry. Check the list for gaps before designing (seen missing on one org: Stripe, so use REST V2; Fabric connectors; OpenAI, so use the generic LLM connector).

### L-CONN-022  Connectors are per agent: every connector a mapping uses must be on the agent that runs it
**Kind:** LAW · **Proven:** 2026-07-08 · **Evidence:** state=3 in 2 s with connectors on separate agents (2026-07-04); agent package inventory plus binding check (2026-07-06/08)
Connector availability is per Secure Agent / runtime environment. A mapping task whose source connector is on one agent and target connector on another failed within about 2 s (state 3, 0 rows) with 'DTM process terminated unexpectedly'. A task that aborts during session setup at 'Importing Connection: <conn>' (for example `trepcnx.cpp:296`) means its runtime cannot use that connection: the connection is bound to another runtime environment, or the agent lacks that connector. Use connections bound to the task's own runtime environment and co-locate source and target connectors (pushdown needs them on one agent too).

### L-CONN-023  'No running service found of type Connector_Service' usually means the connection is bound elsewhere
**Kind:** ERROR · **Proven:** 2026-09-16 · **Evidence:** Connection bound to a managed agent in another region failed; a locally bound one passed (2026-09-16)
A test failing with 'No running service found of type Connector_Service' usually means the connection is bound to another runtime environment (for example a hosted or regional agent) rather than your Secure Agent. Use or create a connection bound to your own runtime environment.

### L-CONN-024  The reserved 'Informatica Cloud Hosted Agent' runtime cannot be created in an org that lacks it
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** Import SUCCESSFUL after the remap (2026-09-28)
Tasks and connections bound to the hosted runtime environment fail to import into an org that does not have one, and the name is reserved (REPO_38210), so you cannot create it. Remap those objects to your own runtime environment inside the package (the inner files, the `exportMetadata.v2.json` entry and every `objectRefs` list) or at import. The remapped Salesforce tasks then ran on the self-hosted agent.

### L-CONN-025  A containerized agent must use Docker service names, not 127.0.0.1, in connection hosts
**Kind:** GOTCHA · **Proven:** 2026-08-18 · **Evidence:** Tests green after switching to the aliases (2026-08-18)
When the agent runs in a container on a Docker network, `127.0.0.1` or `localhost` in a connection points at the agent container itself. Use the Docker network aliases of the database containers (for example `postgres:5432`). Prove reachability from inside the agent container (for example a `/dev/tcp/<host>/<port>` probe) before debugging the connection.

### L-CONN-026  Containerized databases often bind a private interface, not localhost
**Kind:** GOTCHA · **Proven:** 2026-07-26 · **Evidence:** Verified on-host (2026-07-26)
Databases in containers commonly publish on a private IP, so every localhost port is closed and a connection sheet saying `localhost` fails. Find the real bind address and credentials with `ss -ltnp`, `docker ps --format '{{.Names}}\t{{.Ports}}'` and `docker inspect -f '{{range .Config.Env}}{{println .}}{{end}}' <container>`. A host's login banner can show a different private address from the provider's API; trust `ss`.

### L-CONN-027  Native PostgreSQL connection body (and its drifting key names)
**Kind:** RECIPE · **Proven:** 2026-09-23 · **Evidence:** Native PostgreSQL connections tested 200 on four orgs (2026-06-27, 2026-07-07, 2026-07-26, 2026-09-23)
`type:"TOOLKIT_CCI"`, `instanceName:"PostgreSQL"`, connector GUID `com.informatica.adapter.postgres`. The parameter set on a September 2026 connection was `hostName`, `port`, `database`, `userName`, `password`, `authenticationType`, `encryptionMethod`, plus `agentId`, `agentGroupId` and `orgId`; there is no schema parameter (do not send `schemaName`). Earlier proven bodies also sent `encryptionMethod:"noEncryption"`, `tlsv1_2:false`, `sslv3:false`, `validateServerCertificate:false`. The accepted `authenticationType` value and user key drifted between connector builds and pods: `Database` ('Basic' rejected as 'not a valid choice', June), `UserIdPassword` with `userName` (a DataDirect driver rename; `user` gave an NPE 'error [null]', July), and `Standard` with `user` and both `databaseName` and `database` (another pod, July). Copy the key set from a UI-created or working connection of the same type (L-CONN-003).

### L-CONN-028  PostgreSQL object paths are <schema>/TABLE/<table> or <schema>/VIEW/<view>
**Kind:** GOTCHA · **Proven:** 2026-09-23 · **Evidence:** Task ran with the path form; database logs showed no query for the failing forms (2026-09-22/23) · **Overturns:** L-CONN-084
As `$Source$` (or target) object of a task, the native PostgreSQL connector wants `<schema>/TABLE/<table>` or `<schema>/VIEW/<view>`. `public/<table>` fails with SDK_APP_COM_20000 'Incorrect list of path is populated with size: 1' (parsed as a live browse path), and bare names, `schema.table`, quoted identifiers or `db.schema.table` give 'Object(s) [X] not found' (a cache-only lookup; database statement logging showed no query arrived). With the right path the adapter resolves the object at run time, even on a connection created over REST and never browsed in the UI.

### L-CONN-029  The PostgreSQL connector types text as string(255) and cannot land jsonb
**Kind:** GOTCHA · **Proven:** 2026-09-26 · **Evidence:** 585-char values survived only to a flat-file diagnostic target; views plus JSON columns kept full text (2026-09-23 to 2026-09-26)
In template mapping tasks the native PostgreSQL connector typed every string as string(255) and truncated longer values silently, and it cannot land `jsonb`/`json`; field-precision overrides through v2 `overriddenFields` returned 400. For such tables create a PostgreSQL view in a source schema that selects every column with `jsonb::text` and land from `<schema>/VIEW/<table>`; on a BigQuery target also use a JSON-typed column (L-CONN-044). Views are additive and reversible (`DROP SCHEMA <schema> CASCADE`).

### L-CONN-030  Use the native PostgreSQL connector, not JDBC V2, for ingestion, CDC and cataloging
**Kind:** LAW · **Proven:** 2026-07-08 · **Evidence:** PAM lookup (2026-06-27); JDBC scans completed with errors (2026-07-08)
Per the Product Availability Matrix (v39.1) JDBC V2 supports Data Integration and Data Quality but not Database Ingestion and Replication. The native PostgreSQL connector supports DBMI/CDC and gives richer catalog metadata; JDBC-based catalog scans of PostgreSQL ended COMPLETED WITH ERRORS because the JDBC scanner cannot read the system catalogs (and dropped sequences, constraints and foreign keys).

### L-CONN-031  Connection test and catalog scans read JDBC drivers from different folders
**Kind:** RECIPE · **Proven:** 2026-07-08 · **Evidence:** Test and scan both succeeded after placement (2026-06-27)
On a minimal agent without the PostgreSQL jar, place the driver (for example `postgresql-42.7.4.jar`) in the JDBC V2 folder used by Test (`<agent_home>/ext/connectors/thirdparty/informatica.jdbc_v2/common/`) and in the scanner folders: `Metadata_Foundation_Agent/.../data/browse/drivers/` (plus a `postgresql` subfolder), `Metadata_Platform_Service/.../lib/drivers/` and `Database_Ingestion/.../dbmi_libs/libs/`. If a scanner still cannot find the driver, drop the jar into the `drivers/` directory of every engine.

### L-CONN-032  truncateTarget is not a reliable reload switch on any connector seen
**Kind:** GOTCHA · **Proven:** 2026-09-28 · **Evidence:** Doubled gold tables (2026-07-04); 0-row SUCCESS (2026-08-19); PG rerun posted 0 rows (2026-09-24); risk flag in a code review (2026-09-28)
BigQuery V2 targets appended on some tasks despite `truncateTarget=true` (July; the later BigQuery path uses `$Target$.oprRuntimeAttrs` `writeDisposition: "Write truncate"`); a ClickHouse JDBC V2 target reported SUCCESS with 0 rows when it was true; JDBC V2 targets ignore it (use the `Pre SQL` runtime attribute, L-CONN-056); on a PostgreSQL target it was observed ignored (a rerun of the same file posted 0 new rows), yet a posting task built with `truncateTarget=true` was flagged as able to wipe its system-of-record table. Do not rely on it either way: truncate explicitly (pre-SQL or a TRUNCATE step) for full reloads, keep postings idempotent in the database (for example a BEFORE INSERT trigger that skips existing business keys), and verify row counts. Refined: on PostgreSQL the writer attribute `TruncateTable = YES` does truncate (L-CDI-331); what was observed ignored is the flag.

### L-CONN-033  Rule out source-database blockers with one read-only diagnostic as the connection role
**Kind:** RECIPE · **Proven:** 2026-06-28 · **Evidence:** 0 blocked queries and 0 idle-in-transaction sessions during scans on 4 databases (2026-06-28)
Before blaming the source database for failed scans or runs, run a read-only diagnostic as the exact IDMC connection role: role privileges and SELECT gaps, schema USAGE, row-level security policies, `statement_timeout`, lock and idle-in-transaction timeouts, `temp_file_limit`, plus live checks for blocked queries and long idle transactions during a scan.

### L-CONN-034  BigQuery V2 connection identifiers, parameters and service-account roles
**Kind:** RECIPE · **Proven:** 2026-09-16 · **Evidence:** Connections created and tested (2026-06-27 to 2026-09-16)
Connector GUID `com.infa.adapter.bigqueryv2`, shortName `GoogleBigQueryV2`, sdkType CCI, display name Google BigQuery V2 (connector name 'Google Big Query V2'). `connParams`: `connectorType:"Simple"`, `clientEmail`, `privateKey`, `projectId`, `storagePath` (a `gs://` staging bucket), `datasetNameForCustomQuery`, plus a large `CCM_CONN_PRESENTATION` blob; the easiest path is to GET a working connection and change only these fields. The service account needs at least `roles/bigquery.dataEditor` and `roles/bigquery.jobUser`, plus access to the staging bucket (Bulk writes with truncate needed `roles/storage.objectAdmin`). Keep the key file out of git. Newer evidence: L-ENV-133.

### L-CONN-035  The BigQuery private-key format differs by engine and pod: test each consumer, split connections
**Kind:** OVERTURNED · **Proven:** 2026-09-28 · **Evidence:** 'Invalid PKCS#8 data' on the wrong form per engine; 5 formats tested against CDI and DBMI (2026-09-22 to 2026-09-28) · **Overturns:** L-CONN-082, L-CONN-083
Never send real newlines in `privateKey` (the v2 API strips them and the key fails as 'Invalid PKCS#8 data'). Beyond that, the accepted form varies: on one dmp-us pod CDI accepted the stripped base64 body, but the Data Gateway behind CLAIRE GPT data queries required the full PEM with literal `\n` escapes exactly as in the service-account JSON; on another dm-us pod the CDI BigQuery V2 connector accepted only the PEM body without the BEGIN/END header lines and rejected the escaped-PEM form, while Database Ingestion's Simba JDBC driver rejected the header-less form and accepted the PEM form (the reports call it 'escaped PEM'; the script's replace was a byte-for-byte no-op, so probably the unmodified PEM). Test each candidate per engine (CDI test, DBMI deploy, a gateway query) and keep one BigQuery connection per consumer when they disagree.

### L-CONN-036  Find a working key format with a probe loop, and restore the last good value if none passes
**Kind:** RECIPE · **Proven:** 2026-09-28 · **Evidence:** No single format passed both CDI and DBMI on one pod, so two connections were created (2026-09-28)
