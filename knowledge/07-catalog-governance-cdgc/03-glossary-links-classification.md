# Glossary, Links & Classification

**Answers:** How do I create, rename and delete glossary domains and terms headless? How do I link terms to assets,
curate descriptions and apply classifications? What is still UI-only (bulk accept, stewardship, DAM policies)? How do I
rebuild a glossary in another org?

**Read when:** scripting glossary or data-dictionary content; preparing the catalog so CLAIRE answers from the business
glossary; replacing or migrating a catalog source that carries links and classifications.

**Key rules:**
- Create domains and terms with `POST /data360/content/v1/assets` (`core.classType` Domain or BusinessTerm; a term names
  its domain as `parent`) (L-CDGC-050, L-CDGC-051).
- Edit with PATCH operation arrays on the segments `summary`, `glossary` and `dataClassification`, addressed by internal
  identity resolved through an Elasticsearch `terms` query on `core.externalId` (L-CDGC-056, L-CDGC-057, L-CDGC-060).
- Read back every delete by search: a Published term can report "deleted" and stay (L-CDGC-059).
- A scan can blank curated descriptions: also set them in the source system and re-run the curation script after every
  scan (L-CDGC-055).
- Promote only exact matches to built-in classes; bulk accept of CLAIRE classifications, stakeholder assignment and DAM
  policy authoring remain UI (L-CDGC-061, L-CDGC-062, L-CDGC-066, L-CDGC-067).
- Harvest GUID-keyed links and classifications into a name-keyed manifest before purging or replacing a source
  (L-CDGC-084).

> **Summary.** The glossary, the data dictionary and manual classification are all headless on the
> `data360/content/v1/assets` plane. Slash-bearing external ids in a URL path give 400, so always resolve identities by
> search first. Glossary content does not travel in a v3 package: rebuild it in a target org through these routes.

All routes are on `https://idmc-api.<domain>.informaticacloud.com` unless noted, with the three identity headers
([01](01-cdgc-apis-auth.md) section 2.4). `API` below means that base.

## 1. The content model

| `core.classType` | What it is | How it gets there |
|---|---|---|
| `com.infa.ccgf.models.governance.Domain` | Glossary domain (externalId `DOM-<n>`) | `POST /data360/content/v1/assets` |
| `com.infa.ccgf.models.governance.BusinessTerm` | Business term (externalId `BT-<n>`) | same, with `parent` |
| `core.DataElementClassification` | Data-element classification (built-in or CLAIRE-generated) | built in, or generated by a scan; applied through the `dataClassification` segment |
| `com.infa.ccgf.models.governance.RuleInstance` | DQ rule occurrence (external id `DQO-<n>`, name `DQREC_<column>_<dimension>_<rule>`) | accepting a CLAIRE recommendation, the asset form (New > Business Rules > Data Quality Rule Occurrence), or headless the `ccgf-contentv2/api/v1/publish` that form sends, then a `dataQuality/sync` (L-CDGC-161); delete with `DELETE.../content/v1/assets/<identity>?scheme=internal` (L-CDGC-144). Its `TechnicalDescription` is read-only, copied once from the rule specification (L-CDGC-145). After a Data Quality run its `selfAttributes` hold the score (L-CDGC-166) |
| `core.Resource` | The root asset of a catalog source | a scan |
| `com.infa.odin.models.relational.Database` / `Schema` / `Table` / `View` / `Column` | Harvested relational assets | a scan |
| `IClassTechnicalGlossaryBase` | A term-to-technical-asset relationship on the ccgf-contentv2 plane | `POST ccgf-contentv2/api/v1/publish` |

**Identity vs external id.**
- `core.identity` is the internal UUID. Address an asset as `/data360/content/v1/assets/<identity>?scheme=internal` (writes)
  or `/data360/search/v1/assets/<identity>?scheme=internal&segments=...` (reads).
- `core.externalId` is `DOM-<n>`, `BT-<n>`, a classification id, or for harvested assets
  `<catalogSourceId>://<db>/<schema>/<table>/<column>~com.infa.odin.models.relational.Column` (a view's columns end
  `~com.infa.odin.models.relational.ViewColumn`, L-CDGC-170). Only slash-free external ids work in a path with
  `?scheme=external` (L-CDGC-057).
- `core.location` holds the asset's path (a term's location contains its domain identity); `systemAttributes.core.origin`
  holds the catalog source id of a harvested asset.

**Segments** used on this plane: `summary` (`core.name`, `core.description`), `glossary` (linked terms),
`dataClassification` (classifications), `systemAttributes`, `selfAttributes`, `customAttributes`, `neighborhood`.

**PATCH operations** (body is a JSON list; 200 or 204 = done):

```json
[{"operation": "replace", "segment": "summary", "attributes": {"core.name": "<name>", "core.description": "<text>"}}]
[{"operation": "add", "segment": "glossary", "items": [{"core.identity": "<termIdentity>"}]}]
[{"operation": "add", "segment": "dataClassification", "items": [{"core.identity": "<classificationIdentity>"}]}]
```

A `remove` operation (unlinking) was not exercised in these sources.

## 2. Resolving identities (L-CDGC-057, L-CDGC-058)

```python
def identity_of(external_id):
    """externalId -> core.identity, via the Elasticsearch endpoint (never GET-by-path for slash ids)."""
    c, r = call("POST", f"{API}/data360/search/api/v1/search?knowledgeQuery=*&segments=all",
                {"from": 0, "size": 5, "query": {"terms": {"core.externalId": [external_id]}}}, search=True)
    hits = r["hits"]["hits"] if c == 200 else []
    return hits[0]["sourceAsMap"]["core.identity"] if hits else None
```

- A GET or PATCH with a slash-bearing external id in the path gives 400 (encoded slashes) or does not resolve
  (L-CDGC-057).
- The same object can be cataloged as a `Table` or a `View`: when a lookup misses, retry with the other suffix
  (L-CDGC-058).
- A script that maps names to identities from a full read of a source must page it with a sort on `core.identity` and
  filter on `core.origin` + `elementType` OBJECT: unsorted `from`/`size` pages overlap, and a link script reported
  existing assets as missing (L-CDGC-169; [04](04-search-lineage-marketplace.md) section 2.3).
- External ids embed the catalog source id, and `DOM-<n>` numbers and identities differ per org: after a source is
  recreated (another org, or delete and recreate), remap by replacing the source-id prefix, and read domain ids from
  per-org configuration (L-CDGC-058).

## 3. Glossary domains and terms

### 3.1 Create a domain (L-CDGC-050)

```
POST {API}/data360/content/v1/assets
{"core.classType": "com.infa.ccgf.models.governance.Domain",
 "summary": {"core.name": "<domain name>", "core.description": "<what the business does and why this domain exists>"}}
-> {"core.identity": "<domainIdentity>", "core.externalId": "DOM-<n>",...}
```

### 3.2 Create a term (L-CDGC-051)

```
POST {API}/data360/content/v1/assets
{"core.classType": "com.infa.ccgf.models.governance.BusinessTerm",
 "summary": {"core.name": "<term>", "core.description": "<definition>"},
 "parent": {"core.identity": "<domainIdentity>"}}
-> {"core.identity": "<termIdentity>", "core.externalId": "BT-<n>",...}
```

- Terms land in lifecycle **Published** (a term without `parent` was also accepted). The UI flow, for
  comparison, is New > Glossary Business Term > Create (Draft) > Submit (a governance ticket), and the UI expects the
  glossary to be published before terms are associated with assets.
- The Hierarchy tab (term > subdomain > domain) resolves from the parent; reads show `__meta.parentLocation`, so no extra
  write is needed for it.
- The old `glossary/v1/terms` and `businessTerms` paths stay 404: that 404 was never the verdict on glossary writes
  (L-CDGC-125 superseded).

### 3.3 Rename or redefine (L-CDGC-053)

```
PATCH {API}/data360/content/v1/assets/BT-<n>?scheme=external          (or /<identity>?scheme=internal)
[{"operation": "replace", "segment": "summary", "attributes": {"core.name": "<new name>", "core.description": "<new text>"}}]
```

The same works for a domain (`DOM-<n>`). Save the old values in an undo file first. CLAIRE and other catalog readers pick
the change up on their next refresh.

### 3.4 Delete, and the Published-term gotcha (L-CDGC-059)

- `DELETE {API}/data360/content/v1/assets/<identity>?scheme=internal` deletes a domain or term (200/202/204).
- On a **Published** term the call once reported "deleted" while the term stayed in search. Always read back by search;
  if the term persists, rename it "<name> (retired duplicate)" with a pointer to its replacement, move it out of
  Published, or remove it in the UI.

### 3.5 Idempotent, reversible glossary scripts (L-CDGC-052)

1. Search before create: ES `term` on `core.classType` (Domain or BusinessTerm), paged with `from`/`size` 200; match
   `core.name`; for terms also require the domain identity inside `core.location`. Compare the name client-side
   (`match` and `match_phrase` queries answer 400), and never skip the domain check: term names repeat across domains,
   and a name-only lookup reused another domain's term (L-CDGC-165).
2. Reuse what exists; create what does not; write a registry file after each create
   (`key -> {identity, externalId, source id}`).
3. `--undo` deletes the registry items in reverse order (terms before domains).
4. Before any PATCH that replaces a description or name, write the previous value into an undo JSON.
5. To rebuild a glossary in another org, export it read-only from the source org and replay it through these routes:
   glossary content does not travel in a v3 package (L-CDGC-071).
6. Expect one CDGC system job, 'Content Publish Task', per created glossary asset (one domain plus 45 terms made 46
   jobs). Batch the load, keep these jobs out of catalog-job failure alerts, and count them in a job budget that reads
   catalog jobs: they are not in the v2 activity log, and whether they count toward a monthly job cap is untested
   (L-CDGC-153). A glossary-link PATCH starts one too (L-CDGC-173); count them at write time, because completed ones
   are purged from the job list within minutes (L-CDGC-175).

## 4. Data dictionary and curated descriptions (L-CDGC-054, L-CDGC-055)

- Harvest the source first, so the column assets exist. Resolve each column identity (section 2), then
  `PATCH {API}/data360/content/v1/assets/<identity>?scheme=internal` with the `summary` replace operation carrying
  `core.description`.
- The same PATCH curates descriptions on a catalog source's Resource, Database and Schema assets.
- **Technical assets take the description alone** (L-CDGC-164). On a table, view or column,
  `[{"operation": "add", "segment": "summary", "attributes": {"core.description": "<text>"}}]` sets the description; a
  patch that also carries `core.name` answers 400 'Asset name update not supported for technical assets' (business
  assets accept both, L-CDGC-053). Bursts of these patches hit 429: back off and retry.
- **A scan can overwrite curated descriptions** when the source object's own description is blank. Also set descriptions in
  the source system (warehouse dataset, table and view descriptions; CRM field help text) and re-run the curation script
  after every scan of that source (L-CDGC-055).

## 5. Term-to-asset links

### 5.1 Content PATCH (the current method; L-CDGC-056)

```python
def link(term_identity, asset_external_id, log):
    key = f"{term_identity}|{asset_external_id}"
    if log.get(key) == "linked":
        return
    ai = identity_of(asset_external_id)
    if not ai:
        log[key] = "missing-asset"; return
    c, r = call("PATCH", f"{API}/data360/content/v1/assets/{ai}?scheme=internal",
                [{"operation": "add", "segment": "glossary", "items": [{"core.identity": term_identity}]}])
    log[key] = "linked" if c in (200, 204) else f"err {c}"
```

Link after each source's scan completes (the assets must exist). Proven on three link batches (11, 47 and 42 links).
This overturns the older verdict that term-to-column binding was UI-only (L-CDGC-126 superseded).

**Cost:** every PATCH starts one CDGC 'Content Publish Task' job, so one PATCH per link costs one catalog job per link
(L-CDGC-173). For more than a handful of links use the batched publish in 5.2: one call, one job (L-CDGC-174).

### 5.2 ccgf-contentv2 publish (the older write plane; L-CDGC-065)

**Batched links (L-CDGC-174):** one publish carrying N RELATIONSHIP INSERT items of type
`com.infa.ccgf.models.governance.IClassTechnicalGlossaryBase` (`fromIdentity` = the harvested asset's external id,
`toIdentity` = `BT-<n>`, both `EXTERNAL`; attributes `core.curationStatus` ACCEPTED, `core.channels` ["MANUAL"],
`core.inferred` false; header `X-INFA-PRODUCT-ID: CDGC`) answers 207 with a 201 per item and starts ONE Content Publish
Task for the whole call (96 links, one job). The links read back exactly like PATCH links.

`POST https://cdgc-api.<domain>.informaticacloud.com/ccgf-contentv2/api/v1/publish` returns 207 Multi-Status + job id; read
each item. It created a term-to-column relationship (type `IClassTechnicalGlossaryBase`, `curationStatus` ACCEPTED, item
201, link count 0 -> 1 on read-back) and set REJECTED curation. A publish of data-flow lineage edges returned 207 with
`items: []` and changed nothing. One capture also sent `X-INFA-PRODUCT-ID` (any value). The same route creates DQ rule
occurrences (a RuleInstance plus its column relationship), and that publish needs `X-INFA-PRODUCT-ID: CDGC`: without it,
500 'Required request header X-INFA-PRODUCT-ID' (L-CDGC-161; the recipe is in
[DQ Scorecards](../06-data-quality-profiling/04-dq-scorecards-warehouse-pattern-and-data-profiling-scorecards.md) §4).

### 5.3 Harvest links before replacing a source (L-CDGC-084)

Links and accepted classifications are keyed to the asset GUIDs of one catalog source. Before purging or replacing a
source, export a name-keyed manifest (asset path > terms, classifications) and re-apply it after the replacement is
scanned; match renamed assets by column-set similarity.

## 6. Classification

### 6.1 Two kinds of classification (L-CDGC-062)

| | Built-in Data Element Classifications | CLAIRE-generated classifications |
|---|---|---|
| What | About 230 regulatory and common classes (passport, tax id, IBAN, Email, Name, Gender, Address, Phone Number USA,...) | Custom classes CLAIRE generates, often one per column name (e.g. "Order Identifier") |
| On the asset | `core.acceptedClassification` once accepted | `core.generatedClassification` |
| Use | PII governance, sensitivity (`selfAttributes.core.sensitivity`, e.g. Email = MEDIUM) | Discovery hints |
| Rule | | Promote only exact matches to a built-in class; bulk-promoting business names as PII corrupts governance |

CLAIRE classifies from names and metadata (it also covers empty tables); profiling needs rows, so classified counts run well
above profiled counts (L-CDGC-064).

### 6.2 Apply a classification manually (L-CDGC-060)

```python
classes = {}                                   # core.name -> identity
frm = 0
while True:
    c, r = call("POST", f"{API}/data360/search/api/v1/search?knowledgeQuery=*&segments=all",
                {"from": frm, "size": 200, "query": {"term": {"core.classType": "core.DataElementClassification"}}},
                search=True)
    hits = r["hits"]["hits"]
    for h in hits:
        s = h["sourceAsMap"]; classes.setdefault(s.get("core.name"), s["core.identity"])
    frm += 200
    if len(hits) < 200:
        break

col = identity_of("<catalogSourceId>://<db>/<schema>/<table>/<column>~com.infa.odin.models.relational.Column")
call("PATCH", f"{API}/data360/content/v1/assets/{col}?scheme=internal",
     [{"operation": "add", "segment": "dataClassification", "items": [{"core.identity": classes["Email"]}]}])
```

- The asset page then shows "Data Element Classifications Accepted".
- Only classes that exist in the org can be applied (there may be First Name but no Full Name).
- Use it when Auto Classification infers nothing (seen even with fresh profiles) or to apply a reviewed list.

### 6.3 Accepting CLAIRE's suggestions in bulk: still a wall (L-CDGC-061)

- On the data360 plane nothing flipped `core.generatedClassification` to `core.acceptedClassification`:
  `POST /data360/classification/api/v1/accept`, `/dataclassification/.../accept`, `PUT.../status` and `/catalog/.../accept`
  all 404, `POST /public/core/v3/objects` is 405 and a per-object PATCH was 404 (37+ variants).
- In that tenant the UI auto-applied the classes and offered only a per-item Dismiss (X).
- **The bulk lever** is the catalog source's Data Classification capability configuration (auto-accept threshold) in MCC,
  applied on a re-scan.
- The type-level Data Classification configuration exposes no option groups, so there is no threshold to set over the
  type schema (L-CDGC-016).
- Not yet re-probed against the content-API segments. Known partial routes: manual application (6.2) and the
  browser-captured Classification Promotion job (6.4).

### 6.4 Classification Promotion job (disputed; L-CDGC-063)

`POST https://ccgf-api.<domain>.informaticacloud.com/ccgf-orchestration-management-api-server/api/v1/management/job` with
type 'Classification Promotion' returned 200 + jobId from an authenticated browser session; the undo was a
ccgf-contentv2 publish with curationStatus REJECTED. The body is not recorded, it was never re-proven headless, and a
same-day check of another tenant found only Dismiss in the UI. Treat it as a lead: capture the request from the browser
before relying on it.

### 6.5 Counting, propagating and moving classifications

- Coverage: count `core.generatedClassification` / `core.acceptedClassification` through search facets
  (`/data360/classification/api/v1/classifications` 404s) (L-CDGC-076, L-CDGC-077); count PII by the classification's
  sensitivity (L-CDGC-075).
- Propagation: walk lineage from classified source columns and propose the same class for derived columns as a reviewed
  worklist, then apply it with the PATCH in 6.2 (L-CDGC-069).
- Moving out of CDGC: export per-column assignments as data; a rule-based classifier elsewhere does not reproduce CLAIRE's
  output (L-CDGC-083).
- Before a personal-data answer in CLAIRE GPT, check that the columns carry classifications: with none in the catalog,
  'Which columns ... contain personal data' named one column 'based on its column name' and said none of 17 columns had
  a classification. A new catalog tenant can start without data element classifications (L-CDGC-204), so run Data
  Classification on the source first (L-MCP-129, 2026-10-27).

## 7. Stewardship (stakeholders): still UI (L-CDGC-066)

- `core.assignedStakeholders` and `core.stakeholders` are read-only over REST: stewardship, stakeholder and responsibility
  paths 404, `/data360/asset/v1/*/stakeholders` is 404/405 (PUT 405) across 100+ variants, a per-object PATCH is 404, and
  there is no stakeholder object to clone. `PUT /dataCollections/<id>` with stakeholder ids echoes 200 without persisting.
- UI path: MCC > Associations > Stakeholders > Assign Stakeholders > pick the role (Data Owner, Data Steward) > users. The
  roles must already exist in Administrator or the picker is empty.
- Keep ownership as code: a RACI table (data owner, data steward, technical steward per asset) is the authoritative store;
  the catalog assignment mirrors it.
- Not re-probed with the content-API segments; a stakeholder segment on the content PATCH is untested.

## 8. Policies and Data Access Management

- **DAM policy authoring has no REST plane on the probed orgs** (L-CDGC-067): the DAM engine can run and the
  `feature.cdam.*` flags can be present while `cdam-policy-api` and about 40 `/data360/dam/v1/policies` variants 404 on
  every verb and `<pod>-dam` has no DNS. Build the first policy in the UI. The verdict is org-scoped (a third-party tool
  fleet ships policy tools): ask which path they call before calling it a platform wall.
- **Demonstrate the controls as pushdown** while authoring is walled: access control (per-role column projection), row
  filters (role- or region-scoped predicates) and de-identification (deterministic email pseudonym, name mask, date
  truncation) as warehouse views or table functions, with assertions that nothing leaks.
- **Governance-as-code** (L-CDGC-068): a versioned policy catalog linked to datasets through the PII classification, and a
  PII inventory built from the CLAIRE export plus a live schema pass; bind protection to classification tags so new
  columns inherit it.

## 9. QuickLook and other glossary surfaces

- QuickLook (in-context glossary definitions) is a per-user browser extension: no server enablement, `/data360/quicklook/*`
  404s; it needs a catalog with published terms (L-CDGC-070).
- Term Relationships (term to column, query field, DQ rule) come from links (section 5); the Hierarchy tab comes from the
  parent (section 3.2).

## 10. Making CLAIRE answer from the glossary (L-CDGC-072)

Create a domain whose description states the company, what it does and its goal; add a term for every business concept
(including one that explains legacy technical names); link each term to its tables, columns and CRM objects; curate
descriptions on sources, databases and schemas; set descriptions in the source systems; then test a fixed question set
phrased as "the business term X". CLAIRE answered 18 of 18 such questions. Prompt rules, index lag and demo hygiene are in
[CLAIRE & MCP](../09-claire-mcp/) and [04](04-search-lineage-marketplace.md) section 8.

## 11. Rebuilding glossary content in another org

1. Export read-only from the source org: domains, terms (name, description, domain), links (term > asset externalId),
   curated descriptions (asset externalId > text), applied classifications (column externalId > class name).
2. In the target: recreate and scan the catalog sources first ([02](02-catalog-sources-create-scan-update-purge.md)).
3. Remap external ids by replacing the old catalog-source id prefix with the new one (L-CDGC-058).
4. Create domains and terms (3.1, 3.2), then links (5.1), descriptions (4) and classifications (6.2), each idempotent with
   a registry, a per-item log and undo files.
5. Read back counts (terms, links, classified columns) against the export.
