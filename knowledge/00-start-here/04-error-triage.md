# Error Triage

**Answers:** What does this IDMC error code, status or message really mean, what is the fix, and which doc explains it?

**Read when:** a call, run, scan, test or prompt fails, or succeeds suspiciously (an empty 200, a value that reverts,
a lane that reads FAILED while its data landed).

**Key rules:**
- Read the body, not the status: an HTML or zero-byte 200 is not success (L-AUTH-006, L-AUTH-007).
- Bogus-twin any surprising answer before you believe it either way (L-METHOD-024).
- Most errors mean the wrong host, header, path, body or gate, rarely "not licensed" (L-AUTH-070, L-AGENT-034).
- In a session log, read the first `[ERROR]`: later token or write errors can be a cascade (L-CDI-210).
- Retry a failed run once, and only on a transient signature; never retry the job-cap error (L-CDI-205,
  L-IPU-041).

## Triage in five checks

1. **Read the body, not the status.** Empty, HTML (starts with `<`) or a value that reverts on read-back is not success.
2. **Right host, right header?** Compare the call with the plane map in
   [Pods, Hosts & Service Planes](../01-access-auth-orgs/01-pods-hosts-service-planes.md); check `dm-us`
   versus `dmp-us` and the pod host versus `<pod>-<service>`.
3. **Bogus twin.** Send the same call with a nonsense path, name or host. An identical answer is an artifact.
4. **Look the signature up below** (Ctrl+F the code or a distinctive phrase). The rows are grouped: HTTP status
   patterns, then code families in alphabetical order, then messages without a code, by area.
5. **Not listed?** Grep the KB and `lessons` for the exact string, then the reference library's status-code
   decoder. Record what you learn as a lesson.
