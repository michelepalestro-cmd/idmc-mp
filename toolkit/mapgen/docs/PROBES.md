# Probes: transformations and writer options proven on a real Secure Agent

Every feature below was generated by idmc_mapgen, imported as a package, wrapped in a mapping task, run on a
Secure Agent, and checked row by row in the target. The specs are in `examples/probes/`; each one runs as is
against your own profile (`${DATASET}` = a scratch BigQuery dataset, `${PG_SCRATCH}` = a scratch PostgreSQL
schema, connection aliases `BQ` and `PG`).

Verdicts: **WORKS** (rows checked), **RUN-FAILED** (imports, fails at run time), **IMPORT-REJECTED**,
**NOT TRIED** (with the reason). Measured 2026-10-03, Data Integration Server 77.0.x, BigQuery V2 and
PostgreSQL connectors; the flat-file target row on 2026-11-03.

BigQuery and PostgreSQL are simply the connections the test org had; they are not a recommendation. Transformation
behaviour (lookups, normalizer, parameters, mapplets) is decided by the engine and carries to any source and target.
Writer options (truncate, upsert, pre/post SQL) are per connector: re-probe them on yours with one small spec.

## Details and traps

### Connected Lookup
- Spec: `{"type": "lookup", "name": "LKP_STORE", "connected": true, "conn": "BQ", "query": "SELECT ...", "fields": [...],
  "cond": [["lk_store_id", "store_id"], ["lk_region", "=", "region"]], "policy": "Use First Value"}`.
- IMF: `TmplLookup` with `unconnected="false"`, one `DefaultGroup` (input and output, all-fields rule), `returnPortName=""`,
  `inputPortNames=[]`, `LookupCondition{leftOperand=<lookup field>, operator, rightOperand=<incoming field>}`.
- Every lookup field leaves the lookup as a port: prefix them (`lk_`) so they cannot collide with incoming names.
- Policies: Use First Value, Use Last Value, Use Any Value, Use All Values (one row per match), Report Error.

### Target write operations
- IMF operation names: `Insert`, `Update`, `Upsert`, `Delete`, and `Rowbased` (= Data Driven).
  `WriteOptions.updateStrategyExpression` is read only for `Rowbased`.
- Writer attributes are connector-specific and live in two lists: `oprRuntimeAttributes` (internal names) and
  `runtimeAttributes` (display names). Booleans are `YES` / `NO`. The connector's own attribute catalogue is in its
  `*modelattributes*.jar` -> `plugin.xml` on the agent (`ModelProperty name=... displayName=...`).
- BigQuery writer attributes used: `UpdateMode` (Update As Update | Update Else Insert), `isMergeEnabled` /
  "Enable Merge", `isDataDrivenEnabled` / "Enable Data Driven", `preSQLWriter` / "pre SQL", `postSQLWriter` / "post SQL".
- PostgreSQL writer attributes used: `UpdateMode` / "Update Mode", `TruncateTable` / "Truncate target",
  `preSQL` / "Pre-SQL", `postSQL` / "Post-SQL".
- The BigQuery Upsert works by UPDATE from a staging table, then nulling the matched keys in the staging table, then
  INSERT. Duplicate keys in the TARGET make the second step fail with
  `UPDATE/MERGE must match at most one source row for each target row` (the log says "Check if there are duplicate
  key values in the target table"). Keep keyed targets unique.

### In-out parameters
- `"inOutParameters": [{"name": "p_max_seq", "type": "INTEGER", "default": "0", "aggregation": "MAX",
  "retention": "ON_SUCCESS_OR_WARNING"}]` -> `Template.variables` (`SessionVariable`).
- Reference them as `$$p_max_seq` anywhere an expression is allowed (filter condition, expression port, source query).
- `SETMAXVARIABLE($$p, value)` / `SETMINVARIABLE` / `SETCOUNTVARIABLE` / `SETVARIABLE` update the value; it is persisted
  at the end of a run according to `retention`. This is the incremental-load (high-water mark) pattern.

### Normalizer
- Spec `fields` = the normalized fields; `occurs: n` creates inputs `<name>_1..<name>_n` and one output `<name>` plus
  `GCID_<name>`. `map` binds normalizer inputs to incoming fields. Only normalized fields (+ GCID_/GK_) leave it.
- IMF: `TmplNormalizer` (`fieldsMode NOT_PARAMETERIZED`, `normalizerFields.fieldList` of `NormalizerField{occurs, level}`,
  `inputFields` / `outputFields` of `NormalizerTxField{occurrence, referenceField}`, `manualMappings.mappingList` of
  `NormalizerFieldMapping{fromFieldName, toField}`).

### Running totals without window functions
Sort by the partition and order keys, then use VARIABLE ports. A VARIABLE port that reads a variable defined below it
(or itself) gets that variable's value from the previous row, because ports are evaluated top to bottom:

    v_same      = IIF(customer_id = v_prev_cust, 1, 0)
    v_run       = IIF(v_same = 1, v_run + amount, amount)
    v_lag       = IIF(v_same = 1, v_prev_amt, NULL)
    v_prev_amt  = amount
    v_prev_cust = customer_id

### Other observations
- A REUSE import of a new mapping does not keep the package's GUID: the imported mapping gets a new FRS id. Look the
  mapping up by name inside its folder after the import, and rebuild later packages with that id (OVERWRITE).
- A shell hop that re-runs a command can run seed SQL twice. Seed test tables with one atomic statement per table
  (`CREATE OR REPLACE TABLE t AS SELECT ...`), never `CREATE` + separate `INSERT`.

### Mapplets
- Build: a spec with `"documentType": "DMAPPLET"`, an `input` node (TmplInput: one output group, declared fields), the
  logic, and an `output` node (TmplOutput: `OutputFieldMappings` of `OutputFieldMapping{fromFieldName, toField}`).
  `compile.build` + `nodes.mapplet.mapplet_package_bytes` -> import (REUSE). Example: `examples/probes/mplt_ex_clean_names.json`.
- Call: `{"type": "mapplet", "mappletGuid": "<frs id>", "inputs": [...], "outputs": [...], "map": {mapplet input: incoming field}}`
  (TmplMapplet `type NATIVE`, `saasMappletId "@<id>"`, `inputGroups` / `outputGroups` of `TxFieldGroup`, `MappletAdapter`,
  `fieldMapping`), plus an `assets` entry (`type DMAPPLET`, its folder path) so the package declares the dependency.
  Look the mapplet's id up by name in its folder after its import (a REUSE import assigns a new id).
- Only the mapplet's outputs leave it; carry other fields around it (Joiner) or route them through the mapplet.
- Shipped bundle mapplets (for example the core data-quality set) cannot be exported by a non-admin user
  (`MigrationSvc_038`), so their port lists are not readable headless; generate your own mapplets instead.

### SQL transformation (not working yet)
- **RUN-FAILED** (3 variants against PostgreSQL). The package imports and the mapping reads as
  valid (`TmplSql` + `SqlAdapter{sql, sqlType ENTERED_QUERY, typeSystem TOOLKIT, fields}`, `SqlField{fieldType IN|OUT|INOUT}`,
  generated `SQLError` port), but the run dies at DTM start with "The DTM process terminated unexpectedly". The session log
  shows why the pipeline breaks: `Could not create link From Field:k ... To Field:k Instance:SQL_STOCK` (the incoming
  field never reaches the SQL transformation, with or without a bound `?param?`, with an all-fields rule or a name rule,
  and with the field declared INOUT + passthroughPort) and `Invalid table attribute: Connection Information`. The node
  (`nodes/sql.py`) is kept for the next attempt; the missing piece is the pass-through port shape, which one UI-authored
  SQL transformation exported once (route 4) would show.
